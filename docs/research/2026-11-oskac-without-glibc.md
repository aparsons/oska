# What is needed to remove the Oska toolchain's dependency on glibc, so that the released `oskac` Linux binaries (aarch64 and x86_64) run on any Linux, including a `FROM scratch` container image or a musl-based distro?

Accessed: 2026-11-19

## Short answer

The glibc dependency is not caused by any crate: the workspace has no third-party crates and no build scripts. It comes from two things. The release builds use the `*-linux-gnu` target, which links glibc dynamically. And `oska-sys` declares eight C-library functions, which `std` already links. Building the two Linux release binaries for `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl` gives static executables that need no C library at run time. Both are Tier 2 targets with host tools and full `std`. Both are statically linked by default, and Rust bundles musl 1.2.5 for them. No source change should be needed. The work is in the release workflow, CI, the installer and its tests, and the docs. A fully libc-free `oskac` (raw system calls, `no_std`) is possible in principle, but it is not realistic for this codebase.

## 1. Why `oskac` needs glibc today (repo findings)

- **The toolchain.** Rust 1.100.0 is pinned with no `targets` list, so only the host target is installed ([rust-toolchain.toml](../../rust-toolchain.toml)). Here `rustup target list --installed` shows only `x86_64-unknown-linux-gnu`.
- **No external crates.** The workspace has seven path crates and nothing else ([Cargo.toml](../../Cargo.toml)). `Cargo.lock` lists only those seven ([Cargo.lock](../../Cargo.lock)). No crate has a `build.rs`, and there is no `.cargo/config*`. Nothing like `cc`, `openssl`, `libgit2` or `ring` is in the tree, so no crate blocks musl.
- **Checked-in cargo config and workflow `RUSTFLAGS` are refused.** The unsafe guard rejects a checked-in cargo config, and any workflow that sets `RUSTFLAGS`, a rustc wrapper or `--cap-lints` ([scripts/unsafe-guard/guard.sh](../../scripts/unsafe-guard/guard.sh)). Because of this, `-C target-feature=+crt-static` cannot be added the usual way without changing the guard. A musl target needs no flags.
- **`oska-sys` calls the C library directly.** It declares `openat`, `mkdirat`, `renameat`, `unlinkat`, `fdopendir`, `readdir`, `closedir`, `__errno_location` and `geteuid` itself. These resolve against the C library that `std` already links ([crates/oska-sys/src/unix.rs](../../crates/oska-sys/src/unix.rs), [crates/oska-sys/src/lib.rs](../../crates/oska-sys/src/lib.rs), [ADR 0009](../adr/0009-oska-sys-is-the-only-crate-with-unsafe.md)). Its constants are chosen with `target_os`/`target_arch` and not `target_env`, so they apply to both `linux-gnu` and `linux-musl`. Its `D_NAME_OFFSET` is 19 on both Linux architectures ([unix.rs](../../crates/oska-sys/src/unix.rs)).
- **What the binary links.** A local debug build (`target/debug/oskac`, built on a newer host) is a dynamically linked PIE with interpreter `/lib64/ld-linux-x86-64.so.2`. It has `NEEDED` entries `libgcc_s.so.1`, `libc.so.6` and `ld-linux-x86-64.so.2` (`file` and `readelf -d`, run read-only). It imports about 120 glibc symbols. The strong ones go up to `GLIBC_2.34` (`__libc_start_main`, `pthread_*`). The newest versions (`pidfd_spawnp`, `GLIBC_2.39`) are `WEAK` imports that `std` uses only when they exist. The binary imports no NSS functions (`getaddrinfo`, `getpwnam`) and no `dlopen`. It has only `dlsym` and `dl_iterate_phdr` (`objdump -T`, `readelf --dyn-syms`).
- **Release builds.** Linux binaries are built natively on `ubuntu-22.04` and `ubuntu-22.04-arm` with `cargo build --release --locked -p oskac`. The workflow then fails if `objdump -T` shows a symbol version newer than `GLIBC_2.35` ([.github/workflows/release.yml](../../.github/workflows/release.yml)).
- **Installer and docs.** `install.sh` hard-codes `MIN_GLIBC=2.35`. It probes `getconf GNU_LIBC_VERSION` and `ldd --version`, and stops with `unsupported_libc` on musl or an older glibc ([scripts/install/install.sh](../../scripts/install/install.sh)). Its tests check this refusal ([scripts/install/test.sh](../../scripts/install/test.sh)). The install guide documents the limit ([docs/guide/install.md](../guide/install.md)), and so does the release runbook ([docs/agents/release.md](../agents/release.md)).
- **Asset names and checksums.** `assemble.sh` lists `oskac-linux-x86_64` and `oskac-linux-aarch64` by name and hashes them into `SHA256SUMS` ([scripts/release/assemble.sh](../../scripts/release/assemble.sh)). Nothing in the names says glibc.
- **Context.** Programs that `oskac` emits are already static and libc-free. ADR 0011 makes the Linux output "a static ELF executable that makes system calls directly with no libc" ([ADR 0011](../adr/0011-oska-generates-native-code-itself.md)), and only `std.rt` may make those calls ([ADR 0013](../adr/0013-system-calls-only-in-std-rt.md)). The OS research note leaves a static or musl `oskac` "an open item" for a `FROM scratch` toolchain image ([2026-11-oska-operating-system.md](2026-11-oska-operating-system.md)). Supported platforms are fixed by [ADR 0014](../adr/0014-every-supported-platform-builds-and-runs-natively.md). ADR 0012 is not affected: TLS and git will be Oska code, not C libraries ([ADR 0012](../adr/0012-tls-git-and-crypto-are-written-in-oska.md)).
- **A glibc-specific behaviour the interpreter copies.** The native runtime's `canonical` mirrors "Rust's `fs::canonicalize`, which is glibc's `realpath`", and its `getcwd` handling also follows glibc ([crates/oska-check/src/std/rt.osk](../../crates/oska-check/src/std/rt.osk)). The interpreter calls `std::fs::canonicalize` ([crates/oska-run/src/host.rs](../../crates/oska-run/src/host.rs)). Under musl these calls would go through musl's `realpath`/`getcwd`.

## 2. The Rust musl targets

- `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl` are "Tier 2 with Host Tools", described as "64-bit Linux with musl 1.2.5" and "ARM64 Linux with musl 1.2.5". The `*-linux-gnu` targets are Tier 1 and need glibc 2.17+ ([rustc book, Platform Support](https://doc.rust-lang.org/rustc/platform-support.html)). All Tier 2 targets with host tools support the full standard library ([Platform Support](https://doc.rust-lang.org/rustc/platform-support.html)).
- The Reference says most targets link the C runtime dynamically by default. It lists `x86_64-unknown-linux-musl` among the exceptions that "are static by default" ([Reference, Linkage](https://doc.rust-lang.org/reference/linkage.html#static-and-dynamic-c-runtimes)). Its list does not name aarch64. The aarch64 target spec, however, sets `crt_static_default = true`, with a FIXME that musl targets should eventually be dynamic by default ([aarch64_unknown_linux_musl.rs](https://raw.githubusercontent.com/rust-lang/rust/main/compiler/rustc_target/src/spec/targets/aarch64_unknown_linux_musl.rs)). The x86_64 spec sets the same flag ([x86_64_unknown_linux_musl.rs](https://raw.githubusercontent.com/rust-lang/rust/main/compiler/rustc_target/src/spec/targets/x86_64_unknown_linux_musl.rs)).
- **Static-pie.** The x86_64 musl spec sets `static_position_independent_executables = true` ([x86_64_unknown_linux_musl.rs](https://raw.githubusercontent.com/rust-lang/rust/main/compiler/rustc_target/src/spec/targets/x86_64_unknown_linux_musl.rs)). The summary of the aarch64 spec did not list that option ([aarch64 spec](https://raw.githubusercontent.com/rust-lang/rust/main/compiler/rustc_target/src/spec/targets/aarch64_unknown_linux_musl.rs)). So whether the aarch64 binary is static-pie or plain static (non-PIE) remains open, and only the built binary can settle it. Both kinds run without a dynamic loader.
- **Self-contained linking.** The shared musl base sets `link_self_contained: InferredForMusl` and uses musl's own self-contained CRT objects ([base/linux_musl.rs](https://raw.githubusercontent.com/rust-lang/rust/main/compiler/rustc_target/src/spec/base/linux_musl.rs)). Inference: the rustup `rust-std` component for the target ships musl's `libc.a` and CRT objects. A native build on an Ubuntu runner should then need only the host `cc` as linker driver, with no `musl-gcc` or cross toolchain. The first CI run must confirm this.
- **musl version.** The newest musl release is 1.2.6 (20 March 2026) ([musl releases](https://musl.libc.org/releases.html)). Rust 1.100.0's targets still say 1.2.5 ([Platform Support](https://doc.rust-lang.org/rustc/platform-support.html)). Inference: the bundled musl moves only when Rust updates it, so musl fixes come through `scripts/bump-rust.sh` like any other toolchain change.
- **`oska-sys` on musl.** musl's `struct dirent` is `d_ino`, `d_off`, `d_reclen`, `d_type`, `d_name[256]` ([musl arch/generic/bits/dirent.h](https://git.musl-libc.org/cgit/musl/plain/arch/generic/bits/dirent.h); [musl include/dirent.h](https://git.musl-libc.org/cgit/musl/plain/include/dirent.h)). Inference: `ino_t` and `off_t` are 64-bit on musl's 64-bit ports. That puts `d_name` at offset 8+8+2+1 = 19, which matches `D_NAME_OFFSET`. The `O_*`/`E*` values are the kernel's and do not depend on the libc. musl also exports `__errno_location`. The existing escape tests on a musl build must confirm all of this; the sources read here do not prove it.
- **Threads.** musl's default thread stack is 128 KiB ([musl, functional differences](https://wiki.musl-libc.org/functional-differences-from-glibc.html)). `oska-run` already spawns its interpreter thread with an explicit `stack_size(STACK_SIZE)` ([crates/oska-run/src/lib.rs](../../crates/oska-run/src/lib.rs)). Inference: the smaller default does not affect it.
- **Name resolution.** musl's resolver differs from glibc's. For example, it queries all nameservers in parallel and supported DNS over TCP only from 1.2.4 ([musl, functional differences](https://wiki.musl-libc.org/functional-differences-from-glibc.html)). `oskac` does not resolve names today (no `getaddrinfo` import, see §1). Inference: once the ADR 0012 fetcher exists, it should use its own Oska DNS code or none, not libc.

## 3. Why not `+crt-static` on `*-linux-gnu`

- `-C target-feature=+crt-static` asks for a static C runtime. "Targets which do not support switching between linkage of the C runtime will ignore this flag", so the Reference advises inspecting the binary ([Reference, Linkage](https://doc.rust-lang.org/reference/linkage.html#static-and-dynamic-c-runtimes)).
- glibc's NSS modules are shared objects named `libnss_SERVICE.so.N`, such as `libnss_files.so.2` ([glibc manual, NSS Module Names](https://sourceware.org/glibc/manual/latest/html_node/NSS-Module-Names.html); [glibc manual, Name Service Switch](https://sourceware.org/glibc/manual/latest/html_node/Name-Service-Switch.html)). Inference: a statically linked glibc program that uses NSS functions (user, group and host lookups) still loads those modules at run time. In a `FROM scratch` image they are missing, and on another distro they may not match. `oskac` imports none of these functions today, but the glibc FAQ entry on this could not be read (the site blocked the fetch), so this limit is cited only through the manual.
- Inference: there are three more reasons. glibc is LGPL, so a static glibc binary carries relinking obligations that a musl (MIT) binary does not. The repo's guard refuses `RUSTFLAGS` in workflows ([guard.sh](../../scripts/unsafe-guard/guard.sh)), so the flag would need a guard exception. And the musl targets make static the default with no flag. Prefer musl.

## 4. Allocator performance

- In Rust, "the default global allocator is unspecified". `#[global_allocator]` on a `static` whose type implements `GlobalAlloc` replaces it, and it "can only be used once in a crate or its recursive dependencies" ([std::alloc](https://doc.rust-lang.org/std/alloc/index.html)). The trait's implementation is `unsafe impl` ([std::alloc](https://doc.rust-lang.org/std/alloc/index.html)).
- musl 1.2.1 replaced its old allocator with "mallocng". The release notes stress hardening ("strong hardening against memory usage errors by the caller") and returning memory "on a much finer granularity", not speed ([musl releases](https://musl.libc.org/releases.html)). No primary source read here measures mallocng against glibc's malloc, so the size of any slowdown for `oskac` is **open**.
- Inference: the interpreter (`oska-run`) and the checker allocate heavily, so measure before release. Run `scripts/bench-native.sh` and the test suite's wall time on gnu and musl builds ([.github/workflows/bench.yml](../../.github/workflows/bench.yml)). If musl is clearly slower, the workspace's no-external-crates rule rules out `mimalloc` or `jemalloc` crates. A custom `GlobalAlloc` needs `unsafe`, so it could live only in `oska-sys` ([ADR 0009](../adr/0009-oska-sys-is-the-only-crate-with-unsafe.md)). For example, it could be a size-class or arena allocator over `mmap`, which `std` can reach only through libc. That is real security-sensitive work. Try cheaper fixes first: fewer allocations in hot paths, or `Vec::with_capacity`.

## 5. What GitHub Actions provides

- Public repositories get free `ubuntu-22.04`, `ubuntu-24.04`, `ubuntu-26.04` and `ubuntu-latest` x64 runners, and `ubuntu-22.04-arm`, `ubuntu-24.04-arm` and `ubuntu-26.04-arm` arm64 runners. `ubuntu-slim` runs as an unprivileged container ([GitHub Docs, GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)).
- A job can run its steps in a container with `jobs.<job_id>.container.image` (any Docker Hub or registry image). In a container the default shell is `sh`, not `bash` ([GitHub Docs, Run jobs in a container](https://docs.github.com/en/actions/how-tos/write-workflows/choose-where-workflows-run/run-jobs-in-a-container)). Inference: this allows a smoke-test job that runs the built `oskac` inside `alpine` (and a `scratch`-like image built in the job) on both architectures.
- The rustup toolchain file's `targets` key lists "platforms to install for cross-compilation" ([rustup, Overrides](https://rust-lang.github.io/rustup/overrides.html)). Inference: adding the two musl targets to `rust-toolchain.toml` installs them on every runner and the Pi, with no `rustup target add` step. This is lighter than a separate workflow step, but every clone then downloads two extra `rust-std` components. A `rustup target add` step in the release and CI jobs only is the leaner alternative.
- Inference: the native ARM runner keeps ADR 0014's "builds and runs natively" practice, so cross-compiling is not needed.

## 6. A fully libc-free `oskac`?

- `#![no_std]` stops `std` being linked automatically and switches to the `core` prelude ([Reference, Preludes](https://doc.rust-lang.org/reference/names/preludes.html#the-no_std-attribute)). A `no_std` binary must supply its own `#[panic_handler]` with signature `fn(&PanicInfo) -> !`, and only one may exist in the dependency graph ([Reference, Panic](https://doc.rust-lang.org/reference/panic.html)). It also needs a global allocator to use `alloc` ([std::alloc](https://doc.rust-lang.org/std/alloc/index.html)).
- Inference: for `oskac` this means replacing `std::fs`, `std::io`, `std::env`, `std::process` and `std::thread`, used in 33 source files, and `HashMap`/`HashSet`, used in 12 (repo count by `grep`). It also means writing an entry point, argument and environment parsing, a panic handler, an allocator and a raw-syscall layer. All of that is `unsafe` and would have to sit in `oska-sys`, and it would be Linux-only, because macOS and Windows have no stable syscall ABI ([ADR 0011](../adr/0011-oska-generates-native-code-itself.md), [ADR 0014](../adr/0014-every-supported-platform-builds-and-runs-natively.md)). That is weeks of work and a large new `unsafe` surface, in exchange for removing a statically linked, MIT-licensed musl that already has no run-time dependency. Not realistic now. The natural route to a libc-free toolchain is a self-hosted `oskac` written in Oska and compiled by its own native backend, which is already libc-free on Linux.

Total for steps 1–8: about 3–6 working days. The main unknowns are the musl `realpath`/`dirent` checks (step 2) and the allocator cost (step 3).

## Open questions

- How much slower `oskac` is with musl's mallocng than with glibc malloc. None of the sources read measures it, so step 3 has to.
- Whether the aarch64 musl binary is static-pie or non-PIE static. The target spec summary did not show `static_position_independent_executables`.
- Whether musl's `realpath`/`getcwd` match the glibc behaviour that `std.rt` copies in every edge case.
- The glibc FAQ on static linking and NSS could not be fetched (bot protection), so §3 relies on the manual's NSS pages and inference.
