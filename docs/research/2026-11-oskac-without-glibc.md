# What is needed to remove the Oska toolchain's dependency on glibc, so that the released `oskac` Linux binaries (aarch64 and x86_64) run on any Linux, including a `FROM scratch` container image or a musl-based distro?

Accessed: 2026-11-19

## Short answer

The glibc dependency is not caused by any crate: the workspace has no third-party crates and no build scripts. It comes from two things. The release builds use the `*-linux-gnu` target, which links glibc dynamically. And `oska-sys` declares nine C-library functions, which `std` already links. Building the two Linux release binaries for `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl` gives static executables that need no C library at run time. Both are Tier 2 targets with host tools and full `std`. Both are statically linked by default, and Rust bundles musl 1.2.5 for them. No source change should be needed. The work is in the release workflow, CI, the installer and its tests, and the docs. A fully libc-free `oskac` (raw system calls, `no_std`) is possible in principle, but it is not realistic for this codebase.

## 1. Why `oskac` needs glibc today (repo findings)

- **The toolchain.** Rust 1.100.0 is pinned with no `targets` list, so only the host target is installed ([rust-toolchain.toml](../../rust-toolchain.toml)). Here `rustup target list --installed` shows only `x86_64-unknown-linux-gnu`.
- **No external crates.** The workspace has seven path crates and nothing else ([Cargo.toml](../../Cargo.toml)). `Cargo.lock` lists only those seven ([Cargo.lock](../../Cargo.lock)). No crate has a `build.rs`, and there is no `.cargo/config*`. Nothing like `cc`, `openssl`, `libgit2` or `ring` is in the tree, so no crate blocks musl.
- **Checked-in cargo config and workflow `RUSTFLAGS` are refused.** The unsafe guard rejects a checked-in cargo config, and any workflow that sets `RUSTFLAGS`, a rustc wrapper or `--cap-lints` ([scripts/unsafe-guard/guard.sh](../../scripts/unsafe-guard/guard.sh)). Because of this, `-C target-feature=+crt-static` cannot be added the usual way without changing the guard. A musl target needs no flags.
- **`oska-sys` calls the C library directly.** It declares `openat`, `mkdirat`, `renameat`, `unlinkat`, `fdopendir`, `readdir`, `closedir`, `__errno_location` and `geteuid` itself. These resolve against the C library that `std` already links ([crates/oska-sys/src/unix.rs](../../crates/oska-sys/src/unix.rs), [crates/oska-sys/src/lib.rs](../../crates/oska-sys/src/lib.rs), [ADR 0009](../adr/0009-oska-sys-is-the-only-crate-with-unsafe.md)). Its constants are chosen with `target_os`/`target_arch` and not `target_env`, so they apply to both `linux-gnu` and `linux-musl`. Its `D_NAME_OFFSET` is 19 on both Linux architectures ([unix.rs](../../crates/oska-sys/src/unix.rs)).
- **What the binary links.** A local debug build (`target/debug/oskac`, built on a newer host) is a dynamically linked PIE with interpreter `/lib64/ld-linux-x86-64.so.2`. It has `NEEDED` entries `libgcc_s.so.1`, `libc.so.6` and `ld-linux-x86-64.so.2` (`file` and `readelf -d`, run read-only). It imports about 120 glibc symbols. The strong ones go up to `GLIBC_2.34` (`__libc_start_main`, `pthread_*`). The newest versions (`pidfd_spawnp`, `GLIBC_2.39`) are `WEAK` imports that `std` uses only when they exist. The binary imports no NSS functions (`getaddrinfo`, `getpwnam`) and no `dlopen`. It has only `dlsym` and `dl_iterate_phdr` (`objdump -T`, `readelf --dyn-syms`).
- **Release builds.** Linux binaries are built natively on `ubuntu-22.04` and `ubuntu-22.04-arm` with `cargo build --release --locked -p oskac`. The workflow then fails if `objdump -T` shows a symbol version newer than `GLIBC_2.35` ([.github/workflows/release.yml](../../.github/workflows/release.yml)).
- **Installer and docs.** `install.sh` hard-codes `MIN_GLIBC=2.35`. It probes `getconf GNU_LIBC_VERSION` and `ldd --version`, and stops with `unsupported_libc` on musl or an older glibc ([scripts/install/install.sh](../../scripts/install/install.sh)). Its tests check this refusal ([scripts/install/test.sh](../../scripts/install/test.sh)). The install guide documents the limit ([docs/guide/install.md](../guide/install.md)), and so does the release runbook ([docs/agents/release.md](../agents/release.md)).
- **Asset names and checksums.** `assemble.sh` lists `oskac-linux-x86_64` and `oskac-linux-aarch64` by name and hashes them into `SHA256SUMS` ([scripts/release/assemble.sh](../../scripts/release/assemble.sh)). Nothing in the names says glibc.
- **Context.** Programs that `oskac` emits are already static and use no C library. ADR 0011 makes the Linux output "a static ELF executable that makes system calls directly with no libc" ([ADR 0011](../adr/0011-oska-generates-native-code-itself.md)), and only `std.rt` may make those calls ([ADR 0013](../adr/0013-system-calls-only-in-std-rt.md)). The OS research note leaves a static or musl `oskac` "an open item" for a `FROM scratch` toolchain image ([2026-11-oska-operating-system.md](2026-11-oska-operating-system.md)). Supported platforms are fixed by [ADR 0014](../adr/0014-every-supported-platform-builds-and-runs-natively.md). ADR 0012 is not affected: TLS and git will be Oska code, not C libraries ([ADR 0012](../adr/0012-tls-git-and-crypto-are-written-in-oska.md)).
- **A glibc-specific behaviour the interpreter copies.** The native runtime's `canonical` mirrors "Rust's `fs::canonicalize`, which is glibc's `realpath`", and its `getcwd` handling also follows glibc ([crates/oska-check/src/std/rt.osk](../../crates/oska-check/src/std/rt.osk)). The interpreter calls `std::fs::canonicalize` ([crates/oska-run/src/host.rs](../../crates/oska-run/src/host.rs)). Under musl these calls would go through musl's `realpath`/`getcwd`.

## 2. The Rust musl targets

- `x86_64-unknown-linux-musl` and `aarch64-unknown-linux-musl` are "Tier 2 with Host Tools", described as "64-bit Linux with musl 1.2.5" and "ARM64 Linux with musl 1.2.5". The `*-linux-gnu` targets are Tier 1 and need glibc 2.17+ ([rustc book, Platform Support](https://doc.rust-lang.org/rustc/platform-support.html)). All Tier 2 targets with host tools support the full standard library ([Platform Support](https://doc.rust-lang.org/rustc/platform-support.html)).
- The Reference says most targets link the C runtime dynamically by default. It lists `x86_64-unknown-linux-musl` among the exceptions that "are static by default" ([Reference, Linkage](https://doc.rust-lang.org/reference/linkage.html#static-and-dynamic-c-runtimes)). Its list does not name aarch64. The aarch64 target spec, however, sets `crt_static_default = true`, with a FIXME that musl targets should eventually be dynamic by default ([aarch64_unknown_linux_musl.rs](https://raw.githubusercontent.com/rust-lang/rust/main/compiler/rustc_target/src/spec/targets/aarch64_unknown_linux_musl.rs)). The x86_64 spec sets the same flag ([x86_64_unknown_linux_musl.rs](https://raw.githubusercontent.com/rust-lang/rust/main/compiler/rustc_target/src/spec/targets/x86_64_unknown_linux_musl.rs)).
- **Static-pie.** The x86_64 musl spec sets `static_position_independent_executables = true` ([x86_64_unknown_linux_musl.rs](https://raw.githubusercontent.com/rust-lang/rust/main/compiler/rustc_target/src/spec/targets/x86_64_unknown_linux_musl.rs)). The aarch64 spec file, as read, did not show that option ([aarch64 spec](https://raw.githubusercontent.com/rust-lang/rust/main/compiler/rustc_target/src/spec/targets/aarch64_unknown_linux_musl.rs)). So whether the aarch64 binary is static-pie or plain static (non-PIE) remains open, and only the built binary can settle it. Both kinds run without a dynamic loader.
- **Self-contained linking.** The shared musl base sets `link_self_contained: InferredForMusl` and uses musl's own self-contained CRT objects ([base/linux_musl.rs](https://raw.githubusercontent.com/rust-lang/rust/main/compiler/rustc_target/src/spec/base/linux_musl.rs)). Inference: the rustup `rust-std` component for the target ships musl's `libc.a` and CRT objects. A native build on an Ubuntu runner should then need only the host `cc` as linker driver, with no `musl-gcc` or cross toolchain. The first CI run must confirm this.
- **musl version.** The newest musl release is 1.2.6 (20 March 2026) ([musl releases](https://musl.libc.org/releases.html)). The current Platform Support page still says 1.2.5 ([Platform Support](https://doc.rust-lang.org/rustc/platform-support.html)). This note read the current docs and the `main` branch, not the 1.100.0 tag, so the spike (step 1) should confirm the bundled version for the pinned toolchain. Inference: the bundled musl moves only when Rust updates it, so musl fixes come through `scripts/bump-rust.sh` like any other toolchain change.
- **`oska-sys` on musl.** musl's `struct dirent` is `d_ino`, `d_off`, `d_reclen`, `d_type`, `d_name[256]` ([musl arch/generic/bits/dirent.h](https://git.musl-libc.org/cgit/musl/plain/arch/generic/bits/dirent.h); [musl include/dirent.h](https://git.musl-libc.org/cgit/musl/plain/include/dirent.h)). Inference: `ino_t` and `off_t` are 64-bit on musl's 64-bit ports. That puts `d_name` at offset 8+8+2+1 = 19, which matches `D_NAME_OFFSET`. The `O_*`/`E*` values are the kernel's and do not depend on the libc. musl also exports `__errno_location`. The existing escape tests on a musl build must confirm all of this; the sources read here do not prove it.
- **Threads.** musl's default thread stack is 128 KiB ([musl, functional differences](https://wiki.musl-libc.org/functional-differences-from-glibc.html)). `oska-run` already spawns its interpreter thread with an explicit `stack_size(STACK_SIZE)` ([crates/oska-run/src/lib.rs](../../crates/oska-run/src/lib.rs)). Inference: the smaller default does not affect it.
- **Name resolution.** musl's resolver differs from glibc's. For example, it queries all nameservers in parallel and supported DNS over TCP only from 1.2.4 ([musl, functional differences](https://wiki.musl-libc.org/functional-differences-from-glibc.html)). `oskac` does not resolve names today (no `getaddrinfo` import, see §1). Inference: once the ADR 0012 fetcher exists, it should use its own Oska DNS code or none, not libc.

## 3. Why not `+crt-static` on `*-linux-gnu`

- `-C target-feature=+crt-static` asks for a static C runtime. "Targets which do not support switching between linkage of the C runtime will ignore this flag", so the Reference advises inspecting the binary ([Reference, Linkage](https://doc.rust-lang.org/reference/linkage.html#static-and-dynamic-c-runtimes)).
- glibc's NSS modules are shared objects named `libnss_SERVICE.so.N`, such as `libnss_files.so.2` ([glibc manual, NSS Module Names](https://sourceware.org/glibc/manual/latest/html_node/NSS-Module-Names.html); [glibc manual, Name Service Switch](https://sourceware.org/glibc/manual/latest/html_node/Name-Service-Switch.html)). Inference: a statically linked glibc program that uses NSS functions (user, group and host lookups) still loads those modules at run time. In a `FROM scratch` image they are missing, and on another distro they may not match. `oskac` imports none of these functions today, but the glibc FAQ entry on this could not be read (the site blocked the fetch), so this limit is cited only through the manual.
- Inference: there are three more reasons. glibc is LGPL and musl is MIT-licensed, so a static glibc binary may carry relinking obligations that a musl binary does not. This note did not read the license texts, so check them before relying on this. The repo's guard refuses `RUSTFLAGS` in workflows ([guard.sh](../../scripts/unsafe-guard/guard.sh)), so the flag would need a guard exception. And the musl targets make static the default with no flag. Prefer musl.

## 4. Allocator performance

- In Rust, "the default global allocator is unspecified". `#[global_allocator]` on a `static` whose type implements `GlobalAlloc` replaces it, and it "can only be used once in a crate or its recursive dependencies" ([std::alloc](https://doc.rust-lang.org/std/alloc/index.html)). The trait's implementation is `unsafe impl` ([std::alloc](https://doc.rust-lang.org/std/alloc/index.html)).
- musl 1.2.1 replaced its old allocator with "mallocng". The release notes stress hardening ("strong hardening against memory usage errors by the caller") and returning memory "on a much finer granularity", not speed ([musl releases](https://musl.libc.org/releases.html)). No primary source read here measures mallocng against glibc's malloc, so the size of any slowdown for `oskac` is **open**.
- Inference: the interpreter (`oska-run`) and the checker allocate heavily, so measure before release. Run `scripts/bench-native.sh` and the test suite's wall time on gnu and musl builds ([.github/workflows/bench.yml](../../.github/workflows/bench.yml)). If musl is clearly slower, the workspace's no-external-crates rule rules out `mimalloc` or `jemalloc` crates. A custom `GlobalAlloc` needs `unsafe`, so it could live only in `oska-sys` ([ADR 0009](../adr/0009-oska-sys-is-the-only-crate-with-unsafe.md)). For example, it could be a size-class or arena allocator over `mmap`, which `std` can reach only through libc. That is real security-sensitive work. Try cheaper fixes first: fewer allocations in hot paths, or `Vec::with_capacity`.

## 5. What GitHub Actions provides

- Public repositories get free `ubuntu-22.04`, `ubuntu-24.04`, `ubuntu-26.04` and `ubuntu-latest` x64 runners, and `ubuntu-22.04-arm`, `ubuntu-24.04-arm` and `ubuntu-26.04-arm` arm64 runners. `ubuntu-slim` runs as an unprivileged container ([GitHub Docs, GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)).
- A job can run its steps in a container with `jobs.<job_id>.container.image` (any Docker Hub or registry image). In a container the default shell is `sh`, not `bash` ([GitHub Docs, Run jobs in a container](https://docs.github.com/en/actions/how-tos/write-workflows/choose-where-workflows-run/run-jobs-in-a-container)). Inference: this allows a smoke-test job that runs the built `oskac` inside `alpine` (and a `scratch`-like image built in the job) on both architectures.
- The rustup toolchain file's `targets` key lists "platforms to install for cross-compilation" ([rustup, Overrides](https://rust-lang.github.io/rustup/overrides.html)). Inference: adding the two musl targets to `rust-toolchain.toml` installs them on every runner and the Pi, with no `rustup target add` step. This is lighter than a separate workflow step, but every clone then downloads two extra `rust-std` components. A `rustup target add` step in the release and CI jobs only is the leaner alternative.
- Inference: the native ARM runner keeps ADR 0014's "builds and runs natively" practice, so cross-compiling is not needed.

## 6. An `oskac` with no C library at all?

- `#![no_std]` stops `std` being linked automatically and switches to the `core` prelude ([Reference, Preludes](https://doc.rust-lang.org/reference/names/preludes.html#the-no_std-attribute)). A `no_std` binary must supply its own `#[panic_handler]` with signature `fn(&PanicInfo) -> !`, and only one may exist in the dependency graph ([Reference, Panic](https://doc.rust-lang.org/reference/panic.html)). It also needs a global allocator to use `alloc` ([std::alloc](https://doc.rust-lang.org/std/alloc/index.html)).
- Inference: for `oskac` this means replacing `std::fs`, `std::io`, `std::env`, `std::process` and `std::thread`, used in 33 source files, and `HashMap`/`HashSet`, used in 12 (repo count by `grep`). It also means writing an entry point, argument and environment parsing, a panic handler, an allocator and a raw-syscall layer. All of that is `unsafe` and would have to sit in `oska-sys`, and it would be Linux-only, because macOS and Windows have no stable syscall ABI ([ADR 0011](../adr/0011-oska-generates-native-code-itself.md), [ADR 0014](../adr/0014-every-supported-platform-builds-and-runs-natively.md)). That is weeks of work and a large new `unsafe` surface, in exchange for removing a statically linked, MIT-licensed musl that already has no run-time dependency. Not realistic now. The natural route to a libc-free toolchain is a self-hosted `oskac` written in Oska and compiled by its own native backend, which is already libc-free on Linux.

## Open questions

- How much slower `oskac` is with musl's mallocng than with glibc malloc. None of the sources read measures it, so step 3 has to.
- Whether the aarch64 musl binary is static-pie or non-PIE static. The target spec summary did not show `static_position_independent_executables`.
- Whether musl's `realpath`/`getcwd` match the glibc behaviour that `std.rt` copies in every edge case.

## 2026-11-21: Dropping the glibc build at the same speed

**Question:** What would it take to drop the glibc Linux build of `oskac` and ship only a build with no glibc dependency (today the static musl build from `<arch>-unknown-linux-musl`), while it runs at similar or better speed than the glibc build on x86_64 and aarch64?

### Short answer

The gap is in musl's allocator and in musl's x86_64 `memcpy`. No newer musl release changes either of them. So "musl only, at the same speed" needs work in Oska, in three layers. First, allocate and copy less (fixes 1 to 6, tickets #500 to #505). This helps both builds. Second, a global allocator for the musl build, written in `oska-sys` (#507). This needs new `unsafe` code and an update to ADR 0009. Third, ADR 0022 must be replaced by a new ADR that drops the glibc build. Replacing musl's `memcpy` is hard and probably not needed once the copies are gone. A Rust program with no C library at all is not a real option: the only such target is Tier 3, has no `std` and no `alloc`, and ships no prebuilt library.

### 1. Which musl the pinned Rust bundles, and what newer musl changes

- Rust 1.100.0 builds its musl targets from musl 1.2.5. Its CI script sets `MUSL=musl-1.2.5` ([rust 1.100.0, `src/ci/docker/scripts/musl.sh`](https://github.com/rust-lang/rust/blob/1.100.0/src/ci/docker/scripts/musl.sh)). The platform-support page agrees: "64-bit Linux with musl 1.2.5" and "ARM64 Linux with musl 1.2.5" ([Platform Support](https://doc.rust-lang.org/rustc/platform-support.html)).
- The same script patches 1.2.5 for CVE-2025-26519 and three 2026 CVEs ([musl.sh](https://github.com/rust-lang/rust/blob/1.100.0/src/ci/docker/scripts/musl.sh)). The three 2026 patches change only `src/locale/iconv.c`, `src/stdlib/qsort.c` and `src/regex/regcomp.c` ([the three `musl-cve-2026-*.diff` files beside it](https://github.com/rust-lang/rust/tree/1.100.0/src/ci/docker/scripts)). None touches the allocator or `memcpy`.
- musl 1.2.6 is the newest release ([mirror, `VERSION`](https://github.com/kraj/musl/blob/7813e9119eb5fe681b6750b8a033a0490bca0941/VERSION)). Its release notes list no change to malloc, to locking or to `memcpy` ([`WHATSNEW`, 1.2.6 notes](https://github.com/kraj/musl/blob/7813e9119eb5fe681b6750b8a033a0490bca0941/WHATSNEW)).
- The last performance change to mallocng in the release notes is in 1.2.2: "mallocng no longer uses MADV_FREE (high performance cost, little gain)" ([`WHATSNEW`](https://github.com/kraj/musl/blob/7813e9119eb5fe681b6750b8a033a0490bca0941/WHATSNEW)). mallocng itself and the "optimized memcpy and memset for aarch64" came in 1.2.1 ([`WHATSNEW`](https://github.com/kraj/musl/blob/7813e9119eb5fe681b6750b8a033a0490bca0941/WHATSNEW)).
- After 1.2.5, the mirror's history has three mallocng commits: "prevent stray ';' at top-level" (2024), "fix handling of allocations with extreme alignment" and "fix linkage namespace violations in mallocng" (2026) (`git log v1.2.5..master -- src/malloc` on the [mirror](https://github.com/kraj/musl)). The x86_64 `memcpy.s` last changed in 2015, and the aarch64 `memcpy.S` in 2020 ([mirror](https://github.com/kraj/musl)). Inference: these are correctness fixes. A Rust bump to musl 1.2.6 or a later musl `master` would not shrink the gap.

### 2. How mallocng locks, and when it gives memory back

- **Locking.** mallocng's lock functions lock only when `MT` is set, and `MT` is `libc.need_locks` ([`mallocng/glue.h`](https://github.com/kraj/musl/blob/7813e9119eb5fe681b6750b8a033a0490bca0941/src/malloc/mallocng/glue.h)). `__lock` returns at once when `need_locks` is 0; otherwise it does an atomic compare-and-swap ([`src/thread/__lock.c`](https://github.com/kraj/musl/blob/7813e9119eb5fe681b6750b8a033a0490bca0941/src/thread/__lock.c)).
- `pthread_create` sets `need_locks = 1` when the process goes from one thread to two. When the last other thread exits, it sets `need_locks = -1`, and the next `__lock` then sets it back to 0 ([`src/thread/pthread_create.c`](https://github.com/kraj/musl/blob/7813e9119eb5fe681b6750b8a033a0490bca0941/src/thread/pthread_create.c); [`__lock.c`](https://github.com/kraj/musl/blob/7813e9119eb5fe681b6750b8a033a0490bca0941/src/thread/__lock.c)). This confirms the earlier note's inference. Inference: `oska-run` keeps its interpreter thread alive for the whole run while the main thread waits in `join` ([crates/oska-run/src/lib.rs](../../crates/oska-run/src/lib.rs)), so every allocation in the interpreter takes the lock.
- `malloc` takes the lock on every call that is not a large `mmap` ([`mallocng/malloc.c`](https://github.com/kraj/musl/blob/7813e9119eb5fe681b6750b8a033a0490bca0941/src/malloc/mallocng/malloc.c)). `free` skips the lock when the slot is neither the first nor the last free slot of its group. Then it only sets a bit, with an atomic compare-and-swap when `MT` is set ([`mallocng/free.c`](https://github.com/kraj/musl/blob/7813e9119eb5fe681b6750b8a033a0490bca0941/src/malloc/mallocng/free.c)).
- **Giving memory back.** When the last used slot of a group is freed, `okay_to_free` decides whether to free the whole group. It frees it if the group lives inside another group's slot, if another non-full group exists in that size class, or if the size class is "not bouncing" ([`free.c`](https://github.com/kraj/musl/blob/7813e9119eb5fe681b6750b8a033a0490bca0941/src/malloc/mallocng/free.c)). A freed group that has its own mapping goes to `munmap` after the lock is released ([`free.c`](https://github.com/kraj/musl/blob/7813e9119eb5fe681b6750b8a033a0490bca0941/src/malloc/mallocng/free.c)).
- A size class "bounces" when a new group is mapped fewer than 10 sequence steps after one was unmapped. Only after 100 such bounces does musl keep the last group ([`mallocng/meta.h`](https://github.com/kraj/musl/blob/7813e9119eb5fe681b6750b8a033a0490bca0941/src/malloc/mallocng/meta.h)). Bounces are tracked only for size classes 7 to 38 (`sc-7U < 32`) ([`meta.h`](https://github.com/kraj/musl/blob/7813e9119eb5fe681b6750b8a033a0490bca0941/src/malloc/mallocng/meta.h)). Inference: the smallest classes never count as bouncing, so their empty groups are always freed. This fits the 338,144 `mmap` calls the earlier note saw for a loop of 16-byte allocations.
- Groups bigger than half a page are mapped with `mmap`, and requests of `MMAP_THRESHOLD` (131,052 bytes) or more get their own mapping ([`malloc.c`](https://github.com/kraj/musl/blob/7813e9119eb5fe681b6750b8a033a0490bca0941/src/malloc/mallocng/malloc.c); [`meta.h`](https://github.com/kraj/musl/blob/7813e9119eb5fe681b6750b8a033a0490bca0941/src/malloc/mallocng/meta.h)). `madvise(MADV_FREE)` on freed whole pages is compiled out: `USE_MADV_FREE` is 0 ([`glue.h`](https://github.com/kraj/musl/blob/7813e9119eb5fe681b6750b8a033a0490bca0941/src/malloc/mallocng/glue.h); [`free.c`](https://github.com/kraj/musl/blob/7813e9119eb5fe681b6750b8a033a0490bca0941/src/malloc/mallocng/free.c)).
- **Tunables.** At build time, `configure --with-malloc=...` chooses the malloc directory; the default is `mallocng` ([`configure`](https://github.com/kraj/musl/blob/7813e9119eb5fe681b6750b8a033a0490bca0941/configure)). The other constants (`USE_MADV_FREE`, `MMAP_THRESHOLD`, the bounce limits) are `#define`s in the source ([`glue.h`](https://github.com/kraj/musl/blob/7813e9119eb5fe681b6750b8a033a0490bca0941/src/malloc/mallocng/glue.h); [`meta.h`](https://github.com/kraj/musl/blob/7813e9119eb5fe681b6750b8a033a0490bca0941/src/malloc/mallocng/meta.h)). The mallocng files read here contain no environment variable and no `mallopt`. Inference: there is no run-time tunable. Any build-time change means building musl ourselves, not using Rust's `rust-std`, which is far outside this project's toolchain rules.

### 3. Replacing the allocator, or `memcpy`, from Rust

- **The allocator contract.** `#[global_allocator]` may only be applied to a static whose type implements `GlobalAlloc`, and "may only be used once in the crate graph" ([Reference, Runtime](https://doc.rust-lang.org/reference/runtime.html)). `GlobalAlloc` is an `unsafe` trait. The allocator must not touch memory that is currently allocated, and it must not unwind ([`GlobalAlloc`](https://doc.rust-lang.org/std/alloc/trait.GlobalAlloc.html)). `alloc` gets a non-zero size and returns null for exhaustion or an unsupported layout. `dealloc` and `realloc` get the same layout that was used to allocate ([`GlobalAlloc`](https://doc.rust-lang.org/std/alloc/trait.GlobalAlloc.html)). The compiler may remove or merge allocations, so a program must not rely on allocations happening ([`GlobalAlloc`](https://doc.rust-lang.org/std/alloc/trait.GlobalAlloc.html)).
- Inference: a size-class allocator or a cache in front of `std::alloc::System` fits this contract. The `unsafe impl` must sit in `oska-sys`, which ADR 0009 allows, but ADR 0009 describes `oska-sys` as a filesystem-confinement crate ([ADR 0009](../adr/0009-oska-sys-is-the-only-crate-with-unsafe.md)). So the ADR needs an amendment, and the code a security review. It needs no external crate, so "no external crates" holds ([scripts/check.sh](../../scripts/check.sh)). The `#[global_allocator]` static can be limited with `#[cfg(all(target_os = "linux", target_env = "musl"))]`, so macOS and Windows keep their system allocator.
- **compiler-builtins `mem`.** compiler-builtins has a `mem` feature that exports `memcpy` and friends as unmangled symbols ([compiler-builtins `Cargo.toml` at 1.100.0](https://github.com/rust-lang/rust/blob/1.100.0/library/compiler-builtins/compiler-builtins/Cargo.toml)). These symbols get weak linkage on Linux ([`src/macros.rs`](https://github.com/rust-lang/rust/blob/1.100.0/library/compiler-builtins/compiler-builtins/src/macros.rs)). `std` reaches it only through its own `compiler-builtins-mem` feature ([`library/std/Cargo.toml`](https://github.com/rust-lang/rust/blob/1.100.0/library/std/Cargo.toml)). Inference: turning on a feature of `std` needs a rebuilt `std` (`-Zbuild-std`, nightly), which the pinned stable toolchain does not allow. A weak symbol would also lose to musl's strong `memcpy`.
- It would not help anyway. On x86_64 its `memcpy` uses `rep movsb` if `ermsb` is enabled at compile time, else `rep movsb` / `rep movsq` / `rep movsb`, the same shape as musl's ([`src/mem/x86_64.rs`](https://github.com/rust-lang/rust/blob/1.100.0/library/compiler-builtins/compiler-builtins/src/mem/x86_64.rs); [musl `src/string/x86_64/memcpy.s`](https://github.com/kraj/musl/blob/7813e9119eb5fe681b6750b8a033a0490bca0941/src/string/x86_64/memcpy.s)).
- **Our own `memcpy` in `oska-sys`.** musl's x86_64 `memcpy.s` defines both `memcpy` and the hidden `__memcpy_fwd`, and its `memmove.s` jumps to `__memcpy_fwd` ([`memcpy.s`](https://github.com/kraj/musl/blob/7813e9119eb5fe681b6750b8a033a0490bca0941/src/string/x86_64/memcpy.s); [`memmove.s`](https://github.com/kraj/musl/blob/7813e9119eb5fe681b6750b8a033a0490bca0941/src/string/x86_64/memmove.s)). Inference: any use of `memmove` pulls musl's `memcpy` object out of `libc.a`, so a strong `#[no_mangle] memcpy` in `oska-sys` would most likely clash with it at link time. Even if it links, it is hand-written `unsafe` code (inline assembly or SIMD), and the compiler can turn a byte loop back into a call to `memcpy`. It is possible only in `oska-sys`, and it is fragile. Prefer fewer copies.

### 4. aarch64

- glibc's aarch64 `memcpy` is an ifunc. It picks `__memcpy_mops` when the CPU has MOPS, an SVE or A64FX version on SVE CPUs, an Oryon version on Oryon, and `__memcpy_generic` otherwise ([glibc `sysdeps/aarch64/multiarch/memcpy.c`](https://github.com/bminor/glibc/blob/master/sysdeps/aarch64/multiarch/memcpy.c)). `__memcpy_generic` is `sysdeps/aarch64/memcpy.S` ([`memcpy_generic.S`](https://github.com/bminor/glibc/blob/master/sysdeps/aarch64/multiarch/memcpy_generic.S)).
- That generic routine and musl's both split copies into "small copies of up to 32 bytes, medium copies of up to 128 bytes, and large copies", with branchless unaligned loads ([glibc `sysdeps/aarch64/memcpy.S`](https://github.com/bminor/glibc/blob/master/sysdeps/aarch64/memcpy.S); [musl `src/string/aarch64/memcpy.S`](https://github.com/kraj/musl/blob/7813e9119eb5fe681b6750b8a033a0490bca0941/src/string/aarch64/memcpy.S)). musl's copy is "Copyright (c) 2012-2020, Arm Limited" and uses pairs of 64-bit registers (`ldp x`) ([musl `memcpy.S`](https://github.com/kraj/musl/blob/7813e9119eb5fe681b6750b8a033a0490bca0941/src/string/aarch64/memcpy.S)). glibc's says "Advanced SIMD" and uses 128-bit `q` registers ([glibc `memcpy.S`](https://github.com/bminor/glibc/blob/master/sysdeps/aarch64/memcpy.S)).
- Inference: on aarch64 the two `memcpy`s are close for short copies, so cause 3 of the performance note mostly goes away there. glibc may still win on long copies, and on CPUs where it picks MOPS or SVE. The allocator causes (lock and `munmap` churn) are in musl's portable C, so they apply on aarch64 as on x86_64. The aarch64 numbers are still unmeasured (#506).

### 5. No C library at all

- The only `linux-none` target in the platform list is `x86_64-unknown-linux-none`, "64-bit Linux with no libc", with `*` in the `std` column ([Platform Support](https://doc.rust-lang.org/rustc/platform-support.html)). `*` means "the target only supports `no_std` development" ([Platform Support](https://doc.rust-lang.org/rustc/platform-support.html)).
- Its page says it is Tier 3 and "has no support for host tools, std, or alloc". Rust ships no prebuilt artifacts for it; you build Rust with it or use `build-std` ([x86_64-unknown-linux-none](https://doc.rust-lang.org/rustc/platform-support/x86_64-unknown-linux-none.html)). The platform list shows no aarch64 `linux-none` target ([Platform Support](https://doc.rust-lang.org/rustc/platform-support.html)).
- Inference: this route means everything §6 of the 2026-11-19 note lists (no `std`, own entry point, panic handler, allocator and system-call layer, all `unsafe` in `oska-sys`), plus a nightly toolchain, plus no aarch64 target. It is worse than when that note rejected it. The fast path to "no C library and fast" is still a self-hosted `oskac` built by Oska's own backend.

### 6. How much Oska-side fixes could close (Inference)

All of this is Inference from the 2026-11-20 counts ([2026-11-musl-oskac-performance.md](2026-11-musl-oskac-performance.md)). It assumes each cause scales with the number of calls it sees.

- **Interpreter.** Fixes 1, 2 and 6 remove up to 46 of 52 million allocations (88%) and about 31 of 39 million `memcpy` calls (79%). The gap was 3,629 samples: allocator 1,580, kernel 732, `memcpy` 1,018, rest 592, `memcmp` −293. If the allocator and kernel parts fall by about 85% and `memcpy` by 79%, the gap left is about 350 + 215 = 565 samples, plus part of the 592 in cache and TLB cost.
- Fix 3 removes about 25% of the interpreter's instructions in both builds, and most of the `memcmp` calls where musl was faster. So the glibc time also falls, from 5,554 to perhaps 3,300 samples, and musl's `memcmp` advantage mostly goes away.
- Result: the absolute gap shrinks by about 70 to 80%. But the musl build would still be roughly 15 to 35% slower than the new, faster glibc build. Fixes 1 to 6 alone probably do not reach "≤10% slower" in the interpreter.
- **Compile.** Fixes 4 and 5 remove up to 544,000 of 689,000 allocations (79%). The gap was 762 of 1,191 samples, nearly all allocator, kernel and `memcpy`. The rough estimate leaves the musl compile 10 to 20% slower.
- An allocator in `oska-sys` removes the lock and the `mmap`/`munmap` churn (causes 1 and 2), and probably much of the cache and TLB cost of fresh pages (cause 4). After fixes 1 to 6, the x86_64 `memcpy` residue is about 215 samples, roughly 6% of the improved glibc time. So fixes 1 to 6 plus the allocator should reach ≤10% on x86_64, and more easily on aarch64. Only the bench can prove this.

### Open questions

- The aarch64 numbers (#506). The plan's estimates are x86_64 only.
- Whether the residual gap after fixes 1 to 6 is really 15 to 35%. The estimate assumes each cause scales with call counts.
- Whether a thread-local free list is safe inside a `GlobalAlloc` (no allocation and no unwinding during TLS set-up). The `GlobalAlloc` page does not say.
- Whether a strong `memcpy` in `oska-sys` clashes with musl's `memcpy.o` at link time, as §3 infers. It was not tried.
- When Rust moves to musl 1.2.6 or later. §1 shows this does not change speed.
- musl's own sites and sourceware were unreachable; the GitHub mirrors stand in for them.
- No local measurement: the musl targets could not be installed in this session.
