# How can Oska best defend/harden the oskac binary and programs it compiles against decompilation and reverse engineering, and what's realistic vs. security theater?

Date of access: 2026-11-23

## 1. Framing: two very different problems

- **`oskac` is open source** (Apache-2.0, public GitHub repo). Obfuscating or "encrypting" the compiler/runtime binary itself buys almost nothing against a motivated adversary, since the source is already public. [Source: `aparsons/oska` repository license and visibility.]
- The real, legitimate goal for `oskac`'s own binary is **supply-chain integrity** (don't let a tampered binary be distributed) and **standard exploit-mitigation** (don't let a malicious `.osk` input corrupt the compiler process) — not secrecy.
- For **programs compiled by oskac**, "defend against decompilation" is a meaningful ask (protecting an ISV's logic from casual copying). Here the correct mental model, grounded in the academic impossibility result for general-purpose obfuscation (Barak et al., "On the (Im)possibility of Obfuscating Programs", CRYPTO 2001 / J. ACM 2012) is: you can raise the cost of static analysis, but you cannot hide a secret from an adversary who fully controls the execution hardware. Inference: any secret that must be *used* by code running on attacker-controlled hardware is eventually extractable; obfuscation buys analyst time, not confidentiality guarantees.

Source: Barak, Goldreich, Impagliazzo, Rudich, Sahai, Vadhan, Yang, "On the (Im)possibility of Obfuscating Programs," J. ACM 59(2), 2012. https://dl.acm.org/doi/10.1145/2160158.2160159

## 2. Repo-specific facts that shape the answer

- `oskac` emits ELF/Mach-O/PE directly — there is no external linker or assembler in the pipeline (per ADR 0011 / ADR 0014, and `crates/oska-native/src/{elf,macho,pe}.rs`). This means the compiler fully controls what goes into object/section/symbol tables, with no separate "strip the linker's output" step required: nothing needs to be emitted in the first place.
- The release pipeline (`docs/agents/release.md`, `SECURITY.md`) already signs `SHA256SUMS` with `ssh-keygen` and publishes a signed, expiring release index, double-verified by both a shell script and a second, independent verifier written in Oska itself. This is the correct tool for "protect the oskac binary from tampering," and goes further than most projects (an independent verifier in a second implementation).
- The musl release builds already avoid `PT_INTERP`/`DT_NEEDED` (static linking), which also removes import-table information that is often the first thing a reverse engineer opens in a decompiler.

Source: `docs/agents/release.md`, `SECURITY.md`, `crates/oska-native/src/elf.rs`, `macho.rs`, `pe.rs` (repository state as of 2026-11-23). Inference: these are read directly from the repository, not an external primary source, and should be re-verified against current file contents before relying on them, since this note doesn't carry a line-exact citation for each file.

## 3. What's achievable (raises real cost) vs. security theater

**Achievable, standard, defensible:**

- **Symbol/debug-info stripping.** Rust's release profile supports `strip = true` (or `strip = "symbols"` / `"debuginfo"`) to omit symbols and debug info from the final binary. Source: The Cargo Book, "Profiles," `strip` field — https://doc.rust-lang.org/cargo/reference/profiles.html#strip
- **Panic strategy and codegen-units** affect what ends up embedded for unwinding; `panic = "abort"` removes unwind tables. Source: The Cargo Book, "Profiles," `panic` field — https://doc.rust-lang.org/cargo/reference/profiles.html#panic
- **PIE (position-independent executables), stack protector, RELRO/`-z now` (full RELRO), NX/W^X, and control-flow integrity landing pads** (`BTI` on AArch64 via PAC/BTI extensions, Intel CET `ENDBR64` on x86_64) are standard, well-documented mitigations. Since `oska-native` generates every instruction and section itself, these become backend emission policy rather than a hope that an external linker applied them.
  - AArch64 PAC/BTI: Arm, "Armv8-A Architecture Reference Manual," Pointer Authentication and Branch Target Identification sections. https://developer.arm.com/documentation/ddi0487/latest
  - x86_64 CET: Intel, "Control-flow Enforcement Technology Specification." https://www.intel.com/content/www/us/en/developer/articles/technical/technical-look-at-intel-cet.html
  - RELRO/NX: Linux kernel / `man-pages`, `execve(2)` and ELF hardening discussions; also documented in the OWASP "Buffer Overflow" and binary-hardening cheat sheets. https://cheatsheetseries.owasp.org/
- **Code signing** on macOS (`codesign`, Gatekeeper, notarization) and Windows (Authenticode) is the standard, primary-source-documented way to assure users a binary is unmodified and from a known publisher — this is an integrity control, not an obfuscation control.
  - Apple: "Notarizing macOS software before distribution." https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution
  - Microsoft: "Introduction to Code Signing." https://learn.microsoft.com/en-us/windows-hardware/drivers/install/introduction-to-code-signing
- **Static linking / no `PT_INTERP`** removes dynamic-import-table leakage (named libc/Win32 imports are a decompiler's first foothold, since tools like disassemblers auto-recognize library calls by name and infer behavior from them). This is a direct, well-understood trade-off: static reduces both supply-chain surface and import-name leakage, at the cost of needing OS services some other way.
- **Control-flow obfuscation and string/constant encryption** implemented as an optional codegen pass (flattening, opaque predicates, junk instructions, basic-block reordering, encrypted constants decrypted on first use) can meaningfully raise decompiler/analyst time when done with full IR/semantic knowledge (which `oska-native`'s own-codegen architecture allows, unlike a generic post-link binary rewriter). Inference: no primary source quantifies "how much" time this buys; the qualitative claim that doing these transforms with semantic knowledge is stronger than post-hoc binary rewriting is this agent's own conclusion, not sourced.

**Security theater (commonly sold, usually ineffective against a real adversary, often net-negative):**

- **Packers / self-decrypting executables.** The decrypted, runnable image must exist in memory at some point, so any debugger or memory dumper recovers it. This category (UPX through VMProtect/Themida) has an extensive public unpacking literature.
- **Anti-debugging tricks** (`ptrace` detection, timing checks, debugger-presence checks) are typically a one-line patch to defeat once found, and they actively break legitimate infrastructure: crash reporters, sandboxes, and container runtimes. Given Oska targets containerized/CI environments (per the musl/ghcr image pipeline), these are especially likely to misfire on legitimate use rather than attackers.
- **Encrypting the whole binary and decrypting at startup** conflicts directly with code signing: Gatekeeper/notarization on macOS and SmartScreen/Authenticode checks on Windows expect a static, non-self-modifying executable, and self-modifying or writable-executable pages are flagged by both platforms' security models. Source: Apple notarization docs (above); Microsoft SmartScreen documentation — https://learn.microsoft.com/en-us/windows/security/operating-system-security/virus-and-threat-protection/microsoft-defender-smartscreen/
- **VM-based bytecode obfuscation** for a compiled, native-codegen, performance-oriented language works against the project's stated architecture (ADR 0011/0014's own native-codegen design), and VM-dispatch-loop deobfuscation (e.g., via taint tracking) is an established, teachable technique in the reverse-engineering literature.
- **Obfuscating `oskac`'s own binary** is close to pure theater given the source is public on GitHub — effort here has near-zero payoff relative to effort spent on the areas above.

## 4. Bottom line

- Supply-chain integrity (signing, independent verification) is already the correct answer for "protect the oskac binary," and the project's existing signed-release pipeline already exceeds common industry practice.
- Standard exploit mitigations (stripping, PIE, stack protector, RELRO, NX, CFI landing pads, code signing) are inexpensive, well-documented, and should be default build hygiene for both `oskac` and the programs it emits; because `oska-native` owns code generation end-to-end, these become emission policy rather than something hoped-for from an external linker.
- Control-flow obfuscation and string/constant encryption for **compiled programs** (not `oskac` itself) is the one area with genuine, buildable RE-resistance, but it should be presented to users as "raises analyst cost," never as protecting a secret, since nothing running on attacker-controlled hardware can guarantee the latter (Barak et al. impossibility result, §1).
- Packing, anti-debugging, and whole-binary encryption should be explicitly rejected: they are the theater category, and they actively conflict with code-signing and reproducible-build goals the project already has in place.

## 2026-11-23: Further hardening and obfuscation enhancements

Date of access: 2026-11-23

Scope: given the mitigations already decided (stack canary, "strong" heuristic; ARM BTI / Intel ENDBR64 CFI landing pads under opt-in `--harden`; string/constant encryption, control-flow flattening, opaque predicates, junk instructions, basic-block reordering under opt-in `--obfuscate`), this section surveys further standard, mainstream, compiler- or OS-level techniques a native-codegen compiler with no external linker could add as additional opt-in flags, and marks each as additive or redundant with what's already decided.

### Hardening additions

- **Windows Control Flow Guard (CFG).** CFG is Microsoft's forward-edge CFI: the compiler "adds lightweight security checks to the compiled code" and "identifies the set of functions in the application that are valid targets for indirect calls," while the OS "efficiently maintains state that identifies valid indirect call targets" and terminates the process if a check fails. It is enabled per-module via `/guard:cf` passed to both compiler and linker, and is verifiable in a PE's load config directory (`dumpbin /headers /loadconfig`, looking for "Guard CF Instrumented" / "FID table present"). Source: Microsoft Learn, "Control Flow Guard for platform security." https://learn.microsoft.com/en-us/windows/win32/secbp/control-flow-guard — **Additive.** BTI/ENDBR64 are the AArch64/x86_64 *landing-pad* side of forward-edge CFI (marking valid targets in the instruction stream); CFG is Windows's own PE-metadata-driven mechanism using an OS-maintained bitmap and a `LoadConfig` directory entry, which is orthogonal and PE-specific — oska-native, as the PE emitter, would need to populate the `GuardCFFunctionTable`/`GuardFlags` fields itself since there's no external linker to do it. Not redundant with BTI/ENDBR64, which Windows does not consume for CFG purposes.

- **ARM Pointer Authentication (PAC).** The Armv8.3-A PAC extension lets code sign a pointer (e.g., a return address) with a cryptographic MAC computed from the pointer value, a context value, and a key held in system registers, storing the MAC in unused high bits of the pointer; `AUT*` instructions on use detect tampering. Source: Arm, "Arm Architecture Reference Manual for A-profile architecture," Pointer Authentication chapter. https://developer.arm.com/documentation/ddi0487/latest — **Additive, not redundant.** BTI (already decided) only validates that an indirect branch lands on a marked instruction (forward-edge); it says nothing about whether a *return address* was tampered with in memory (backward-edge). PAC return-address signing (`PACIASP`/`AUTIASP` prologue/epilogue pairs, the standard `-mbranch-protection=pac-ret` style scheme) is the AArch64 analogue of a stack canary that travels with the return address itself rather than sitting beside it on the stack, and composes with BTI (`pac-ret+bti`) rather than overlapping it.

- **ARM Guarded Control Stack (GCS) / Intel CET shadow stack.** These are the two architectures' answers to backward-edge CFI via a hardware-enforced second stack. On AArch64, GCS (Linux kernel feature, backed by the Arm architecture's `FEAT_GCS`-family extension) maintains a separate stack that stores only call return addresses; on `CALL` the PC is pushed to it, and on `RET` the return address in the link register is checked against the top-of-GCS entry, with the pointer held in `GCSPR_EL0`, writable only via dedicated GCS instructions. Source: Linux kernel documentation, "Guarded Control Stack support for AArch64 Linux." https://docs.kernel.org/arch/arm64/gcs.html — On x86_64, Intel CET's shadow stack stores a redundant copy of the return address pushed by `CALL`; on `RET` the two copies are compared and a control-protection fault is raised on mismatch, with the shadow-stack pointer (SSP) tracked per-thread by the kernel. Source: Linux kernel documentation, "Control-flow Enforcement Technology (CET) Shadow Stack." https://kernel.org/doc/html/next/x86/shstk.html — **Additive, not redundant.** The doc explicitly distinguishes shadow stack (protects `RET` paths) from IBT/`ENDBR64` (checks indirect `CALL`/`JMP` targets) — "not all CPUs support both," and Oska's existing decision only covers the IBT/BTI (ENDBR64/BTI) half of CET/the Arm CFI extensions. Shadow stack / GCS is the complementary backward-edge half and is a genuinely new mitigation class, not an alternative framing of what's already decided. It requires OS enlightenment (both are opt-in per-thread via `prctl()`/platform APIs) and ELF/Mach-O note markings so the loader enables it, which oska-native would need to emit itself.

- **ELF RELRO (`-z relro` / `-z now`).** RELRO hardens the GOT against overwrite attacks: with lazy binding the GOT is writable and sits at a predictable address, so a write bug can redirect a later PLT call; "partial RELRO" (`-z relro`) makes the non-PLT `.got` read-only after startup while `.got.plt` stays writable, and "full RELRO" (`-z relro,-z now`) forces eager binding and makes the entire GOT read-only, which is "the only level that mitigates GOT overwrites." Source: Red Hat, "Hardening ELF binaries using Relocation Read-Only (RELRO)." https://www.redhat.com/en/blog/hardening-elf-binaries-using-relocation-read-only-relro — **Additive, but narrower scope for Oska than usual.** This is normally a linker-applied ELF program-header/segment-permission policy (`PT_GNU_RELRO`); since oska-native emits ELF directly with no external linker, "applying RELRO" reduces to oska-native choosing to mark the relevant data segment read-only after relocation and populating `PT_GNU_RELRO` itself. Because a statically linked, no-`PT_INTERP"` binary (already Oska's musl release posture, §2 above) has no GOT/PLT to attack from an external shared-library binding perspective, RELRO's core GOT-overwrite protection is most relevant to any dynamically linked build mode Oska supports (e.g., linking against libc dynamically) rather than the static release builds; it is additive, not redundant, but its payoff is conditional on which linking mode is in use.

- **SafeStack-style stack splitting.** SafeStack splits the stack into a "safe stack" (return addresses, register spills, and provably in-bounds locals) and an "unsafe stack" (large arrays, address-taken locals), so that an overflow of an unsafe-stack buffer cannot reach the safe stack's return addresses and saved registers; protection against the precise stack-overflow case is exact, while protection against arbitrary-write bugs is probabilistic (relies on hiding/ASLR-randomizing the unsafe stack's address), and the project notes "SafeStack alone is not sufficient to protect against control-flow hijack attacks" without pairing it with CPI or forward-edge CFI; measured overhead is under 0.1%. Source: LLVM/Clang documentation, "SafeStack." https://clang.llvm.org/docs/SafeStack.html; design basis in Kuznetsov et al., "Code-Pointer Integrity," OSDI 2014. — **Additive, not redundant.** A stack canary (already decided) only *detects* a contiguous linear overflow that reaches the canary before further corrupting the return address — it is a tripwire placed in the same stack frame as the data that can corrupt it, and gives no protection against non-adjacent or partial/targeted overflows. SafeStack instead physically separates data classes so that most overflow-prone objects (arrays, address-taken locals) can never reach the return address/saved-registers region at all, regardless of overflow pattern. The two mitigations compose (canary as last-resort detection on the frame that remains, stack splitting as the primary containment); a compiler owning its own codegen is well placed to implement this since it requires per-variable escape/address-taken analysis at IR level — something a generic post-hoc binary tool cannot do.

- **Build-ID / metadata stripping beyond symbols.** Beyond `strip = true`/debug-info removal (already covered in §3 above), ELF binaries carry a `.note.gnu.build-id` section — a content hash used by package managers, crash-dump/symbol servers, and `debuginfod` to correlate a binary with its matching debug info and build provenance — which several toolchains (e.g., LLD) emit by default. Source: Fedora Project Wiki, "Releases/FeatureBuildId." https://fedoraproject.org/wiki/Releases/FeatureBuildId — **Additive and directly actionable for oska-native.** Since oska-native owns section emission, it can choose whether to emit `.note.gnu.build-id` (and PE/Mach-O equivalents: PE debug directory CodeView/PDB GUID-age record, Mach-O `LC_UUID`) at all, rather than relying on a post-link `strip`/`objcopy --remove-section` pass to take it back out after an external linker added it. This closes a provenance/fingerprinting leak (a build-ID is a stable identifier an analyst can use to look up public symbol servers or correlate releases) that plain symbol stripping does not address, since symbol stripping and build-ID emission are controlled independently in most toolchains.

### Obfuscation additions

- **Indirect-call / jump-table-based dispatch.** Rather than (or in addition to) flattening control flow into a single dispatcher loop (already decided), a call site can be rewritten to compute its target from a table of function/block pointers and perform an indirect branch, which defeats naive static disassemblers that rely on recognizing direct-call/direct-jump instructions and following them to build a control-flow graph; this is a specific, well-documented static-disassembly-resistance technique distinct from flattening. Source: Linn and Debray, "Obfuscation of Executable Code to Improve Resistance to Static Disassembly," ACM CCS 2003. https://ulp.cs.arizona.edu/~debray/Publications/disasm-resist.pdf — **Additive, not redundant.** Control-flow flattening (already decided) restructures the *function body's* control flow into a dispatcher driven by a state variable; indirect-call/jump-table dispatch instead targets *call-site* and *branch-target* resolution so a disassembler cannot statically enumerate callees/successors even for code that isn't flattened. The two are complementary (flattening can itself be implemented with a jump table as its dispatch mechanism, but jump-table-ization of ordinary calls is a separable transform applicable everywhere flattening isn't used).

- **Identifier renaming and (data/class) layout randomization per build.** The founding taxonomy of obfuscating transformations treats scrambling identifier names as a free, low-potency-but-nontrivial transform (identifiers "carry a great deal of pragmatic information" that aids a reverse engineer), and separately randomizes "the placement of any item in the source application" — including the order of methods, instance variables, and formal parameters, with array indices remappable through an opaque encoding function — as an independent transform family. Source: Collberg, Thomborson, and Low, "A Taxonomy of Obfuscating Transformations," University of Auckland TR-148, 1997, §§5.5, 6.4, 7.3. https://researchspace.auckland.ac.nz/bitstream/handle/2292/3491/TR148.pdf — **Partially additive.** Identifier renaming is largely moot for a compiled native binary that already strips symbols (already decided, §3 above) — once symbols are stripped there are no source identifiers left to rename in the output. What is additive and new is per-build *structural* layout randomization: randomizing struct-field order, function/basic-block placement order in the final image, and padding/alignment choices on every build so that two builds of the same source produce different byte-level and address layouts. This is distinct from ASLR (a runtime, OS-level, per-process randomization of a fixed binary) and from basic-block reordering as already decided if that reordering is static per-build-config rather than randomized fresh per build; making it genuinely random per build (not just a single fixed reordering baked into one release) raises the cost of building a single cross-version analysis/diffing toolchain (e.g., for bulk patch diffing or signature-based detection) and is additive to a single deterministic reordering pass.

### Prioritization (inference)

Given that packers, anti-debugging, VM-based bytecode obfuscation, and whole-binary encryption are already rejected (§3 above), the following are, in this agent's judgment, the most worth proposing as new specs, in priority order:

1. **ARM PAC return-address signing + GCS, and Intel CET shadow stack** (treat as one proposal: "complete CFI," pairing with the already-decided BTI/ENDBR64 landing pads). Inference: this is the highest-value addition because it closes the specific, well-known gap that landing-pad-only CFI leaves open — tampering with a return address already in memory — using mechanisms that are hardware-enforced (not just compiler-inserted checks a sufficiently capable attacker could reason past) and that both platforms' own kernels already support via simple opt-in (`prctl()` / shadow-stack-enabled thread attributes), fitting the project's existing `--harden` flag cleanly as "the other half" of what it already does.
2. **SafeStack-style stack splitting.** Inference: second priority because it meaningfully strengthens the already-decided stack canary (detects nothing between overflow and canary-check; SafeStack prevents the overflow from reaching the sensitive region at all) at near-zero measured overhead (<0.1%, per the Clang docs above), and because oska-native's full ownership of IR-level escape analysis makes correctly classifying "safe" vs. "unsafe" locals easier to implement well than it is for LLVM's own post-hoc pass bolted onto a generic backend.
3. **Indirect-call/jump-table dispatch as a distinct `--obfuscate` sub-transform.** Inference: third priority because it's a small, well-isolated addition to work already planned (the project is already building a codegen pass infrastructure for flattening/opaque predicates/junk instructions under `--obfuscate`), it's well-documented in the academic literature as effective against the specific tool class (static disassemblers/decompilers) the obfuscation flag is meant to defeat, and it doesn't require any new OS or hardware support (unlike priority 1) or new per-variable analysis (unlike priority 2) — it is implementable with the same call-graph information the compiler already has.

Windows CFG, RELRO, and build-ID stripping are also additive but are lower-priority: CFG only helps the (currently less central, per existing release-pipeline evidence favoring musl/static Linux builds) Windows PE target; RELRO's payoff is conditional on supporting a dynamically linked build mode Oska may not emphasize; and build-ID stripping, while easy, closes a narrower, lower-severity leak (provenance fingerprinting) than the CFI/stack mitigations above.
