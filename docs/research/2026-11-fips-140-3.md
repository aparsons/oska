# What does FIPS 140-3 require, how can a project honestly evidence its FIPS 140-3 position in a compliance report on GitHub Pages, and how could Oska offer a "FIPS mode"?

Accessed: 2026-11-21

## Summary and recommendation

- FIPS 140-3 validates a **cryptographic module**, not a language or a compiler. Only a module that an accredited lab tested and CMVP certified is "validated". The CMVP FAQ says "the correct term is validated". To that FAQ, "compliant" means only that the vendor believes the product meets the standard ([CMVP FAQ](https://csrc.nist.gov/Projects/cryptographic-module-validation-program/faqs)).
- Oska has no CMVP or CAVP certificate today. In the repo, the only crypto code is two Rust SHA-256 copies, one for the build cache (`crates/oskac/src/sha256.rs`) and one for macOS code signatures (`crates/oska-native/src/sha256.rs`). The Oska `std.sha2` is still planned (#231, as named in `crates/oskac/src/sha256.rs`). `Random` is SplitMix64 and "is not cryptographically secure" (`crates/oska-run/src/prng.rs`).
- Inference: The honest position today is "not FIPS 140-3 validated; no module in process". Publish it as a short self-assessment under ADR 0017, with determination **Does not conform** beside the standard's own measure ("no CMVP certificate"). Add an algorithm inventory that marks each Crypto-milestone algorithm as approved or not approved.
- Inference: The best next step is option (b): an "approved-only" mode for Oska's own crypto, with self-tests and a service indicator. Word it as "uses NIST-approved algorithms, implemented in Oska; not CMVP-validated". Do not call it "FIPS compliant" or "FIPS validated". Keep option (c), real CMVP validation, for when a user needs and funds it. Go's Cryptographic Module is the model to follow. Option (a), delegating to the platform's validated modules, gives real validation soonest, but it conflicts with ADR 0012.

## 1. FIPS 140-3 basics

### What is validated

- FIPS 140-3 is the US standard for the security of cryptographic modules. CMVP runs it jointly for the US and Canada ([NIST FIPS 140-3 standards](https://csrc.nist.gov/projects/cryptographic-module-validation-program/fips-140-3-standards)).
- CMVP is run by NIST and the Canadian Centre for Cyber Security. Modules are tested by Cryptographic and Security Testing Laboratories (CSTLs), "each ... accredited by NVLAP", and CMVP then reviews and validates each submission ([CMVP](https://csrc.nist.gov/projects/cryptographic-module-validation-program)).
- Microsoft says the same in practice: it validates "the cryptographic modules ... not individual Windows services or applications" ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/security/security-foundations/certification/fips-140-validation)).
- Inference: So a language can offer a module, or a way to use one. It can never be "FIPS validated" itself.

### Security levels and the ISO/IEC standards

- FIPS 140-3 does not spell out the requirements itself. It points to ISO/IEC 19790:2012 for the requirements and to ISO/IEC 24759:2017 for the test methods ([NIST FIPS 140-3 standards](https://csrc.nist.gov/projects/cryptographic-module-validation-program/fips-140-3-standards)).
- ISO/IEC 19790 defines four security levels across 11 requirement areas ([NIST FIPS 140-3 standards](https://csrc.nist.gov/projects/cryptographic-module-validation-program/fips-140-3-standards)).
- The required integrity test gets stronger with the level. Level 1 needs "an approved integrity technique". Level 2 needs "an approved digital signature or keyed message authentication code". Levels 3 and 4 need "an approved digital signature" ([FIPS 140-3 IG, IG 1.B](https://csrc.nist.gov/csrc/media/Projects/cryptographic-module-validation-program/documents/fips%20140-3/FIPS%20140-3%20IG.pdf)).
- Software modules are typically Level 1. For example, Apple's corecrypto user and kernel modules are "Software, Level 1" ([Apple macOS certifications](https://support.apple.com/guide/certifications/macos-security-certifications-apc35eb3dc4fa/web)).

### The SP 800-140x series

CMVP changes the ISO/IEC standards through this series ([NIST FIPS 140-3 standards](https://csrc.nist.gov/projects/cryptographic-module-validation-program/fips-140-3-standards)):

- SP 800-140: Derived Test Requirements.
- SP 800-140A: documentation requirements.
- SP 800-140B Rev. 1: Security Policy requirements.
- SP 800-140C Rev. 2: approved security functions.
- SP 800-140D Rev. 2: approved methods to generate and establish sensitive parameters.
- SP 800-140E: approved authentication mechanisms.
- SP 800-140F: approved metrics for non-invasive attack mitigation.

The Implementation Guidance (IG) adds detailed rules. The copy read here says "Last Update" November 20, 2026 ([FIPS 140-3 IG](https://csrc.nist.gov/csrc/media/Projects/cryptographic-module-validation-program/documents/fips%20140-3/FIPS%20140-3%20IG.pdf)).

### CMVP and CAVP (ACVP)

- CAVP tests the algorithms. CMVP validates the module. CAVP covers "Approved (i.e., FIPS-approved and NIST-recommended) cryptographic algorithms", and algorithm validation is a prerequisite for module validation ([CAVP](https://csrc.nist.gov/projects/cryptographic-algorithm-validation-program)).
- The CMVP FAQ agrees: the approved algorithms "must first be validated by the ... CAVP" before the module goes to CMVP ([CMVP FAQ](https://csrc.nist.gov/Projects/cryptographic-module-validation-program/faqs)).
- Testing uses the Automated Cryptographic Validation Test System (ACVTS), which is "entirely black-box". The vendor declares its capabilities, the server sends test cases, and the implementation returns answers ([CAVP](https://csrc.nist.gov/projects/cryptographic-algorithm-validation-program)).
- "A Demo ACVTS server is available at no cost". The Production server, the only route to a certificate, "is only available to NVLAP-accredited testing laboratories" ([CAVP](https://csrc.nist.gov/projects/cryptographic-algorithm-validation-program)).

### Process, time and cost

- Labs "charge a fee for the conformance testing", and the fee varies by lab. NIST also charges its own fees. The FAQ gives no amounts ([CMVP FAQ](https://csrc.nist.gov/Projects/cryptographic-module-validation-program/faqs)).
- A validated module stays on the Active list for 5 years, or 2 years for an Interim Validation ([CMVP](https://csrc.nist.gov/projects/cryptographic-module-validation-program)).
- CMVP says interim validations have "greatly ramped up processing". It gives no waiting times ([CMVP](https://csrc.nist.gov/projects/cryptographic-module-validation-program)).
- Go sets a pace for comparison: Google has a contract with Geomys "to facilitate at least yearly CMVP validations". Go froze v1.0.0 in early 2024, and it became certificate #5247 ([Go FIPS 140-3](https://go.dev/doc/security/fips140)).
- Inference: Plan on a year or more from freezing the code to getting a certificate, plus a lab contract. This is an estimate, not a published figure.

### Modules In Process and Implementation Under Test lists

- The Modules In Process (MIP) list shows modules "submitted to the CMVP but have not yet been validated" ([CMVP FAQ](https://csrc.nist.gov/Projects/cryptographic-module-validation-program/faqs)).
- The Implementation Under Test (IUT) list is "provided as a marketing service for vendors who have a viable contract with an accredited laboratory". Being on it is voluntary. A module moves from IUT to MIP when the lab submits its test report ([CMVP FAQ](https://csrc.nist.gov/Projects/cryptographic-module-validation-program/faqs)).
- Vendors do cite these stages publicly. Apple lists macOS 26 corecrypto modules as "Review" and "Implementation Under Test" ([Apple macOS certifications](https://support.apple.com/guide/certifications/macos-security-certifications-apc35eb3dc4fa/web)). Go has a `GOFIPS140=inprocess` alias for "the latest version in the MIP list" ([Go FIPS 140-3](https://go.dev/doc/security/fips140)).

### FIPS 140-2 sunset

- CMVP stopped taking FIPS 140-2 submissions for new certificates on April 1, 2022 ([FIPS 140-3 Transition Effort](https://csrc.nist.gov/projects/fips-140-3-transition-effort)).
- In September 2026, "All FIPS 140-2 certificates are placed on the Historical List". The page gives both September 21 and September 22, 2026 ([FIPS 140-3 Transition Effort](https://csrc.nist.gov/projects/fips-140-3-transition-effort)).
- FIPS 140-2 modules could be used in new systems through September 21, 2026. After that, agencies may use them only in existing systems ([CMVP](https://csrc.nist.gov/projects/cryptographic-module-validation-program)).
- "Even on the historical list, CMVP supports the purchase and use of these modules for existing systems" ([FIPS 140-3 Transition Effort](https://csrc.nist.gov/projects/fips-140-3-transition-effort)).
- Inference: As of today (2026-11-21), the sunset has passed. Any new Oska claim should name FIPS 140-3 only.

## 2. Approved algorithms and services

### Approved security functions and SSPs

- SP 800-140C Rev. 2 (July 2023) lists the approved security functions. They replace ISO/IEC 19790 Annex C and ISO/IEC 24759 6.15 ([SP 800-140C Rev. 2](https://csrc.nist.gov/pubs/sp/800/140/c/r2/final)).
- SP 800-140D Rev. 2 covers the approved ways to generate and establish sensitive parameters, called SSPs ([NIST FIPS 140-3 standards](https://csrc.nist.gov/projects/cryptographic-module-validation-program/fips-140-3-standards)).
- CAVP tests AES and its modes, DSA, ECDSA, RSA, KBKDF, KAS, HMAC, DRBGs, and SHA-1, SHA-2 and SHA-3, among others ([CAVP](https://csrc.nist.gov/projects/cryptographic-algorithm-validation-program)).

### Oska's planned algorithms (from ADR 0012)

ADR 0012 lists AES-128-GCM, ChaCha20-Poly1305, SHA-256, SHA-384, X25519 with a P-256 fallback, ECDSA P-256 and P-384, and RSA PKCS#1 v1.5 and PSS.

- AES, ECDSA, RSA, SHA-2, HMAC and KAS are in CAVP's list ([CAVP](https://csrc.nist.gov/projects/cryptographic-algorithm-validation-program)).
- Inference: ChaCha20-Poly1305 and X25519 are not among the CAVP-tested algorithms seen, so treat them as **non-approved** in a FIPS mode. In that mode, TLS would use AES-GCM and P-256 ECDH only. This is an open question to confirm against SP 800-140C/D. The pages read here do not name them ([SP 800-140C Rev. 2](https://csrc.nist.gov/pubs/sp/800/140/c/r2/final)).
- Go's TLS in FIPS mode does the same kind of filtering. It "will ignore and not negotiate any ... cipher suite, signature algorithm, or key exchange mechanism that is not FIPS 140-3 approved" ([Go FIPS 140-3](https://go.dev/doc/security/fips140)).

### SP 800-131A transitions

- SP 800-131A Rev. 3 is still an Initial Public Draft from October 21, 2024. It proposes to retire ECB for confidentiality and DSA for signing, to set a retirement schedule for SHA-1 and the 224-bit hashes, to move from 112-bit to 128-bit security strength, and to move to quantum-resistant algorithms ([SP 800-131A Rev. 3 ipd](https://csrc.nist.gov/pubs/sp/800/131/a/r3/ipd)).
- Open question: whether a final Rev. 3, with dates, was published before 2026-11-21. The page read here shows none.
- Inference: Oska's chosen set (SHA-256/384, P-256/P-384, AES-128) fits a 128-bit world. RSA key sizes need a floor in FIPS mode.

### DRBG and entropy (SP 800-90A/B/C, ESV)

- Requirements for an entropy source in a FIPS-approved module are in SP 800-90B and IGs D.J, D.K and D.O. Random bit generators fall under SP 800-90C and IG D.T ([ESV](https://csrc.nist.gov/projects/cryptographic-module-validation-program/entropy-validations)).
- Entropy sources can get their own Entropy Validation Certificate ([ESV](https://csrc.nist.gov/projects/cryptographic-module-validation-program/entropy-validations)).
- Go's `crypto/rand.Reader` "is implemented in terms of a NIST SP 800-90A DRBG". It mixes in platform randomness "as uncredited additional data". From v1.26.0 it seeds from a CPU jitter source (ESV #E318) ([Go FIPS 140-3](https://go.dev/doc/security/fips140)).
- AWS-LC uses CPU Jitter RNG entropy certificates #E77 and #E280 ([AWS-LC FIPS.md](https://github.com/aws/aws-lc/blob/main/crypto/fipsmodule/FIPS.md)).
- Inference: Oska needs a CSPRNG anyway, since SplitMix64 is not one. An SP 800-90A DRBG (for example HMAC_DRBG or CTR_DRBG) seeded from the OS is the natural design. ESV for the OS source, or a jitter source, would be needed only for option (c).

### Self-tests

- The IG has a section on cryptographic algorithm self-tests (IG 10.3.A) and one on the pre-operational integrity test (IG 10.2.A) ([FIPS 140-3 IG](https://csrc.nist.gov/csrc/media/Projects/cryptographic-module-validation-program/documents/fips%20140-3/FIPS%20140-3%20IG.pdf)). The tool used here could not read their full text. Open question: the exact CAST list and timing rules.
- Vendor practice shows what those rules lead to:
  - Go: "All algorithms perform known-answer self-tests ... either at `init` time, or on first use". An integrity self-check runs at `init` time, "comparing the checksum of the module's object file computed at build time with the symbols loaded in memory". Pairwise consistency tests on generated keys can slow some key types by up to 2x ([Go FIPS 140-3](https://go.dev/doc/security/fips140)).
  - AWS-LC and BoringCrypto: an HMAC over the module's code and data runs in a constructor. The expected value is injected at link time, and a mismatch makes the module exit ([AWS-LC FIPS.md](https://github.com/aws/aws-lc/blob/main/crypto/fipsmodule/FIPS.md); [BoringSSL FIPS.md](https://boringssl.googlesource.com/boringssl/+/HEAD/crypto/fipsmodule/FIPS.md)).
  - BoringCrypto: on a failed power-on test, "BoringCrypto will crash" ([BoringSSL FIPS.md](https://boringssl.googlesource.com/boringssl/+/HEAD/crypto/fipsmodule/FIPS.md)).
  - Windows: since April 2024 the modules "automatically run the self-tests before these modules use a cryptographic algorithm" ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/security/security-foundations/certification/fips-140-validation)).

### Approved service indicator

- The IG has a section on the approved service indicator (IG 2.4.C) ([FIPS 140-3 IG](https://csrc.nist.gov/csrc/media/Projects/cryptographic-module-validation-program/documents/fips%20140-3/FIPS%20140-3%20IG.pdf)).
- OpenSSL added FIPS indicators to its FIPS provider in 3.4. "An absent indicator must not be interpreted as approval", and "Some algorithms can change from approved to unapproved as a result of their parameters" ([OpenSSL 3.5 fips_module](https://docs.openssl.org/3.5/man7/fips_module/)).
- AWS-LC uses a per-thread counter. If the counter changes during a call, the call was approved. The macro `CALL_SERVICE_AND_CHECK_APPROVED` wraps this ([AWS-LC FIPS.md](https://github.com/aws/aws-lc/blob/main/crypto/fipsmodule/FIPS.md)).
- Go exposes `crypto/fips140.Enabled` and `Version` ([Go FIPS 140-3](https://go.dev/doc/security/fips140)).

### Zeroisation

- The IG covers zeroisation in IG 9.7.A and 9.7.B. For hybrid modules, one service must "support zeroisation of all SSPs" ([FIPS 140-3 IG](https://csrc.nist.gov/csrc/media/Projects/cryptographic-module-validation-program/documents/fips%20140-3/FIPS%20140-3%20IG.pdf)). Open question: the full text of IG 9.7.A, which was not readable here.
- Inference: Oska's `Secret<U8/U32/U64>` types are the natural place for zeroisation. Copy-on-write `Bytes` could leave stale copies of keys, so a FIPS mode would need a key type that is wiped when dropped and never copied.

## 3. What claims are allowed

### CMVP's own wording

- "The correct the term is validated" (sic) ([CMVP FAQ](https://csrc.nist.gov/Projects/cryptographic-module-validation-program/faqs), SG-7).
- "Compliant" means the vendor believes the product meets the standard, and nobody has tested it independently. A validated product has a certificate number ([CMVP FAQ](https://csrc.nist.gov/Projects/cryptographic-module-validation-program/faqs), P-18).
- "Non-validated cryptography is viewed as providing no protection to the information or data". The data counts as unprotected plaintext ([CMVP FAQ](https://csrc.nist.gov/Projects/cryptographic-module-validation-program/faqs), P-4).
- Buyers should check a claim against the CMVP entry, and may ask for a signed letter that cites the certificate number ([CMVP FAQ](https://csrc.nist.gov/Projects/cryptographic-module-validation-program/faqs), SG-8).
- On Windows, a certificate noted "When operated in FIPS mode" means the Security Policy rules must be followed ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/security/security-foundations/certification/fips-140-validation)).

### What a project with no certificate can truthfully say

Inference, from the FAQ wording above:

- True: "Oska's crypto is not FIPS 140-3 validated. No Oska module is on the CMVP Modules In Process or IUT list."
- True, once option (b) exists: "In approved-only mode, Oska uses only algorithms that NIST approves. They are implemented in Oska and tested with NIST ACVP sample vectors. They are not CAVP-certified or CMVP-validated. US federal rules treat them as providing no protection."
- Avoid: "FIPS compliant", "FIPS certified", "FIPS 140-3 ready", and a bare "FIPS mode". Each suggests a test that never took place. CMVP reads "compliant" as a vendor's own belief.

### How other ecosystems do it

- **Go.** The Go Cryptographic Module is the set of packages under `crypto/internal/fips140/...`. v1.0.0 has CMVP #5247 (CAVP A6650). v1.26.0 has CMVP #5581 (CAVP A8028) ([Go FIPS 140-3](https://go.dev/doc/security/fips140)).
  - `GOFIPS140` is set at build time. It picks the frozen module version and turns FIPS mode on by default. `GODEBUG=fips140=on` turns it on at run time. `fips140=only` makes non-approved algorithms error or panic, but it is "not intended to be used in production" ([Go FIPS 140-3](https://go.dev/doc/security/fips140)).
  - Go hedges its claims. It says the mechanisms "facilitate compliance", and that using a validated module "may not—on its own—satisfy all relevant regulatory requirements" ([Go FIPS 140-3](https://go.dev/doc/security/fips140)).
- **OpenSSL 3.** FIPS is a separate provider. Applications turn it on through config, or with `default_properties = fips=yes` or `EVP_set_default_properties(NULL, "fips=yes")`. "Some released versions of OpenSSL do not include a validated FIPS provider" ([OpenSSL 3.0 fips_module](https://docs.openssl.org/3.0/man7/fips_module/)). "The property query `fips=yes` is mandatory" for applications that want to operate in an approved manner ([OpenSSL 3.5 fips_module](https://docs.openssl.org/3.5/man7/fips_module/)).
- **BoringCrypto.** "BoringSSL as a whole is not FIPS validated", only its core module. The `main` branch is an "update stream", and there `FIPS_version` returns zero ([BoringSSL FIPS.md](https://boringssl.googlesource.com/boringssl/+/HEAD/crypto/fipsmodule/FIPS.md)).
- **AWS-LC.** Each certificate is tied to a module version: v2.0 is #4816 (static) and #5429 (dynamic), v3.1 is #5298 and #5314, and v4.0 is in process. "Please review the correct FIPS Security Policy to determine which APIs, algorithms, and parameters are approved" ([AWS-LC FIPS.md](https://github.com/aws/aws-lc/blob/main/crypto/fipsmodule/FIPS.md)).
- **Rust (rustls).** The `fips` feature plus `default_fips_provider().install_default()` uses aws-lc-rs, which "is covered by FIPS 140-3 certificate #4816". `ClientConfig::fips()` reports whether a config is FIPS-only. rustls bases its claim on the aws-lc-rs certificate, not on itself ([rustls manual](https://docs.rs/rustls/latest/rustls/manual/_06_fips/index.html)).
- **Microsoft.** Windows validates its modules per release, such as `bcryptprimitives.dll` and `CNG.sys`. The old "Use FIPS-compliant algorithms" policy no longer drives self-tests, and apps do not inherit validation ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/security/security-foundations/certification/fips-140-validation)).
- **Apple.** corecrypto has separate certificates for Apple silicon and Intel, and for user space and kernel. Examples for macOS 15 are 5184 and 5387. "Validation of conformance can be performed only against a final released version of macOS" ([Apple macOS certifications](https://support.apple.com/guide/certifications/macos-security-certifications-apc35eb3dc4fa/web)).
- **Linux kernel.** Booting with `fips=1` sets `fips_enabled`. The crypto API then restricts some algorithms and runs self-tests. `fips_name` and `fips_version` come from kernel config ([kernel sysctl/crypto](https://docs.kernel.org/admin-guide/sysctl/crypto.html)). The upstream docs claim no validation. Inference: certificates come from the distributions that ship the kernel.

## 4. Evidence for a GitHub Pages compliance report

### Constraints from ADR 0017 and the glossary

- A report is a **self-assessment**. It cites a pinned commit or release for each claim, never calls itself an audit, and says that no third party performed or certified it (ADR 0017; GLOSSARY "Self-assessment").
- High and Medium gaps are **findings**. Low gaps are **observations**. Only findings lower the **determination** (Conforms, Partially conforms, Does not conform). The determination is given "beside the standard's own measure" (ADR 0017).
- GitHub Pages is static hosting, "HTML, CSS, and JavaScript files straight from a repository" ([GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/about-github-pages)). Inference: so every piece of evidence must be a file or a link. Nothing on the page can be checked live.

### Artifacts that would evidence the position

Inference, unless cited:

1. **Position statement.** One line at the top: "Not validated. No CMVP certificate. Not on the MIP or IUT list." It links to the CMVP search so a reader can check ([CMVP FAQ](https://csrc.nist.gov/Projects/cryptographic-module-validation-program/faqs), SG-8). If a certificate ever exists, show its number, module version, security level, and tested operational environments.
2. **Algorithm inventory.** A table of each algorithm, its NIST standard, approved or not approved, which mode allows it, the source file at a pinned commit, and the test vectors it passes.
3. **ACVP vectors.** NIST's ACVP-Server repo has sample JSON files for "all algorithms covered by the Gen/Vals", including prompt and expectedResults files, and anyone can generate vector sets without the ACVTS API ([ACVP-Server](https://github.com/usnistgov/ACVP-Server)). Publish the pinned vector files' hashes and the CI run that passed them. Say plainly that these are self-run, not CAVP certificates. Certificates need the Production server, which only labs can use ([CAVP](https://csrc.nist.gov/projects/cryptographic-algorithm-validation-program)). The free Demo ACVTS server is another option ([CAVP](https://csrc.nist.gov/projects/cryptographic-algorithm-validation-program)), but its results are not certificates either.
4. **Wycheproof and RFC vectors.** ADR 0012 already names them as Oska's assurance.
5. **Self-test code.** Links to the CAST and integrity-test code, plus a test that corrupts a known answer and shows the module refusing to run. This follows BoringSSL's and AWS-LC's `break-kat.go` ([BoringSSL FIPS.md](https://boringssl.googlesource.com/boringssl/+/HEAD/crypto/fipsmodule/FIPS.md)).
6. **Service-indicator tests.** A test for each non-approved path, showing it is refused or flagged.
7. **Build provenance.** The signed `SHA256SUMS` and release index already in `docs/agents/release.md`, and reproducible builds (`SOURCE_DATE_EPOCH`). These show which bytes the claims are about. They are not FIPS evidence.
8. **Known gaps.** No lab testing, no entropy validation, no physical security, no Security Policy document, and no timing measurement (ADR 0012 says "Nothing measures it").

### Mapping to findings, observations and a determination

Inference:

- Standard's own measure: "CMVP certificate: none; security level: n/a".
- Determination: **Does not conform**. Under FIPS 140-3, only validation counts, and non-validated crypto "provid[es] no protection" ([CMVP FAQ](https://csrc.nist.gov/Projects/cryptographic-module-validation-program/faqs)). "Partially conforms" would mislead readers.
- Finding (High): no validated module. Users who need FIPS 140-3 cannot use Oska's crypto for protection.
- Finding (Medium, once crypto ships): approved and non-approved algorithms run with no indicator.
- Observations (Low): missing Security Policy-style document; no ACVP Demo run; no zeroisation of key buffers. Rate each one honestly when the time comes.
- Wording: the page says "self-assessment" and "not validated". It never says "FIPS compliant" or "audit".

## 5. Design options for an Oska FIPS mode

### (a) Delegate to platform validated modules

- What: in FIPS mode, `std.crypto` calls OpenSSL's FIPS provider on Linux, CNG on Windows, and corecrypto on macOS.
- Pros: real certificates today, on many platforms ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/security/security-foundations/certification/fips-140-validation); [Apple macOS certifications](https://support.apple.com/guide/certifications/macos-security-certifications-apc35eb3dc4fa/web)). rustls shows this pattern: a protocol in a safe language on top of a validated module ([rustls manual](https://docs.rs/rustls/latest/rustls/manual/_06_fips/index.html)).
- Cons:
  - It conflicts with ADR 0012, whose goal is "an all-Oska implementation". ADR 0012 rejected even Rust intrinsics for primitives.
  - Only the user's own configuration makes it valid. OpenSSL needs a validated provider build and `fips=yes` ([OpenSSL 3.0 fips_module](https://docs.openssl.org/3.0/man7/fips_module/)), and Windows needs the Security Policy rules followed ([Microsoft Learn](https://learn.microsoft.com/en-us/windows/security/security-foundations/certification/fips-140-validation)).
  - Inference: it brings C libraries into a static, musl-built `oskac` world. Oska would need a different backend on each OS, and Apple's APIs might not offer every primitive.
- Inference: this is the only option that gives validated crypto within months. Adopting it would need a new ADR that amends 0012, for the FIPS mode only.

### (b) Approved-only mode for Oska's own crypto (recommended next)

- What: a mode that allows only approved algorithms (AES-GCM, SHA-2, HMAC, HKDF/TLS KDF, P-256/P-384 ECDH and ECDSA, RSA with minimum sizes, an SP 800-90A DRBG). In that mode, X25519 and ChaCha20-Poly1305 are refused. The module runs CASTs and an integrity check, and exposes a service indicator. It follows the patterns in Go and AWS-LC ([Go FIPS 140-3](https://go.dev/doc/security/fips140); [AWS-LC FIPS.md](https://github.com/aws/aws-lc/blob/main/crypto/fipsmodule/FIPS.md)).
- Pros: it keeps ADR 0012. It is the groundwork for (c), because CAVP needs these same pieces. The checker's secret types already help with key handling.
- Cons: it gives no legal validation, and federal buyers see it as unprotected ([CMVP FAQ](https://csrc.nist.gov/Projects/cryptographic-module-validation-program/faqs)). The TLS client loses its preferred X25519. There is a risk that readers take "approved" to mean "validated".
- Inference: name it for what it does, for example "approved-algorithms mode", not "FIPS mode". Go's `fips140=only` is the closest match, and Go marks it as a testing aid ([Go FIPS 140-3](https://go.dev/doc/security/fips140)).

### (c) CMVP validation of an Oska crypto module

- What: freeze an "Oska Cryptographic Module" version, contract a CSTL, run CAVP through the lab, get entropy validated, write a Security Policy, and submit to CMVP ([CMVP](https://csrc.nist.gov/projects/cryptographic-module-validation-program); [CAVP](https://csrc.nist.gov/projects/cryptographic-algorithm-validation-program); [ESV](https://csrc.nist.gov/projects/cryptographic-module-validation-program/entropy-validations)).
- Cost and time: lab fees plus NIST fees ([CMVP FAQ](https://csrc.nist.gov/Projects/cryptographic-module-validation-program/faqs)). Go needs a funded contract for yearly runs ([Go FIPS 140-3](https://go.dev/doc/security/fips140)). Inference: allow a year or more per version, and ongoing money.
- The operational environment problem:
  - Each software operational environment is "the Operating System, the platform, and the processor". The algorithms "must have been tested on every operating environment claimed", and "The module certificate can only claim what is tested" ([FIPS 140-3 IG, IG 2.3.A and 2.3.C](https://csrc.nist.gov/csrc/media/Projects/cryptographic-module-validation-program/documents/fips%20140-3/FIPS%20140-3%20IG.pdf)).
  - Inference: Oska's six targets (Linux, macOS and Windows on x86_64 and aarch64; ADR 0011 and 0014) mean at least six tested environments. Apple even validates Apple silicon and Intel separately ([Apple macOS certifications](https://support.apple.com/guide/certifications/macos-security-certifications-apc35eb3dc4fa/web)).
- The compiled-language problem:
  - Inference: the validated thing is the machine code `oskac` emits, so the compiler version is part of the module. Go solves this by freezing the module source as a version and selecting it with `GOFIPS140`. An init-time checksum then compares the module's object code with what was computed at build time ([Go FIPS 140-3](https://go.dev/doc/security/fips140)). AWS-LC and BoringCrypto compute the HMAC before the final link and inject it ([AWS-LC FIPS.md](https://github.com/aws/aws-lc/blob/main/crypto/fipsmodule/FIPS.md)).
  - Inference: Oska would need `oskac` to place the module in its own relocation-free section and inject the expected HMAC. It would also need the module's code generation pinned, either by pinning the compiler or by keeping code generation stable for the frozen source.
- Inference: use a validated stream plus an update stream, as BoringSSL does. FedRAMP guidance promotes "update streams over ... validated module streams" ([BoringSSL FIPS.md](https://boringssl.googlesource.com/boringssl/+/HEAD/crypto/fipsmodule/FIPS.md)).

### How a mode could be selected

Inference:

- **Build flag (primary).** For example, `oskac build --crypto=approved` or a manifest field. It links the frozen module and turns the mode on by default, like `GOFIPS140` ([Go FIPS 140-3](https://go.dev/doc/security/fips140)). A build-time choice fits signed, reproducible releases, because the binary then records which module it carries.
- **Runtime setting (secondary).** An environment or config switch that can turn the mode on but never off, read once at start-up, like `GODEBUG=fips140=on`, which "can't be changed after the program has started" ([Go FIPS 140-3](https://go.dev/doc/security/fips140)).
- **Capability or type-level.** Oska makes authority visible in signatures (ADR 0012 mentions `NetConnect`). An approved-only API surface, such as a module or a capability that can only reach approved functions, would let the checker reject non-approved calls at compile time. That is stronger than a runtime indicator, but CMVP still expects an indicator at the service level (IG 2.4.C).
- **Query API.** `std.crypto.fips.enabled()`, `version()` and a per-call indicator, like Go's `crypto/fips140.Enabled` and OpenSSL's "fips-indicator" ([Go FIPS 140-3](https://go.dev/doc/security/fips140); [OpenSSL 3.5 fips_module](https://docs.openssl.org/3.5/man7/fips_module/)).
- **Self-test failure.** Stop the process, as BoringCrypto does ([BoringSSL FIPS.md](https://boringssl.googlesource.com/boringssl/+/HEAD/crypto/fipsmodule/FIPS.md)). Oska's panic is the natural route.
