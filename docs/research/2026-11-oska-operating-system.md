# What could an operating system (or OS-like environment) built using Oska look like, and how could it best support Oska and AI-agent development?

Date of access: 2026-11-19

Scope: kernel choice, mapping Oska capabilities to OS enforcement, agents and MCP, user experience, and a staged roadmap. Sections marked "Inference:" are design proposals or conclusions of this note, not decisions of the project. Everything else is a fact with its source. Repo links are relative to this file.

## 1. Oska features that shape any OS design

- Oska has no ambient authority. A function can touch the filesystem, network, environment or clock only if it is handed a capability, and every capability a program uses is declared at its entry point ([README](../../README.md)).
- `main` is the root of authority: the runtime grants `main` exactly the capabilities its signature declares ([GLOSSARY](../../GLOSSARY.md)). The built-in capabilities are `Stdin`/`Stdout`/`Stderr`, `Fs`, `Env`, `Clock`, `Random`, `Net` (attenuating to `NetConnect`/`NetListen`), `Sched` and `Spawn`; `Net`, `Sched` and `Spawn` check but do not run yet ([capabilities guide](../guide/capabilities.md)).
- A function's effects are exactly the capabilities it can reach. A function with no capability-bearing parameters is pure and deterministic ([ADR 0002](../adr/0002-capabilities-are-the-effect-system.md)).
- Untrusted text carries a trust flag. Untrusted text can never flow into a trusted slot, and `.assume_trusted()` is an audited trust assertion ([ADR 0006](../adr/0006-trust-is-a-flag-on-text.md)). Structural positions of sinks, such as a program name, an attenuation directory or a network host, reject untrusted values ([GLOSSARY](../../GLOSSARY.md)).
- `Fs` only attenuates. Every read and write goes through a directory or file capability, and code that wants the whole filesystem must write `restrict_to("/")`, which the authority report shows ([ADR 0008](../adr/0008-file-access-goes-through-confined-capabilities.md)). The runtime holds an OS handle for each root, opens each path component relative to the one before with `openat` and `O_NOFOLLOW`, and refuses every symlink and every hard-linked file ([runtime notes](../runtime.md#capabilities)).
- `oskac` writes executables itself, with no assembler or linker. A Linux executable is static, and the same program gives the same bytes on every host ([README](../../README.md)). On Linux the executable uses no C library ([GLOSSARY](../../GLOSSARY.md)). The runtime `std.rt` is Oska code compiled into every program ([ADR 0011](../adr/0011-oska-generates-native-code-itself.md)).
- System-call intrinsics exist only in `std.rt`, and the checker rejects any use of them elsewhere, because a raw system call is ambient authority ([ADR 0013](../adr/0013-system-calls-only-in-std-rt.md)).
- TLS 1.3 (client only), git fetch and crypto are to be written in Oska, so the checker sees every byte from the network ([ADR 0012](../adr/0012-tls-git-and-crypto-are-written-in-oska.md)).
- Every supported platform (Linux and macOS on aarch64 and x86_64, Windows on x86_64) must have the same output and the same security guarantees. New language features are frozen until all five are native ([ADR 0014](../adr/0014-every-supported-platform-builds-and-runs-natively.md)).
- Unused authority is a release-check error, with no escape hatch, and the Claude Code Stop gate runs that check ([ADR 0016](../adr/0016-unused-authority-is-a-release-check-error.md)).
- The authority report is available as JSON. `oskac check --baseline=authority.json` exits with 3 when authority widened, and approving a widening is a reviewed change to the committed baseline ([agent guide](../guide/agent-guide.md), [CLI reference](../guide/cli-reference.md#authority-baseline)).
- `oskac hook claude --event=post-edit` and `--event=stop` plug the checker into Claude Code hooks ([agent guide](../guide/agent-guide.md)). `oskac lsp` is the language server that editors and agents query ([GLOSSARY](../../GLOSSARY.md)).
- The released `oskac` binaries for Linux are built on Ubuntu 22.04 and need glibc 2.35 or newer. They do not run on musl systems such as Alpine ([install guide](../guide/install.md)).

Inference: Oska already behaves like a small capability OS inside one process. `main`'s signature works like a process's initial capability set. Attenuation works like reducing a handle's rights. `std.rt` works like the system-call boundary. An "Oska OS" therefore does not need a new security model. It needs the layer below the program to enforce the same model, so that a bug in `std.rt` or in the native backend does not equal full ambient authority.

## 2. The primary-source landscape

### Capability kernels

- In seL4, a capability is "a unique, unforgeable token that constitutes a permission to access an entity or object in the system". Capabilities live in CNodes that form a thread's CSpace, and one object can be pointed to by several capabilities with different permissions ([seL4 capabilities tutorial](https://docs.sel4.systems/Tutorials/capabilities.html)). At initialisation, capabilities to all kernel resources go to the root task ([seL4](https://docs.sel4.systems/Tutorials/capabilities.html)).
- In Zircon (Fuchsia), a handle is "a session or connection to a particular kernel object" with a set of rights. `zx_handle_replace()` creates an equivalent handle, possibly with fewer rights, and handles move between processes only through channels or sockets ([Zircon handles](https://fuchsia.dev/fuchsia-src/concepts/kernel/handles)).
- In FreeBSD Capsicum, after `cap_enter(2)` "only explicitly delegated rights, referenced by memory mappings or file descriptors, may be used". Global namespaces are restricted, `openat(2)` lookups stay beneath the given descriptor, `cap_rights_limit(2)` narrows a descriptor, and the mode is inherited and cannot be cleared ([capsicum(4)](https://man.freebsd.org/cgi/man.cgi?query=capsicum&sektion=4)).

Inference: Oska's `main` grant matches seL4's root task. Its attenuation matches `zx_handle_replace` with fewer rights and `cap_rights_limit`. Its directory capabilities match Capsicum's descriptor-relative `openat`. The fit is close, but Oska supports only Linux, macOS and Windows ([ADR 0014](../adr/0014-every-supported-platform-builds-and-runs-natively.md)), so none of these kernels is a target today.

### Linux sandboxing primitives

- Landlock lets "any process, including unprivileged ones, to securely restrict themselves". It covers file hierarchies (read, write, execute, create, remove), TCP and UDP ports (bind, connect), and scoping of abstract UNIX sockets and signals. Restrictions are inherited, and "only adding more restrictions is allowed". Applications must query the ABI version at runtime ([Landlock docs](https://docs.kernel.org/userspace-api/landlock.html)).
- A seccomp filter is a BPF program over the system-call number and register arguments. It cannot dereference pointers. It requires `no_new_privs` or `CAP_SYS_ADMIN`, and its actions include `KILL_PROCESS`, `ERRNO`, `USER_NOTIF` and `LOG`. The kernel docs state that "System call filtering isn't a sandbox" ([seccomp filter docs](https://docs.kernel.org/userspace-api/seccomp_filter.html)).
- `openat2(2)` (Linux 5.6) has `RESOLVE_BENEATH`, `RESOLVE_NO_SYMLINKS` (all components, unlike `O_NOFOLLOW`), `RESOLVE_IN_ROOT` and `RESOLVE_NO_XDEV` ([openat2(2)](https://man7.org/linux/man-pages/man2/openat2.2.html)).
- Namespaces wrap "a global system resource in an abstraction": mount, network, PID, user, IPC, UTS, cgroup and time. Since Linux 3.8, user namespaces can be created without privilege ([namespaces(7)](https://man7.org/linux/man-pages/man7/namespaces.7.html)).
- cgroup v2 has a single hierarchy with `cpu.max`, `memory.max`, `io.max` and `pids.max`. A cgroup can be delegated to an unprivileged user, and the parent's limits still apply ([cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)).

### Containers, gVisor, microVMs, unikernels, WASM

- An OCI image is a manifest, an optional index (one entry per platform), filesystem layers and a configuration, all content-addressed so the image can be "verified by hash" ([OCI image spec](https://github.com/opencontainers/image-spec/blob/main/spec.md)). The OCI runtime config has `process.args`, `process.capabilities`, `noNewPrivileges`, `root.readonly`, `mounts`, and Linux `namespaces`, `seccomp` and `resources`. It has no Landlock field ([OCI runtime config](https://github.com/opencontainers/runtime-spec/blob/main/config.md)).
- `FROM scratch` is Docker's reserved empty base, "typically used to create minimal images containing only just what an application needs", and it suits statically compiled binaries ([Docker base images](https://docs.docker.com/build/building/base-images/)).
- gVisor is an application kernel in Go whose Sentry services system calls itself and does not pass them to the host. `runsc` is an OCI runtime. gVisor documents poor performance for system-call-heavy workloads and incomplete system-call coverage ([gVisor docs](https://gvisor.dev/docs/)).
- Firecracker runs KVM microVMs and "excludes unnecessary devices and guest-facing functionality to reduce the memory footprint" ([Firecracker README](https://github.com/firecracker-microvm/firecracker)). Its devices are virtio-net, virtio-block, vsock, a serial console and a partial i8042. It loads per-thread seccomp filters before any guest code runs, has a `jailer` for cgroups, chroot and privilege drop, offers token-bucket rate limiters, and does no network filtering of its own ([Firecracker design](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md)). It backs AWS Lambda and Fargate ([Firecracker README](https://github.com/firecracker-microvm/firecracker)).
- Unikraft unikernels are "a single-address space binary object" built from a library OS whose parts are interchangeable ([Unikraft concepts](https://unikraft.org/docs/concepts)). MirageOS is an OCaml library OS whose code runs under Unix during development and is "compiled into a fully-standalone, specialised unikernel that runs under a Xen or KVM hypervisor" ([MirageOS](https://mirage.io/)).
- A WebAssembly component "interacts with a runtime or other components only by calling its imports and having its exports called", so its access can be analysed statically ([Component Model](https://component-model.bytecodealliance.org/design/why-component-model.html)). Oska rejected WASM both with its own engine (too slow) and with an external runtime (a dependency on outside software) ([ADR 0011](../adr/0011-oska-generates-native-code-itself.md)).

### Agent tooling

- Claude Code's sandbox puts shell commands in an OS boundary: bubblewrap and a separate network namespace on Linux, Seatbelt on macOS, and a host-allowlist proxy that "does not terminate or inspect TLS traffic". By default it allows reads of the whole computer, "This default still allows reading credential files", and MCP servers, hooks and file tools run outside the sandbox ([Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)).
- MCP is JSON-RPC 2.0 between hosts, clients and servers. Servers offer resources, prompts and tools. Clients offer sampling, roots ("filesystem boundaries to operate in") and elicitation. The spec says tool "descriptions of tool behavior such as annotations should be considered untrusted, unless obtained from a trusted server", that hosts must obtain consent before invoking any tool, and that "MCP itself cannot enforce these security principles at the protocol level" ([MCP specification 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18)).

## 3. Kernel choice

| Option | What it would be | Fit with Oska today |
|---|---|---|
| A. OCI image on any Linux | Oska programs `FROM scratch`; a toolchain image with `oskac` | Static, libc-free executables ([README](../../README.md)) need nothing else in the image ([Docker](https://docs.docker.com/build/building/base-images/)). `oskac` itself needs glibc 2.35 ([install](../guide/install.md)), so the toolchain image needs a glibc base for now. |
| B. Minimal Linux distro ("Oska host") | A Linux kernel, an Oska init and launcher, Landlock, seccomp, namespaces and cgroups | No new target platform: it is Linux. Landlock is unprivileged and stackable ([Landlock](https://docs.kernel.org/userspace-api/landlock.html)). |
| C. microVM guest | B packed as a Firecracker rootfs, one VM per agent session | Firecracker's threat model assumes the guest is hostile ([design](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md)), which suits code an agent wrote. |
| D. Oska unikernel | `std.rt` lowered to a hypervisor interface, as MirageOS does for OCaml ([MirageOS](https://mirage.io/)) | A new target platform. Under the parity gate it must match the five supported platforms ([ADR 0014](../adr/0014-every-supported-platform-builds-and-runs-natively.md)), and it needs a TCP/IP stack and drivers that Oska does not have. |
| E. Own kernel, or Oska on seL4 or Zircon | Oska capabilities become kernel capabilities | Closest model ([seL4](https://docs.sel4.systems/Tutorials/capabilities.html), [Zircon](https://fuchsia.dev/fuchsia-src/concepts/kernel/handles)). It needs a language feature Oska lacks today: `unsafe` exists only in the Rust crate `oska-sys` ([ADR 0013](../adr/0013-system-calls-only-in-std-rt.md)). |
| (rejected) WASI/WASM component host | Oska compiled to components | Rejected by [ADR 0011](../adr/0011-oska-generates-native-code-itself.md). |
| (optional) gVisor | `runsc` under option A | Possible, but its system-call overhead ([gVisor](https://gvisor.dev/docs/)) buys little for programs whose system-call surface is already one small module ([ADR 0013](../adr/0013-system-calls-only-in-std-rt.md)). |

Inference: the best near-term answer is B, delivered as A and C. That means a Linux kernel with a userland written in Oska, shipped as OCI images for daily use and as a Firecracker microVM image for agent sessions. It keeps Oska on a platform it already supports, so it does not collide with the parity gate. The ambitious options, D and E, are research tracks for after v0.6.0, when the gate is on. Choosing between them depends on whether Oska ever adds a supported platform that is not an existing OS.

## 4. Mapping Oska capabilities to OS enforcement

Inference: the core idea is "the authority report is the sandbox policy". `oskac check --format=json` already lists each function's authority and every attenuation ([CLI reference](../guide/cli-reference.md)). A build step can turn `main`'s capabilities into a Landlock ruleset and a seccomp filter. `std.rt` would install that policy itself at startup, before `main` runs, as defense in depth under the checker's guarantee. Landlock fits because it is unprivileged and can only narrow ([Landlock](https://docs.kernel.org/userspace-api/landlock.html)). seccomp fits as a system-call-surface reduction, not as the sandbox ([seccomp](https://docs.kernel.org/userspace-api/seccomp_filter.html)).

| Oska capability | Language rule (source) | Inference: OS enforcement on Linux |
|---|---|---|
| No capability (pure) | Pure and deterministic ([ADR 0002](../adr/0002-capabilities-are-the-effect-system.md)) | seccomp allow-list of only the calls `std.rt` needs for memory, stdio and exit, with `KILL_PROCESS` as the default. Landlock handles every filesystem and network right and grants none. |
| `Fs` → `Dir`/`DirRead`/`FileRead`... | Confined handles, `openat`+`O_NOFOLLOW`, no symlinks, no hard links ([runtime](../runtime.md#capabilities)) | Landlock path rules for each root that is cut from trusted text. `std.rt` could move to `openat2` with `RESOLVE_BENEATH \| RESOLVE_NO_SYMLINKS` ([openat2](https://man7.org/linux/man-pages/man2/openat2.2.html)) as a second check. A root that is only known at run time, such as `restrict_to("/")` or a root from `Env`, forces a coarser rule, and the report already shows it ([ADR 0008](../adr/0008-file-access-goes-through-confined-capabilities.md)). |
| `Net` → `NetConnect`/`NetListen` | The host is a structural position ([GLOSSARY](../../GLOSSARY.md)) | No `Net`: a new empty network namespace ([namespaces(7)](https://man7.org/linux/man-pages/man7/namespaces.7.html)). `NetConnect`: Landlock TCP-connect rules ([Landlock](https://docs.kernel.org/userspace-api/landlock.html)), plus a host allowlist taken from trusted host literals, enforced by a proxy as Claude Code does ([Claude Code sandboxing](https://code.claude.com/docs/en/sandboxing)). |
| `Spawn` | Starting OS processes; checks only today ([capabilities](../guide/capabilities.md)) | No `Spawn`: seccomp denies `execve`/`execveat` and process-creating `clone`. With `Spawn`: the child inherits the Landlock domain and seccomp filter, which only narrow ([Landlock](https://docs.kernel.org/userspace-api/landlock.html), [seccomp](https://docs.kernel.org/userspace-api/seccomp_filter.html)). |
| `Env` | Can hold secrets ([capabilities](../guide/capabilities.md)) | The launcher passes an empty environment to programs without `Env`. |
| `Clock`, `Random` | Sources of nondeterminism ([ADR 0002](../adr/0002-capabilities-are-the-effect-system.md)) | Little to enforce at OS level. A time namespace ([namespaces(7)](https://man7.org/linux/man-pages/man7/namespaces.7.html)) can pin clocks for reproducible agent runs. |
| `Sched`, tasks | Channels and `select` ([capabilities](../guide/capabilities.md)) | cgroup v2 `pids.max`, `memory.max` and `cpu.max` per session ([cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)). Resources are not capabilities in Oska today, so this is an OS-level addition. |

Inference, a constraint: [ADR 0014](../adr/0014-every-supported-platform-builds-and-runs-natively.md) demands the same security guarantees on every platform. Landlock exists only on Linux, so this layer must be documented as extra hardening that is not part of the language guarantee. Otherwise it creates a Linux-only guarantee. Seatbelt on macOS, as Claude Code uses ([sandboxing](https://code.claude.com/docs/en/sandboxing)), and Windows job objects are possible parity follow-ups, but this note did not research them.

Inference, a second constraint: a Landlock policy must be fixed before it can only narrow. Roots computed at run time therefore either widen the policy to the coarsest root the report shows, or `std.rt` adds a Landlock layer each time a root is opened. Stacked layers can only narrow ([Landlock](https://docs.kernel.org/userspace-api/landlock.html)), but each layer covers the whole process. Whether this is workable is an open question.

## 5. Agents, LLM tools and MCP

- Inference, an agent session is a capability grant. A session is a microVM (option C) or a Landlocked, namespaced process tree (option B). It receives a work directory as its only writable root, an allowlist of hosts and a cgroup budget. That matches what Claude Code configures with `allowWrite` and allowed domains ([sandboxing](https://code.claude.com/docs/en/sandboxing)), but it is derived from authority reports and not written by hand.
- Inference, MCP servers written in Oska. An MCP tool server written in Oska has an authority report that states what each tool can do ([agent guide](../guide/agent-guide.md)). That answers the MCP spec's requirement that users "understand what each tool does before authorizing its use" from the code itself, not from the description, which the spec says to treat as untrusted ([MCP](https://modelcontextprotocol.io/specification/2025-06-18)). The host would show the committed authority baseline as the consent screen, and a widening (exit code 3) would require consent again ([CLI reference](../guide/cli-reference.md#authority-baseline)).
- Inference, trust flags at the protocol edge. Every string arriving over MCP (tool arguments, resource contents, sampling results) enters as `Untrusted<String>` ([ADR 0006](../adr/0006-trust-is-a-flag-on-text.md)). So the checker refuses model output in a structural position, such as a path root, a command name or a host ([GLOSSARY](../../GLOSSARY.md)), unless a validator vouches for it. That is a prompt-injection defense the protocol cannot give, because MCP cannot enforce its principles itself ([MCP](https://modelcontextprotocol.io/specification/2025-06-18)).
- Inference, MCP roots map to directory capabilities. A host's `roots` become the directory capabilities granted to the server, which narrow by `restrict_to` with untrusted `Path` but never escape their root ([ADR 0008](../adr/0008-file-access-goes-through-confined-capabilities.md)).
- Inference, closing Claude Code's gaps. Claude Code's sandbox leaves MCP servers and hooks outside the boundary, and by default allows reads of credential files ([sandboxing](https://code.claude.com/docs/en/sandboxing)). In an Oska OS image, the `oskac hook claude` gates ([agent guide](../guide/agent-guide.md)) and Oska MCP servers would run inside the session VM with their own reports. Reads would be limited to declared roots, not to the whole computer.
- Inference, the inner loop inside the image. `oskac check --format=json`, `oskac fix`, `oskac lsp`, the post-edit and Stop hooks, and the release check that rejects unused authority ([ADR 0016](../adr/0016-unused-authority-is-a-release-check-error.md)) come preinstalled in the session image, so every agent session starts with the same gate.

## 6. User experience

Inference: these are proposals, and each one builds on an existing Oska behaviour.

- **Shell.** An Oska shell in which running a program first shows its `main` capabilities, the one-line answer to "what can this program do?" ([README](../../README.md)). The shell asks for consent when a program needs more than the session holds. Commands are checked programs, so the shell can refuse to pass untrusted text (pasted or fetched) into a program-name or path-root position, as `std.proc` already refuses at check time ([what works today](../guide/what-works-today.md)).
- **Install model.** Packages are git URLs, and the lockfile records each package's computed authority ([GLOSSARY](../../GLOSSARY.md)). Installing an application means approving its authority baseline, and an update that widens authority stops for approval, like a mobile app permission prompt but derived from code. Images are content-addressed OCI artifacts with one manifest per platform ([OCI image spec](https://github.com/opencontainers/image-spec/blob/main/spec.md)). Because Oska builds are byte-reproducible ([README](../../README.md)), a user can rebuild and compare digests.
- **Observability.** For each process, the dashboard shows the authority report, its audit sites (`assume_trusted`, `expose`) and attenuations ([CLI reference](../guide/cli-reference.md)). Runtime denials come from seccomp `LOG`/`USER_NOTIF` ([seccomp](https://docs.kernel.org/userspace-api/seccomp_filter.html)) and cgroup counters ([cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)). A denial at OS level while the checker allowed the call indicates a bug in `std.rt` or the backend, which makes the OS layer a test oracle as well.
- **Agent sessions.** "New session" boots a microVM from the toolchain image, mounts the repo as the one writable root, and attaches the agent over vsock ([Firecracker design](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md)). When the session ends, the user gets a diff, an `authority_diff` against the baseline ([CLI reference](../guide/cli-reference.md#authority-baseline)) and the test results. The VM is then discarded.
- **Developer UX stays cross-platform.** Development happens on Linux, macOS or Windows, as with MirageOS's develop-on-Unix model ([MirageOS](https://mirage.io/)). The OS image is a deployment and agent-isolation target, not a requirement.

## 7. Staged roadmap

Inference: the stages run from cheapest to most ambitious.

1. **Stage 0: OCI images (days).** (a) Application images: `FROM scratch` plus one static Oska executable ([Docker](https://docs.docker.com/build/building/base-images/)), with one image-index entry per `linux-aarch64`/`linux-x86_64` build ([OCI image spec](https://github.com/opencontainers/image-spec/blob/main/spec.md)). The runtime config sets `root.readonly`, `noNewPrivileges` and no Linux capabilities ([OCI runtime config](https://github.com/opencontainers/runtime-spec/blob/main/config.md)). (b) Toolchain image: `oskac` on a glibc 2.35+ base, since released binaries need it ([install](../guide/install.md)). A static or musl build of `oskac` would allow `FROM scratch` here too, but that is an open item.
2. **Stage 1: authority → policy generator.** A tool, written in Oska, reads `oskac check --format=json` and writes the OCI `seccomp` section, the mounts (only declared roots, read-only where the report says `*Read`) and the network mode ([OCI runtime config](https://github.com/opencontainers/runtime-spec/blob/main/config.md), [CLI reference](../guide/cli-reference.md)). This needs no language change.
3. **Stage 2: self-sandboxing `std.rt` on Linux.** At startup, `std.rt` applies Landlock and seccomp from the program's declared authority ([Landlock](https://docs.kernel.org/userspace-api/landlock.html), [seccomp](https://docs.kernel.org/userspace-api/seccomp_filter.html)) and moves confinement to `openat2` ([openat2](https://man7.org/linux/man-pages/man2/openat2.2.html)). This would touch `std.rt` and the parity rule, so it needs an ADR on how ADR 0014's "same security guarantees" treats OS-level hardening.
4. **Stage 3: agent microVM image.** A Linux kernel, an Oska PID 1 that sets up namespaces and cgroups and launches programs with their granted capabilities, the toolchain, Oska MCP servers, and a Firecracker config with the jailer and rate limiters ([Firecracker design](https://github.com/firecracker-microvm/firecracker/blob/main/docs/design.md)). This needs `Spawn` and `Net` to run ([what works today](../guide/what-works-today.md)), which in turn waits on the feature freeze in [ADR 0014](../adr/0014-every-supported-platform-builds-and-runs-natively.md).
5. **Stage 4: Oska userland.** The shell, the package installer with an authority-approval UI, and an observability daemon, all in Oska and each with a committed authority baseline. TLS and git come from [ADR 0012](../adr/0012-tls-git-and-crypto-are-written-in-oska.md).
6. **Stage 5 (research): unikernel or capability kernel.** Lower `std.rt`'s intrinsics to virtio and a hypervisor (option D, in the MirageOS and Unikraft style ([MirageOS](https://mirage.io/), [Unikraft](https://unikraft.org/docs/concepts))), or host Oska on seL4 or Zircon, where every Oska capability is a kernel capability ([seL4](https://docs.sel4.systems/Tutorials/capabilities.html), [Zircon](https://fuchsia.dev/fuchsia-src/concepts/kernel/handles)). Either option adds a target platform and needs a decision under ADR 0014.

## 8. Open questions

- Whether a launcher can hand `main` an already-attenuated capability, such as `DirRead` for `./repo`, in place of `Fs`. Today `main` declares built-in capabilities and the program cuts roots from trusted text ([ADR 0008](../adr/0008-file-access-goes-through-confined-capabilities.md)). This note did not find whether `main` may declare `DirRead` directly.
- How ADR 0014's parity rule treats Linux-only hardening such as Landlock. The answer needs an ADR.
- Whether the seccomp allow-list can be derived exactly for each capability set, given that `std.rt`'s system-call set is still growing ([ADR 0013](../adr/0013-system-calls-only-in-std-rt.md)).
- Seatbelt, Windows job objects and AppContainer equivalents were not researched here (source limit).
- Measured boot and memory figures for Firecracker and Unikraft were not in the pages read ([Firecracker README](https://github.com/firecracker-microvm/firecracker), [Unikraft concepts](https://unikraft.org/docs/concepts)).
