# `oska-sys` is the only crate allowed to use `unsafe`

Amended on 2026-11-21 (spec #521, ticket #523): `oska-sys` also holds the musl build's allocator, under the same rules. See "Amendment: the musl build's allocator" below.

## Decision

Every crate in the workspace forbids `unsafe` code, except one: `oska-sys`, an internal crate that confines filesystem access beneath a directory handle on Unix and Windows, and holds the global allocator of the musl build of `oskac`.

- **It adds no dependencies.** It declares the few system functions it needs itself. On Unix they are C-library functions, such as `openat`, called through the C library that `std` already links. On Windows they are `ntdll` functions, such as `NtCreateFile`, linked by name with `raw-dylib`, so no import library is needed; `ntdll` is loaded in every Windows process.
- **It exposes only a safe API.** The runtime opens a root, and opens directories and files beneath it, through a directory handle type. Nothing `unsafe` is public, except the methods of the standard `GlobalAlloc` trait on the allocator type, which only the compiler's `#[global_allocator]` glue calls.
- **Every `unsafe` block states its invariant.** Each block holds one unsafe operation and begins with a `// SAFETY:` comment. Clippy's `undocumented_unsafe_blocks` and `multiple_unsafe_ops_per_block` lints enforce both.
- **The exception cannot spread.** The workspace keeps `unsafe_code = "forbid"`, and `oska-sys` is the only crate that does not take the workspace's lints. `scripts/check.sh` runs `scripts/unsafe-guard/guard.sh`, which proves it by compiling: every other crate, every target, is built with `-F unsafe_code` last on rustc's command line, so no manifest, source attribute or flag can allow `unsafe` there, and `--cap-lints` is refused. The guard also refuses a checked-in cargo config and a workflow that sets rustc flags or a wrapper, and scans source the build skips, such as `#[cfg(windows)]` code, for the word `unsafe`. `scripts/unsafe-guard/test.sh` tries each known way around it.

## Why

A directory or file capability must not be steerable outside its root, even by another process that swaps a directory for a symlink while the program runs (#69). The only race-free way to do that is to open each path component relative to a handle for the one before, never following a symlink. On Unix that is `openat` with `O_NOFOLLOW`, one component at a time.

`std` has no `openat`, and it has no way to open a path beneath a directory handle. The usual answer, the `libc` or `rustix` crate, is ruled out because the workspace takes no crates from outside the repo. Calling the C library directly needs `unsafe`. Putting all of it in one small crate keeps the code that needs review in one place, with every invariant written down.

## Considered options

- **Keep path-based checks.** Rejected: checking a path and then opening it are separate steps, and a symlink swapped in between them escapes the root. The checks narrow the window, but they cannot close it.
- **Use the `libc` or `rustix` crate.** Rejected: the workspace takes no external crates.
- **Allow `unsafe` in the runtime crate itself.** Rejected: the exception would cover a large crate, and nothing would keep `unsafe` from spreading through it.
- **Linux `openat2` with `RESOLVE_BENEATH`.** Not needed now. Walking with `openat` works on every Unix target in the release matrix, and `openat2` is Linux-only. It remains an optional speed-up for later.

## Consequences

- **Windows walks the same way.** At first `oska-sys` was empty on Windows, which kept path-based checks. [ADR 0014](0014-every-supported-platform-builds-and-runs-natively.md) closed that gap: `oska-sys` declares `ntdll`'s `NtCreateFile` itself and opens each component beneath its parent's handle, refusing reparse points (symlinks, junctions, mount points) and hard-linked files as on Unix.
- **A held directory can be moved out of the root, and its capability follows it.** On Unix a directory descriptor follows its directory through any rename. On Windows `oska-sys` opens with `FILE_SHARE_ALL` (read, write and delete sharing). It applies to every open, files included, not only directories, so another process may rename or delete a held file or directory mid-run, or move a file being written out of the root. The handle follows the object in each case. This is an availability and integrity risk, not a confinement escape: the capability still reaches only that one object and what is beneath it, never the place it was moved to, and the stored path is used only for messages. We keep it, rather than dropping the sharing so that Windows refuses the rename or delete, for three reasons. The behaviour is the same on every platform (the user chose on 2026-11-17 to keep it for Unix parity). The capability does not widen. And a process able to rename or delete in the root could move files in or out of it anyway. The race tests follow from this decision rather than motivate it: since a held directory can still be renamed, they move one aside, put a link to a directory outside in its place, and check that the program keeps reading the directory it holds (`crates/oska-run/tests/race_free_walks.rs`).
- **The platform values are hand-copied.** Flag and error numbers, such as `O_NOFOLLOW` and `ELOOP`, come from each platform's headers. They are declared only for the targets Oska releases for, and any other Unix target fails to compile. CI runs the escape tests on Linux and macOS.
- **Every symlink beneath a root is refused,** including one that points inside the root, because the walk never follows one.

## Amendment: the musl build's allocator (2026-11-21)

Both Linux builds ship ([ADR 0022](0022-linux-oskac-ships-as-glibc-and-musl-builds.md) stands). Spec #521 aimed to ship only the musl build, which needed it to run about as fast as the glibc build. The allocator exists to close that speed gap. It did not close it on x86_64, where the musl build is still 1.07x to 1.16x slower on the site build, and more on text-heavy work. So the glibc build is not retired for now (decided 2026-11-22). After the allocation fixes of #500 to #505 it still took up to 1.4x the glibc build's CPU time on x86_64 and aarch64, mostly in musl's allocator, mallocng, which locks on every call once the interpreter's thread exists and maps and unmaps memory over and over ([docs/research/2026-11-musl-oskac-performance.md](../research/2026-11-musl-oskac-performance.md), sections 3 and 7).

- **`oska-sys` holds the allocator.** `oska_sys::SizeClassAlloc` (`crates/oska-sys/src/heap.rs`) implements `GlobalAlloc`: requests of up to 1 KiB with an alignment of up to 16 bytes are served from 20 size classes, carved from 256 KiB regions that `std::alloc::System` allocates and that are never given back. Each thread keeps a free list per class with no lock; a thread locks a shared pool only to take or give back a batch of blocks, at most once per batch of calls, and once more as it ends, to give its lists back. Every other request goes to `System`. It adds no dependency. Its only calls outside Rust are the system allocator and, on Linux, to arm a thread's exit hook, the C library's `pthread_key_create` and `pthread_setspecific`.
- **The same rules apply.** One unsafe operation per block, each with a `// SAFETY:` comment, enforced by the same clippy lints. The module's documentation states the invariants the blocks rely on: a free block is reachable from exactly one list, a block's route (size class or `System`) is decided from its layout alone, and nothing panics or unwinds; a request that cannot be served returns null.
- **Only the musl build uses it.** The `#[global_allocator]` static is in `oskac` (`crates/oskac/src/heap.rs`), behind `cfg(all(target_os = "linux", target_env = "musl"))`, so macOS, Windows and the glibc build keep the system allocator. Naming the type needs no `unsafe`, so `oskac` keeps `unsafe_code = "forbid"`, and the unsafe guard is unchanged. A unit test there checks that the musl build takes its small blocks from the allocator and that no other build does.
- **It is tested on every platform.** `crates/oska-sys/tests/allocator.rs` installs it as its test binary's global allocator and stresses it with safe code: every size and alignment, growth and shrinking, frees on another thread, and a long run of interpreter-like churn; on Linux, `crates/oska-sys/tests/allocator_threads.rs` checks that threads which end one after another reuse each other's blocks. The musl CI job runs it with the musl build.
- **Considered and rejected:** a third-party allocator crate (the workspace takes no external crates); replacing musl's `memcpy` (a likely link clash with musl's own, and fragile `unsafe`); a no-`std` `oskac` (Tier 3 target, no aarch64). See spec #521.
- **Consequences.** A heap bug here breaks every guarantee in the musl build's process, the capability checks included, so a change to `heap.rs` needs a security review, as any change to `oska-sys` does. Memory a program frees is reused but never returned to the system while the process runs. On Linux, a thread that ends gives its free lists back to the shared pool through an exit hook (a `pthread` key), so `oskac test`, which runs each test block on a thread of its own, does not strand them; only a few blocks freed by a thread's last destructors, or all of a thread's lists (under 8 KiB per class) if the system has no key to give, stay unused. Elsewhere, where only tests install the allocator, there is no hook and an ending thread's lists stay unused. A freed block stays in its size class: the heap holds each class's peak, so a program that fills one class after another can make the process up to 20 times (the number of classes) larger than the most it holds at once; the security review's repro, twenty lists of 100,000 texts of one class at a time, took about 5 times the glibc build's memory (research note, section 8). `--max-memory` still charges every value a program makes and still stops a program that holds too much at once, but it meters values, not the heap, so it no longer bounds the musl build's memory by itself: allow up to 20 times its figure in the worst case.
