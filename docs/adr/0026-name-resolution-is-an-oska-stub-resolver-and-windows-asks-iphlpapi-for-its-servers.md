# Name resolution is an Oska stub resolver, and Windows asks `iphlpapi` for its name servers

- **Status:** Accepted (2026-11-22), for spec #228 (#239). Amended on 2026-11-24 (spec #659, ticket #692): the call is `GetAdaptersAddresses`, not `GetNetworkParams`; see "Amendment: adapters that are up, in metric order". Amends [ADR 0020](0020-windows-intrinsics-are-kernel32-and-ntdll-calls.md) for one function, and builds on [ADR 0025](0025-network-access-goes-through-host-narrowed-capabilities.md), whose `connect()` resolves the name.

## Decision

Names are resolved by **`std.dns`, one stub resolver written in Oska**, the same on all five platforms. It reads the hosts file and the name server configuration, asks each name server over UDP, retries over TCP when an answer is truncated, and treats every answer as untrusted data: the transaction id and question must match, compression pointers only point backwards, every length is checked, and only the records that belong to the name asked (or its `CNAME` chain) are kept. `std.dns` calls no `getaddrinfo`. `connect()` uses it on both backends.

Where the name servers come from:

- **Linux and macOS:** `/etc/resolv.conf` (`nameserver`, `search`, `domain`, and the options `ndots`, `timeout` and `attempts`), and `/etc/hosts`. `std.dns` reads both through `FsRead`.
- **Windows:** the hosts file in `C:\Windows\System32\drivers\etc`, read the same way, and the name servers from **`GetNetworkParams` of `iphlpapi.dll`**, through the intrinsic `rt_sys_get_network_params` and the prelude method `NetConnect.system_name_servers`. `GetNetworkParams` returns the system-wide list in the order Windows uses it, for every adapter, in one call and one buffer. On the other platforms `system_name_servers` gives an empty list.

The datagram itself is one prelude method, `HostConnect.exchange_datagram(message)`: it sends one UDP datagram to the host and port the capability is confined to (an address literal, so no name is resolved on the way) and returns the first datagram from that address whose transaction id is the message's own, waiting at most 5 seconds. TCP uses the existing `connect()`, `send_bytes` and `receive_bytes`.

## Why

- **One behaviour.** The three operating systems' resolvers differ in what they search, in which servers they ask first, in their timeouts and in their wording. [ADR 0012](0012-tls-git-and-crypto-are-written-in-oska.md) puts the code that parses attacker-chosen bytes in Oska, and a DNS answer is such a byte string. ADR 0025 says failures read the same on every platform, which a system resolver cannot promise.
- **Why `iphlpapi`, when ADR 0020 allows only `kernel32` and `ntdll`.** The registry holds the servers per interface (`Tcpip\Parameters\Interfaces\{GUID}`, `NameServer` and `DhcpNameServer`), and what Windows actually asks first depends on interface metrics, VPNs and the name resolution policy table, none of which a registry walk sees. Four `ntdll` calls (`NtOpenKey`, `NtEnumerateKey`, `NtQueryValueKey`, `NtClose`) and UTF-16 parsing in `std.rt` would give a list in an order Windows does not use. `GetNetworkParams` is one call, as ADR 0020 asks of an intrinsic, and returns the list the system itself uses. It is the one function of that DLL the runtime imports.
- **IPv4 only.** `GetNetworkParams` lists IPv4 servers only. A machine whose only name servers are IPv6 has none from this call and falls back to `127.0.0.1`. That is a known gap, accepted for a call that needs no structure parsing beyond one linked list; `GetAdaptersAddresses` would close it at the cost of a far larger structure.

## Considered options

- **The system resolver (`getaddrinfo`, `DnsQuery`).** Rejected: it is three behaviours, it links the C library or `dnsapi.dll` into every program, and it parses answers outside Oska.
- **A registry walk through `ntdll`.** Rejected for the reasons above: no new DLL, but a list in the wrong order.
- **A `GetAdaptersAddresses` call.** Rejected for now: IPv6 servers, a much larger structure to walk in `std.rt`, and the same extra DLL.

## Consequences

- **Every Windows executable imports `iphlpapi.dll`.** The import list is always the whole list (ADR 0020), so a Windows program loads one more DLL at start-up, whether or not it resolves names. The import table is checked by `build_windows.rs`, which lists `GetNetworkParams` as the only function of that DLL.
- **`connect()` resolves a DNS name with `std.dns` on both backends.** Both call one function, `dns.resolve_system`, and try each address it returns in turn (`oska-run/src/resolve.rs` runs it on a nested interpreter that shares the host; `std.rt`'s `net_connect` calls it, because the toolchain check joins the `std` modules `std.rt` imports with it, as a program's are). `oska-sys` resolves no name. `localhost` is no special case: the hosts file answers it. For a test, the environment variables `OSKA_DNS_HOSTS` (the hosts file's text), `OSKA_DNS_RESOLV_CONF` and `OSKA_DNS_PORT` replace the files of the machine and port 53, on both backends.
- **`HostConnect.exchange_datagram` and `NetConnect.system_name_servers` run on both backends.** The native backend lowers them in `std.rt` through the socket and `GetNetworkParams` intrinsics it already has. `std.dns`'s message, hosts file and `resolv.conf` code is pure Oska and runs on both backends.
- **The resolver runs with the runtime's own capabilities, not the program's.** `connect()` resolves a name with the `FsRead`, `NetConnect`, `Random` and `Env` of the runtime itself, on both backends: they are not narrowed by the program's `restrict_to`, and a program that holds none of them still resolves a name, because it holds a `HostConnect` that names the host. The resolver reads the hosts file and `resolv.conf`, asks the name servers, and reads the `OSKA_DNS_*` variables; it reaches nothing else, and what it returns is a list of address texts that `connect()` then connects to under the host capability's port. Natively the four capabilities are made in `std.rt` from the word 0 by the identity intrinsics `rt_mem_as_fs_read`, `rt_mem_as_net_connect`, `rt_mem_as_random` and `rt_mem_as_env`. Like every `rt_mem_` name they are reserved for `std.rt`: user code that names one is `E0209`, and `scripts/intrinsic-guard/guard.sh` fails the build if any other `.osk` file does. A program cannot forge a capability with them.

## Amendment: adapters that are up, in metric order (2026-11-24)

Spec #228 asks for the name servers of the adapters that are up, in metric order. `GetNetworkParams` gives a system-wide IPv4 list that ignores adapter state, so a disconnected adapter's servers were asked, and no IPv6 server was seen. The original Decision rejected `GetAdaptersAddresses` for its size; the spec's rule needs it, so the Decision changes:

- **The call is `GetAdaptersAddresses` of `iphlpapi.dll`**, through the intrinsic `rt_sys_get_adapters_addresses` (family `AF_UNSPEC`, flags that skip the unicast, anycast, multicast and friendly-name lists, so only the DNS server lists are filled). `GetNetworkParams` is no longer imported; `iphlpapi.dll` is still the one extra DLL, and `GetAdaptersAddresses` its one function. The prelude method `NetConnect.system_name_servers` is unchanged. ADR 0014's import check (`build_windows.rs`) lists the new function in place of the old.
- **Only adapters that are up.** An adapter whose `OperStatus` is not `IfOperStatusUp`, and the loopback adapter, give no servers.
- **Metric order.** A server's metric is the adapter's `Ipv4Metric` for an IPv4 server and its `Ipv6Metric` for an IPv6 one; servers are listed lowest metric first, in the system's adapter order among equal metrics, each once at its lowest metric. This is the order Windows prefers adapters in; the name resolution policy table, which can send a name to another server, is still not consulted.
- **IPv6 servers are listed**, as eight groups of four hex digits, the same text on both backends. Two kinds are left out: an unspecified address, and a link-local (`fe80::/10`) or site-local (`fec0::/10`) one. A link-local server is reachable only through an interface scope, and an address literal in Oska (`exchange_datagram`, `connect`) carries none; a site-local server is the deprecated placeholder Windows lists (`fec0:0:0:ffff::1`) on an adapter with no IPv6 server. A machine whose only servers are link-local has none from this call and falls back to `127.0.0.1`.
- **Two implementations of one walk.** The interpreter's is `servers_from_adapter_addresses` in `oska-sys` (pure, unit-tested on Linux against hand-built buffers); the native backend's is `net_system_name_servers` in `std.rt`. Both read the list in the one buffer the call fills, check every link against the buffer, and end a list at a link that leaves it. `build_windows.rs` and the Windows CI run check the native one.

## Amendment: spec #228 names that the code does not use (2026-11-24)

Spec #228 says "no public DNS API" and uses three names the code spells differently. Each difference is decided here once, and the code names stay (spec #659, ticket #694). The spec's wording is superseded.

- **"No public DNS API" is superseded.** `std.dns` is a module a program can import and call (`dns.resolve_system` and the message, hosts-file and `resolv.conf` functions), and `HostConnect.exchange_datagram` and `NetConnect.system_name_servers` are public prelude methods. Why it stays public: `std.dns` is plain Oska with no authority of its own beyond the capabilities it is given, so a program that wants a record the host's resolver would not give (or a test that feeds it a hosts file) can use it; and the two methods must be public prelude methods, because `std.dns` is a module outside the prelude and calls them. What they allow is bounded: `exchange_datagram` sends only to the one host and port its `HostConnect` is confined to, and `system_name_servers` only reads the list of servers (empty off Windows). Neither widens authority.
- **`TrustConfig` and `parse_pem` are the code names, and the spec's too.** The trust configuration is `x509.TrustConfig` with `with_root_der`, `with_root_pem`, `with_roots` and `only_roots`; certificates read from text are `x509.parse_pem`. There is no `RootStore` type, and the glossary and guides never use the word.
- **`t.net_attempts()` supersedes the spec's `net_requests`.** The method of the test stand-in `Net` lists the host and port that code tried to reach. "Attempts" is what it records: the stand-in refuses every one, so none is a request that was served.
