# Certificates and the root store

`std.x509` reads X.509 certificates and decides whether a server's certificate chain is one to trust: it parses DER, builds a path from what the server sent to a root, validates it, and checks the host name. A TLS client needs exactly this. It is written in Oska, like the rest of the crypto ([ADR 0012](../adr/0012-tls-git-and-crypto-are-written-in-oska.md)), and it is pure: it reads no clock and no file, so you pass the time in. Every program on this page is checked by `oskac` when the documentation is tested, and the output shown is what `oskac run` prints.

The code is hand-written and has not been audited by anyone outside the project. It is held by crafted chains for each way a chain can fail, run natively (a part of them on both backends), and by every real root certificate of Mozilla's store, run natively on every platform.

## Verifying a server's chain

A certificate comes from outside the program, so `Certificate.parse` takes untrusted bytes and needs no trust assertion: the parser is strict DER and returns a trusted `Certificate`. `x509.verify_server(store, leaf, others, host, now)` takes the server's certificate, the other certificates it sent (in any order, with extras), the host name your program chose, and the time in seconds since 1970. It returns the path it found, the leaf first, or an `X509Error`.

```oska
use std.x509

fn check(der: Untrusted<Bytes>, now: Int) -> Result<Int, x509.X509Error> {
    let leaf = x509.Certificate.parse(der)?
    let chain = x509.verify_server(x509.TrustConfig.default(), leaf, [], "oskalang.dev", now)?
    Ok(chain.len())
}

fn main(io: Stdout) {
    match check(Bytes.new(), 1750000000) {
        Ok(count) => {
            let _ = io.println("trusted, {count} certificates")
        }
        Err(error) => {
            let _ = io.println("refused: {error}")
        }
    }
}
```

```console cmd=run
refused: the certificate is malformed
```

The host is trusted text: it is the name your program chose to connect to, and an untrusted name is `E0300`. (`std.tls` takes it from the host capability a connection is confined to.) The name is checked first, so a certificate for another host is `HostMismatch` whatever its chain.

## What is checked

For each path from the server's certificate to a root, `verify_server` checks:

- **Validity.** Every certificate is valid at `now`: `NotYetValid` or `Expired`. The validity of the root itself is not checked; the trust configuration drops a root when Mozilla does.
- **Signatures.** ECDSA on P-256 and P-384, RSA PKCS#1 v1.5 and PSS, and Ed25519, with SHA-256, SHA-384 or SHA-512. A signature by MD5 or SHA-1, or by a key it cannot read (an RSA key under 2048 bits), is `UnsupportedAlgorithm`. A signature that does not verify is `BadSignature`.
- **Basic constraints and key usage.** Each issuer must be a CA, with `keyCertSign` if it has a key usage (`NotCa`), within its `pathLenConstraint` (`PathLengthExceeded`). The server's certificate must allow `digitalSignature` if it has a key usage (`KeyUsage`).
- **Extended key usage.** The server's certificate must have the extension and name `serverAuth` or `anyExtendedKeyUsage`; a CA on the path that has the extension must allow it too (`ExtendedKeyUsage`).
- **Name constraints** on the DNS names and IP addresses of every certificate below the constraining CA, the server's certificate and the CAs between: `NameConstraint`. Constraints on other kinds of name are ignored, as no such name is checked.
- **Work bounds.** A path is at most 8 certificates before the root, and one validation makes at most 64 signature checks, so a hostile set of certificates cannot make it run long: `LimitExceeded`. An issuer is chosen by name and, when the certificate's authority key identifier and the issuer's subject key identifier are both present, by that, which also skips the wrong candidates without a signature check.
- **Critical extensions.** A certificate with a critical extension the module does not understand is refused when it is parsed: `UnsupportedCriticalExtension`.
- **The host name**, as RFC 9525 says: only the `dNSName` and `iPAddress` subject alternative names count, never the common name. A wildcard is only the whole leftmost label, stands for one label, and needs two more labels after it. `HostMismatch` otherwise.
- **Mozilla's "distrust after" date** for the root: a server certificate that became valid after it is `DistrustedRoot`.

When several paths exist (an intermediate that was cross-signed, a server that sent extras), the first valid one is returned. When none is valid, the error is the first reason a path was refused, or `UnknownIssuer` when none led to a root.

`X509Error`'s kinds are stable, and each has a message. `Certificate.matches_host`, `Certificate.signed_by(issuer)`, `Certificate.public_key()` (an `x509.PublicKey`: an `Ecdsa`, `Rsa` or `Ed25519` key, for checking a TLS handshake signature) and the other accessors are in the API reference.

## The roots

`x509.TrustConfig.default()` is a pinned copy of the roots Mozilla trusts for TLS server authentication, compiled into the module, so verification gives the same answer on every platform with no system store. `with_roots(certificates)` adds roots, `only_roots(certificates)` replaces them, and `x509.parse_pem(text)` and `x509.parse_der(bytes)` read certificates from untrusted input. To trust a root of your own (a corporate or test CA) from bytes or text, add it so that the trust is checked:

```oska fragment
fn with_corporate_ca(pinned_ca_pem: String) -> Result<x509.TrustConfig, x509.X509Error> {
    x509.TrustConfig.default().with_root_pem(pinned_ca_pem)
}
```

To trust only roots you choose, use `x509.TrustConfig.only_roots(...)`. Which roots to trust is a structural position: `with_root_der` and `with_root_pem` take trusted bytes and text, so a root read from a file needs your own `.assume_trusted()`, which `oskac audit` lists. `with_roots` and `only_roots` take parsed certificates, and the checker does not track trust on a `Certificate` (only on text and bytes), so they are not an audit site: use them for certificates the program itself vouches for, and `with_root_der` and `with_root_pem` for anything read from outside. `with_root_distrusting_after(der, time)` adds a root with Mozilla's kind of restriction.

## Writing a certificate signing request

`std.x509_csr` writes the request an ACME client sends to finalize an order (RFC 8555 section 7.4). `x509_csr.create(key, names)` takes a P-256 private key as a `Secret<Bytes>` (32 bytes) and the names to ask for, and gives the request's DER bytes, signed with ECDSA and SHA-256. A name is a DNS name (a first label of `*` is allowed) or an IPv4 or IPv6 address. Anything else, no names, more than 100 names, or a key that is not a private key is an `x509_csr.CsrError`, and nothing is signed. `create_with_common_name(key, common_name, names)` also sets the subject's common name. The signature uses the deterministic nonce of `std.ecdsa.sign`, so one key and one list of names give one request on every backend. `x509_csr.parse(der)` reads a request from untrusted bytes and checks its signature.

```oska
use std.base64url
use std.x509_csr

fn main(io: Stdout) -> Result<(), IoError> {
    let key = Secret.new(Bytes.from_hex("c9afa9d845ba75166b5c215767b1d6934e50c3db36e89b127b8a622b120f6721").unwrap_or(Bytes.new()))
    match x509_csr.create(key, ["example.com", "www.example.com"]) {
        Ok(der) => {
            // ACME's finalize call sends this text.
            let body = base64url.encode(der)
            let count = body.len()
            io.println("{count} characters")
        }
        Err(e) => io.println(e.to_string())
    }
}
```

```console cmd=run
336 characters
```

The module has two `expose()` sites, both of public values: the key's public point and the signature are written into the request. The private key is never exposed. The code is hand-written and has not been audited.

## Updating the roots

The roots are in `crates/oska-check/src/std/x509_roots.osk`, generated by `scripts/x509-roots/generate.py` from NSS's `lib/ckfw/builtins/certdata.txt` at a release tag of the NSS source (`NSS_3_134_RTM` today), the file Mozilla publishes its store as. The script keeps the roots whose trust for server authentication is `CKT_NSS_TRUSTED_DELEGATOR`, with each one's subject, key, subject key identifier and `CKA_NSS_SERVER_DISTRUST_AFTER` date, and uses only the Python standard library. The generated module names the release tag and the `NSS_BUILTINS_LIBRARY_VERSION` of that release (`x509_roots.nss_release()`) and the SHA-256 of the `certdata.txt` it came from, so the same input gives the same bytes. To update, pick the release tag NSS ships with the Firefox release you follow, and run:

```text
TAG=NSS_3_134_RTM
BASE=https://raw.githubusercontent.com/nss-dev/nss/$TAG/lib/ckfw/builtins
curl -fsS $BASE/certdata.txt -o /tmp/certdata.txt
curl -fsS $BASE/nssckbi.h | grep NSS_BUILTINS_LIBRARY_VERSION
python3 -I scripts/x509-roots/generate.py /tmp/certdata.txt $TAG 2.94 > crates/oska-check/src/std/x509_roots.osk
python3 -I scripts/x509-roots/vectors.py /tmp/certdata.txt > crates/oskac/tests/vectors/x509_mozilla_roots.osk
bash scripts/x509-roots/verify.sh
```

(`2.94` is the `NSS_BUILTINS_LIBRARY_VERSION` the third command prints.) `verify.sh` fetches the tag again and checks that the committed module is exactly what the generator makes from it. It needs the network, so `scripts/check.sh` does not run it; `scripts/x509-roots/test.sh`, which `check.sh` does run, tests the generator on a cut of `certdata.txt` and that the committed module names its release and its source's digest. Run `verify.sh` when the roots change and as the root store step of the release runbook (`docs/agents/release.md`).

The second script (it needs the Python `cryptography` package) rewrites the file of real roots that the tests run, so the tests check the new store. Then run `scripts/check.sh` and add a line to `CHANGELOG.md`. The crafted chains, `crates/oskac/tests/vectors/x509_chains.osk` (every chain, natively) and `crates/oskac/tests/fixtures/x509_cases.osk` (the cheap cases, on both backends), are made by `scripts/x509-roots/chains.py full` and `chains.py quick`; they hold their own test roots and do not change when the store does.

## What to remember

- Parse with `x509.parse_der` or `Certificate.parse` (untrusted bytes in, a trusted certificate out), then `verify_server` with the host you chose and the time you read.
- The checks are RFC 5280 and RFC 9525 as far as TLS needs. Names are compared as DER bytes, and the root's own validity is not checked.
- The default trust configuration is Mozilla's roots, pinned in the module. Add roots from trusted bytes with `with_root_der` and `with_root_pem`; replace them with `only_roots`.
- The API is in the API reference on the site, and `oskac doc std.x509` prints it.
