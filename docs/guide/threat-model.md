# Threat model

What Oska guarantees, where each guarantee stops, how a release reaches you, and what this site trusts. Read it before you rely on an authority report: the report is only as strong as the boundary on this page. Oska is pre-alpha, so a gap between this page and the toolchain is a bug: report it as the [security policy](../../SECURITY.md) says.

## What Oska guarantees

- **No ambient authority.** A program can read a file, read the clock or the environment, or draw a random number only through a capability, and `main` is handed exactly the capabilities its signature names. Every other function reaches only what its parameters carry, and `oskac check` prints that authority for each function. See [capabilities](capabilities.md) and [ADR 0002](../adr/0002-capabilities-are-the-effect-system.md).
- **Untrusted text cannot steer a sink.** Text from outside the program is untrusted, the flag survives every text operation, and the checker refuses untrusted text where trusted text is required (`E0300`). The only way across is `.assume_trusted()`, normally inside a validator. See [untrusted data](untrusted-data.md) and [ADR 0006](../adr/0006-trust-is-a-flag-on-text.md).
- **Secrets stay hidden.** A `Secret<String>` cannot be printed, interpolated or compared with `==`, and `dbg` shows it as `<redacted>`. The only way to read it is `.expose()`. See [secrets](untrusted-data.md#secrets).
- **File access is confined.** A directory capability reaches only what is beneath its root. Each path component is opened beneath the handle of the one before, and symlinks (on Windows, every reparse point) and hard-linked files are refused, so a path swapped while the program runs cannot escape. Another process can still move a directory the program holds out of the root; the capability follows that one directory and reaches nothing new, so this is a risk to availability and integrity, not an escape ([ADR 0009](../adr/0009-oska-sys-is-the-only-crate-with-unsafe.md)). See [ADR 0008](../adr/0008-file-access-goes-through-confined-capabilities.md).
- **One behaviour on every platform.** The same program prints the same bytes and exits with the same codes on Linux, macOS and Windows, on both backends, with the same confinement everywhere. A program the native backend cannot compile yet is refused (`E0390`), never run differently ([ADR 0014](../adr/0014-every-supported-platform-builds-and-runs-natively.md)).

## Where the guarantees stop

- **The checker is the gate.** Authority and trust are checked before a program runs, and both backends run only a program the checker accepted. A checker bug that accepts a program it should refuse breaks the guarantees for that program on every backend.
- **`oska-sys` is the only Rust crate with `unsafe`.** It opens files and directories beneath a handle for the interpreter. Every other crate forbids `unsafe`, and `scripts/check.sh` proves it by compiling with `unsafe_code` forbidden ([ADR 0009](../adr/0009-oska-sys-is-the-only-crate-with-unsafe.md)). A bug in `oska-sys` can break confinement under the interpreter.
- **System calls exist only in `std.rt`.** A native executable reaches the operating system through intrinsics that only the toolchain's own `std.rt` module may use. The checker refuses them anywhere else, in your code and in a dependency's (`E0209`), and `scripts/check.sh` checks the same ([ADR 0013](../adr/0013-system-calls-only-in-std-rt.md)). A bug in `std.rt` can break confinement in native code.
- **The two backends enforce at run time with different code.** The interpreter confines files through `oska-sys`. A native executable confines them with its own system calls in `std.rt`, and its memory safety rests on the native backend being correct. The differential suite runs every program on both and requires the same output on each platform's CI runner, but it tests behaviour, it does not prove it. A fault in native code is reported as `E0392`, a backend bug, not a program error.
- **Audit sites are where you weaken a guarantee on purpose.** Every `.assume_trusted()` and every `.expose()` is listed by `oskac check` with its location, and `oskac check --baseline` fails when one is added. The checker trusts what your validator vouches for: a weak validator lets bad text through, and the audit list is where a reviewer looks for it. See [audit sites](untrusted-data.md#audit-sites).
- **A capability you hand over is used as its holder likes.** A dependency that receives `Fs` can use all of it. Attenuate first, and read the authority report of the functions you call.
- **Not covered:** the operating system, the hardware, other processes on the machine (beyond the confined walk), side channels such as timing (apart from `constant_time_eq` on a secret), and anything the docs say is not built yet, such as `Net` and `Spawn` ([what works today](what-works-today.md)).

## The supply chain

- **One signing key.** Every release's `SHA256SUMS` is signed with one ed25519 SSH key, fingerprint `SHA256:PjwTDycs560g1ktWC/gdznamSkzm4xH+OAdfntNaW4o`. The private half is a secret of the repository's `release` environment, which admits only `v*` tags and `main` (`main` so that the signed release index can be re-signed on a schedule), and only two jobs may read it. GitHub cannot limit an environment to one workflow, so that limit is held by `scripts/release/test.sh` and by `main` changing only through reviewed pull requests, not by GitHub.
- **Build provenance, from v0.7.0.** Each release's binaries and `SHA256SUMS` carry a GitHub artifact attestation, which `gh attestation verify <file> -R aparsons/oska` checks. It proves that GitHub's hosted builder, running the release workflow of this repository, built the file from a given commit. It does not prove the commit is free of bugs or malicious code, that the workflow was reviewed, or that the build can be reproduced; and it trusts GitHub's builder and signing service. It adds to the signature and does not replace it: the installers check only the signature, and `SHA256SUMS.intoto.jsonl`, the attestation of the list itself, is the one file the list does not name. Releases before v0.7.0 have none.
- **The installers verify before they install.** They check the signature on `SHA256SUMS` against the key built into them, that the signed file names the release they asked for, the binary's checksum, and the version it reports. They take the latest release from a signed release index, refuse an older index than the one they last accepted, and download only over `https://` (a `file://` site, for a local mirror, is the one other source they accept). See [install](install.md).
- **The installer and the key come from the same site.** `install.sh`, `install.ps1` and `oska-release.pub` are all served by oskalang.dev. Whoever controls the site could serve another installer with another key. To check the key through a second channel, compare its fingerprint with the one in this repository's `SECURITY.md` and in every GitHub release's notes, then [verify a release by hand](install.md#verify-a-release-by-hand).
- **`latest.json` is unsigned.** It is informational. The installers do not trust it to choose a release while a signed index is published.
- **Dependencies are git URLs.** A package's dependencies are fetched from the URLs in its `oska.toml` and checked by the same checker with the same rules ([ADR 0010](../adr/0010-packages-are-git-urls-resolved-by-minimal-version-selection.md)). They get only the authority you pass them.

## What this site trusts

- **GitHub Pages serves it.** The site is static, built from `main` by `site/build.osk` and deployed by GitHub. A compromise of GitHub, of the repository, or of its Pages deployment can change any page, the installers included.
- **No third-party origin.** Pages load styles, scripts and images only from the site itself, and use the system's fonts. Each page's Content Security Policy allows nothing else, and no script runs but the site's own search.
- **No response headers.** GitHub Pages cannot set custom headers, and a policy in a `<meta>` element cannot use `frame-ancestors`, so the site cannot forbid framing. It has no forms or sign-in, which limits what framing could do.
- **HTTPS is enforced by the domain.** `.dev` is on the browsers' HSTS preload list, so browsers use HTTPS for oskalang.dev without a header from the site.
