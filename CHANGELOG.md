# Changelog

Every release's notes, newest first. A change users can see adds its line under "Unreleased" in the pull request that makes it.

## Unreleased

v0.7.0 ships two Linux builds of `oskac`, so it runs on any Linux, and publishes a container image ([ADR 0022](docs/adr/0022-linux-oskac-ships-as-glibc-and-musl-builds.md)). These are the changes you can see:

- **`std.x509_csr`: write and read a certificate signing request.** `x509_csr.create(key, names)` takes a `Secret` P-256 private key and a list of DNS names (a leading `*.` is allowed) and IP addresses, and gives the DER request, signed with ECDSA and SHA-256 and the same on every backend; `create_with_common_name` adds a subject common name. A name that is neither a valid DNS name nor an IP address, no names, more than 100, or a key out of range is a `CsrError`, and nothing is signed. `x509_csr.parse(der)` reads a request from untrusted bytes and checks its signature. The module's two `expose()` sites are of public values (the public point and the signature). Part of the ACME client (#824).
- **`std.http`: `POST` with a body, and `http.send`.** `http.Request.post(path, content_type, body)` makes a POST, and `http.post(host, request, tls_config, random, clock)` sends it with `Content-Type` and `Content-Length` and returns the same `Response`, whose headers (`Replay-Nonce`, `Location`, `Retry-After`, `Link`) `header(name)` reads in any case, as untrusted text. `http.send` runs a request of either method. A request body over `http.MAX_BODY`, more than `http.MAX_FIELDS` request headers, a request head over `http.MAX_HEAD` bytes, an empty content type, or a `Content-Type` header set on a POST is `InvalidRequest` before anything connects. `http.get` now refuses a POST request (`InvalidRequest`), and `Content-Type` is still free to set on a GET. Nothing changes for existing `http.get` callers.
- **`std.base64url`: unpadded base64url and the raw ES256 signature.** `base64url.encode(bytes)` writes the URL-safe alphabet with no `=`, and `base64url.decode(text)` is strict: padding, the standard alphabet's `+` and `/`, stray characters, an impossible length and non-zero unused bits each give their own `Base64UrlError`. `base64url.es256_raw(r, s)` and `base64url.es256_raw_from_der(der)` give the 64-byte `R || S` signature that RFC 7518 section 3.4 requires, each half padded to 32 bytes. It is written in Oska and runs the same on both backends. Part of the ACME client (#824).
- **`std.ecdsa.sign`: ECDSA P-256 signing over a `Secret` key.** `ecdsa.sign(key, digest)` takes a 32-byte `Secret<Bytes>` private key and the digest of a message (any length, as `verify` takes it) and gives the 64-byte `r || s` signature as a `Secret<Bytes>` (the form ES256 uses), or `None` for a key outside 1 to n - 1; `verify` accepts it. The nonce is the deterministic one of RFC 6979 with HMAC-SHA-256, so the same key and digest give the same signature, and there is no parameter to pass, repeat or bias a nonce. The arithmetic is constant-time over the key and the nonce on both backends. Expose the signature where you need it in the clear: `oskac audit` lists that call. `std.p256`'s curve arithmetic moved to the internal module `std.p256_ops`; `std.p256` behaves as before.
- **`Map` and `Entry` are in the prelude.** A program writes `Map.new()`, `Map.of(...)`, `Map.with_max_entries(n)` and `Entry(key: k, value: v)` with no `use`, as it writes `List`. `use std.map` still works, and so does `map.Map`. Like any prelude name, `Map` and `Entry` cannot be declared by a program: a `struct Map` or `struct Entry` is now `E0202`, so rename your own type. The map is still Oska code that both backends run, so steps are charged the same.
- **`Map.of(entries)`, a map from a list of entries, and a guide page.** `Map.of([Entry(key: "a", value: 1), ...])` puts the entries in order, as repeated `put` calls do: a key that occurs again keeps its first place and takes the later value. There is no `{"a": 1}` literal yet, because braces open a block and the form is still an open language decision (#591). The new [maps guide](docs/guide/maps.md) shows the order rules. `oskac fmt` has no map form to print until #662 lands.
- **`Map<K, V>`, a table that keeps insertion order.** `Map.new()` makes an empty map and `put`, `get`, `remove`, `contains_key`, `len`, `is_empty`, `entries`, `keys` and `values` use it. It is a value, copied on write, so a method that changes it needs a `var`. `entries`, `keys` and `values` give the entries in the order the keys were first put; `put` on a key the map holds keeps its place, and `remove` then `put` moves it to the end. `get` of a missing key is `None`, and `remove` gives the removed value or `None`. Two maps are equal when they hold the same entries in the same order. A key type needs `Eq` and `Hash` (the core types and derived `Hash` from #600). It is written in Oska and runs the same on the interpreter and on native builds. A type that is not a key (no `Eq` or no `Hash`) is `E0266` where a `Map` method is called; a `Secret` key is `E0351` and `E0354`. A struct needs a written `impl Eq` to be a key, because `Eq` has no derived form yet. A `Float` key is refused once `Float` exists. A map holds at most 4,194,304 entries (`Map.with_max_entries(n)` sets a lower limit): a `put` of a new key past it panics with `P0044`. A lookup looks at no more than 64 slots, and a `put` that cannot place its key that close to where it hashes rebuilds the table under the next of two fixed mixes of the key's hash; when all three fail the map panics with `P0045`, so keys picked to collide cost a bounded number of steps or a panic, never an unbounded scan. Each probe is a step under `--max-steps`, the same on both backends. `put` on a key the map holds and `remove` no longer copy the whole table. An internal checker crash on `==` of a generic struct that holds a `List` of its type parameter is fixed.
- **`std.json`: `Value.as_map()`, an object as a `Map`.** After `use std.json`, `value.as_map()` gives `Ok` of a `Map<Untrusted<String>, Value>` for an object, with its members in the order they were written, so you can look a member up with `get`. A key that occurs twice is an `Error` with the reason `duplicate key`, as `parse` reports it; its offset is the place of the later member in the object, not a byte offset, because a `Value` no longer knows the text. A value that is not an object is an `Error` with the reason `not an object`. Keys stay untrusted. `Value.Object(List<Member>)`, `parse` and `encode` are unchanged.
- **`Map<K, V>`, a table that keeps insertion order.** `Map.new()` makes an empty map and `put`, `get`, `remove`, `contains_key`, `len`, `is_empty`, `entries`, `keys` and `values` use it. It is a value, copied on write, so a method that changes it needs a `var`. `entries`, `keys` and `values` give the entries in the order the keys were first put; `put` on a key the map holds keeps its place, and `remove` then `put` moves it to the end. `get` of a missing key is `None`, and `remove` gives the removed value or `None`. Two maps are equal when they hold the same entries in the same order. A key type needs `Eq` and `Hash` (the core types and derived `Hash` from #600). It is written in Oska and runs the same on the interpreter and on native builds. A type that is not a key (no `Eq` or no `Hash`) is `E0266` where a `Map` method is called; a `Secret` key is `E0351` and `E0354`. A struct needs a written `impl Eq` to be a key, because `Eq` has no derived form yet. A `Float` key is refused once `Float` exists. The flood defence and the entry limit of ADR 0028 are not in yet. An internal checker crash on `==` of a generic struct that holds a `List` of its type parameter is fixed.
- **The DNS test variables work in debug builds only.** `OSKA_DNS_HOSTS`, `OSKA_DNS_RESOLV_CONF` and `OSKA_DNS_PORT`, which redirect `connect()`'s name lookups, are ignored by release builds of `oskac` and by the executables they produce, on both backends, so whoever starts a process cannot redirect its lookups. Nothing to change in a program; tests that use them need a debug `oskac`.
- **`TlsConfig.with_rekey_after` is removed (breaking).** A program that calls it no longer checks. The client always sends its `KeyUpdate` after 2^24 records written and fails the stream past 2^24.5 records read under one key, and no setting changes either; delete the call.
- **`std.http`: `with_max_body` has a ceiling.** A maximum body above `http.MAX_BODY` (16 MiB) is now `InvalidRequest` from `http.get`, before it connects, where any value was accepted. Lower the setting to 16777216 or less.
- **`std.p256` refuses a scalar out of range (breaking).** `p256.public_key` and `p256.shared_secret` now return `None` for a scalar of zero, of the group order n, or above it, where they gave zeros or the result mod n. Pick scalars from 1 to n - 1 (`Random.secure_bytes(32)` fails the range about once in 2^32 draws, so retry on `None`); `std.tls` already treats `None` as a failed key share.
- **Network access goes through host capabilities.** `NetConnect.connect` is gone: `net.restrict_to("oskalang.dev", 443)`, on `Net` or `NetConnect`, gives a `HostConnect` for that one host and port, and `.connect()` on it takes no destination. The host is trusted text, so untrusted text there is `E0300`; validate it and write `.assume_trusted()` to reach a host chosen at run time. `net.listen_only().restrict_to_loopback(port)` gives a `LoopbackListen` for a local test server (port 0 picks a free one). Every narrowing is in the authority report, and package authority orders `Net` > `NetConnect` > `HostConnect`. `main` taking `Net`, `NetConnect` or `NetListen` now runs instead of `E0370`. In a plain `test`, `t.net` fails every connect with one stable `IoError` and `t.net_attempts()` lists where code tried to go; it is the real network under `--integration`. To migrate, replace `net.connect(host, port)` with `net.restrict_to(host, port).connect()`. See [ADR 0025](docs/adr/0025-network-access-goes-through-host-narrowed-capabilities.md).
- **`LoopbackListen` listens on `127.0.0.1` and `::1`.** `restrict_to_loopback(port)` now binds both loopback addresses at one port and `accept` takes a connection on either, on both backends; a machine without an IPv6 loopback still listens on `127.0.0.1`. Nothing to change in a program.
- **`connect()` resolves names with `std.dns`, on both backends.** `HostConnect.connect()` no longer calls the operating system's resolver: `localhost`, a name in the hosts file and a name from `resolv.conf`'s name servers all resolve through the Oska stub resolver, and a wrong id, a wrong question or a bad compression pointer in an answer makes `connect()` fail with an `IoError` (`malformed answer`, `answer does not match the query`, `timed out`, `host not found`). A name only the system's resolver knew (an `nsswitch` or mDNS name) now fails with `host not found`: put it in the hosts file.
- **Native programs connect and listen.** `oskac run` and `oskac build` compile `HostConnect.connect`, `Connection.send`, `receive`, `send_bytes`, `receive_bytes`, `close` and `host`, and `LoopbackListen.accept` and `port`, on Linux, macOS and Windows, with the same output as `--interpret`: every failure (`connection refused`, `network unreachable`, `timed out`, a bad host or port) is worded from Oska's table, never the system's. A native plain test refuses `t.net` as the interpreter does. A host that is not an IP address is resolved with `std.dns`, as the interpreter does. A connect waits at most 10 seconds for each address and 30 seconds in all, on both backends. `t.net_attempts()` still runs on the interpreter only.
- **`std.tls`: a TLS 1.3 client written in Oska.** After `use std.tls`, `tls.connect(host, config, random, clock)` takes a `HostConnect`, connects, runs the handshake and returns a `TlsStream` (`send`, `receive`, `close`) or a `TlsError` with a stable kind (`Certificate`, `AlertReceived`, `Protocol`, `Unsupported`, `Truncated`, `Io`). The name sent in the server name indication and checked in the certificate is always `host.name()`, so no code path verifies one name and connects to another. It offers TLS 1.3 only, `TLS_CHACHA20_POLY1305_SHA256` then `TLS_AES_128_GCM_SHA256`, x25519 (and secp256r1 after a `HelloRetryRequest`), and checks the chain with `std.x509` against `x509.TrustConfig.default()` or the roots in `tls.TlsConfig.default().with_trust(...)`, the CertificateVerify signature (Ed25519, ECDSA P-256 and P-384, RSA-PSS) and the Finished message in constant time, and every record's tag before its plaintext is used. `TlsError.Io` prints the reason (`i/o error: connection refused`, `i/o error: timed out`). The client sends a `KeyUpdate` after 2^24 records written (under the AES-128-GCM limit of RFC 8446 section 5.5) and fails the stream when the server sends more than 2^24.5 records under one key (the limit of section 5.5); a program cannot change either number. It sends the alert RFC 8446 names before it fails, reports a received alert by name, handles `KeyUpdate`, drops `NewSessionTicket`, bounds record, handshake and certificate sizes, and reports a stream cut off without `close_notify` as `Truncated`. What `receive` returns is `Untrusted<Bytes>`. The handshake and record layer are also a pure engine, `tls.Engine` (no capability: bytes, 64 bytes of secure randomness and the time in; bytes to send and events out), public for tests and other transports. `std.tls` has no `.assume_trusted()` and exposes a secret only at the key share, the client random and session ID, a record's nonce, the ciphertext to send and the plaintext after its tag verifies, a list a test holds. It is hand-written and unaudited, and is tested against a loopback test server written in Oska with a test CA (every suite and group, `HelloRetryRequest`, `KeyUpdate`, and each way a server can misbehave) on both backends, and against recorded handshakes with openssl, replayed and mutated.
- **`std.http`: an HTTPS GET client written in Oska.** After `use std.http`, `http.get(host, http.Request.get("/path"), tls_config, random, clock)` takes a `HostConnect`, fetches over `std.tls` and returns a `Response` (`status`, `headers`, `header(name)`, and `body` as `Untrusted<Bytes>`, with `Untrusted<String>` header names and values) or an `HttpError` (`Tls`, `Malformed`, `TooLarge`, `InvalidRequest`). It follows no redirect (a `3xx` is returned as it is), sends `Host` from the capability, `Connection: close` and `Accept-Encoding: identity`, and refuses before connecting a path that does not start with `/` or holds a control character, space or `#`, and a header value with CR, LF or NUL. The body is limited to 16 MiB (`with_max_body`), the head to 64 KiB and 100 fields. It reads `Content-Length`, chunked and until-close bodies (the last only after `close_notify`) and rejects a response with both lengths, different lengths, obsolete line folding, a bare line feed or an overflowing chunk size. `http.Reader`, the pure parser, is public for tests. A header value may hold no control character (tab is allowed), and the client sets `Host`, `Connection`, `Accept-Encoding`, and refuses a program's `Content-Length`, `Transfer-Encoding`, `Upgrade`, `Expect` and `TE`; `User-Agent` is `oska` unless the program sets one; a `204` and a `304` have no body; `101 Switching Protocols` is `Malformed` and other `1xx` responses are skipped. ALPN `http/1.1` replaces any protocol list in the `TlsConfig`. A connection waits at most 60 s for the server's next bytes (it was 30 s), on both backends. Tested against a loopback server written in Oska on every framing and hostile response.
- **`std.dns`, a stub resolver written in Oska.** `use std.dns`, then `dns.resolve(config, dns.NetExchange.new(net, random), "example.com")` gives a host's addresses (IPv6 first, then IPv4) the same way on every platform: it reads the hosts file and `resolv.conf` (`dns.load_config(fs, net)`), asks each name server over UDP, and asks again over TCP when an answer is truncated. Every answer is untrusted and checked before use, and a failure reads `host not found`, `timed out` or `name server unreachable` whatever the operating system. The message and file parsers (`build_query`, `parse_response`, `parse_hosts`, `parse_resolv_conf`, `parse_ip`) are pure Oska and run natively on all five platforms. Two methods are new and run on the interpreter only for now: `HostConnect.exchange_datagram(message)` (one UDP datagram out, one back) and `NetConnect.system_name_servers()` (Windows' DNS servers, from `GetNetworkParams`; an empty list elsewhere). A Windows executable now imports `iphlpapi.dll` as well. `connect()` does not use `std.dns` yet (tracked in a follow-up issue): the interpreter resolves names with the operating system's resolver, and the native backend resolves only IP addresses and `localhost`. See [ADR 0026](docs/adr/0026-name-resolution-is-an-oska-stub-resolver-and-windows-asks-iphlpapi-for-its-servers.md).
- **`Float`: literals, arithmetic and `math.fma`.** `1.5`, `2e-3` and `1_000.25` are `Float` literals, IEEE 754 binary64. `+ - * /`, unary `-`, `==`, `!=`, `<`, `<=`, `>` and `>=` work on two `Float`s, `x.sqrt()` is the correctly rounded square root, and after `use std.math`, `math.fma(a, b, c)` is `a * b + c` rounded once. Results are pinned to the bit and the same on the interpreter and natively on x86_64 and aarch64: round to nearest, ties to even, one canonical NaN (`0x7ff8000000000000`), and no fusing of `a * b + c`. `Float.to_bits()` and `Float.from_bits(bits)` give and take the 64 bits. There is no implicit `Int` to `Float` conversion and no `%` on a `Float`, a literal that rounds to infinity is `E0222`, and a `Float` has no text form yet (it cannot be interpolated); conversions and text follow. See [ADR 0027](docs/adr/0027-float-results-are-pinned-by-the-spec-on-every-platform.md).
- **`Float`: checker rules and error codes.** `E0237` refuses an integer where a `Float` is required, as in `x + 1` with `x: Float`: write `1.0`, or convert a value with `to_float()` (there is no implicit conversion). `Secret<Float>` is refused with `E0357` in a type, a field or `Secret.new(1.5)`, because float arithmetic is not constant-time on common hardware; keep a secret as a secret integer or `Secret<Bytes>`. A `Float` literal that rounds to infinity stays `E0222`, the code of every literal out of range. The runtime codes `P0047` (a NaN where a number is needed) and `P0048` (a statistic of an empty list) are reserved for the functions that follow; `oskac explain` shows them.
- **`Float` conversions and text.** `x.to_int()` truncates toward zero and panics (`P0046`) on NaN, an infinity or a value `Int` cannot hold. `n.to_float()` refuses an `Int` beyond 2^53 (`P0049`); name the rounding with `n.to_float_rounded()`, nearest with ties to even. A `Float` has a text form now: `x.to_string()`, `"{x}"` and `dbg` print the shortest digits that parse back (`1.5`, `100.0`, `0.00001`, `1e16`, `1.5e-7`, `NaN`, `inf`). `x.fmt(digits)` prints from 0 to 340 fixed decimals of the exact value, a tie going to the even digit (`P0050` for any other count). `"1.5e3".parse_float()` is correctly rounded and gives `None` for `NaN`, `inf`, a leading `+`, a number beyond `Float` such as `1e999`, spaces and any text over 400 characters; `parse_float_lenient()` is the opt-in that takes `+`, `nan`, `inf` and up to 65536 characters. `x.total_cmp(y)` orders every pair, NaN last, so it sorts, and `x.approx_eq(y, relative, absolute)` compares within a tolerance. The text is written in Oska on the native backend and matches the interpreter on every platform.
- **`std.math` integer helpers.** After `use std.math`, `math.gcd(a, b)`, `math.isqrt(n)`, `math.pow(base, exp)`, `math.floor_div(a, b)` and `math.rem_euclid(a, b)` work on `Int`. A call that breaks a precondition (a negative `gcd` or `isqrt` argument, a negative `pow` exponent, a zero divisor) stops with `P0006`; a `pow` or `floor_div` result that does not fit an `Int` stops with `P0001` and never wraps. Each loop counts steps, so `--max-steps` stops them as it stops any Oska loop.
- **`let k: Secret<Float> = Secret.new(1.5)` reports one `E0357`, and `rem_euclid(Int.MIN, -1)` is documented.** The checker named the `Secret<Float>` annotation and the `Secret.new` call for one mistake; it now reports the annotation only. `math.rem_euclid(Int.MIN, -1)` is 0 on both backends, where `math.floor_div(Int.MIN, -1)` stops with `P0001`. The debugging guide lists `P0046`, `P0049` and `P0050`.
- **`std.math` float functions.** After `use std.math`, `math.abs`, `math.floor`, `math.ceil` and `math.round_half_even` are exact, and `math.hypot`, `math.exp`, `math.ln`, `math.sin`, `math.cos`, `math.atan2` and `math.powf` are within 1 ulp of the exact result (the plain names are the fast tier of ADR 0027; correctly rounded `_exact` versions follow). Each is one fdlibm-style algorithm written in Oska, so the bits are the same on every platform and on both backends, and each call and loop counts steps under `--max-steps`. `math.pow` stays the `Int` function; the `Float` one is `math.powf`. `math.sin` and `math.cos` of a finite number above 1647098 in size stop with `P0006`; an infinity gives NaN.
- **`std.math` correctly rounded float functions.** After `use std.math`, `math.hypot_exact`, `math.exp_exact`, `math.ln_exact`, `math.sin_exact`, `math.cos_exact`, `math.atan2_exact` and `math.powf_exact` return the double nearest the true value for every input, a tie going to the even one (the exact tier of ADR 0027; the plain names stay the fast, within 1 ulp, tier, and the two differ at most in the last bit: `math.exp(1.0)` is 2.7182818284590455, `math.exp_exact(1.0)` is `e`). Each has the special cases of its fast version, and `sin_exact` and `cos_exact` stop with `P0006` above 1647098 in size as `sin` and `cos` do. Each is written in Oska with a fast path in double-double arithmetic that is right for all but about one input in 100000, and a slow path (256-bit fixed point, or exact integers for `hypot`) for the rest, so the bits are the same on every platform and on both backends, and each call and loop counts steps under `--max-steps`. The exact tier takes about 1.3 to 25 times as long as the fast tier natively (`exp_exact` 480 ns a call against 46, `ln_exact` 1270 against 51, `powf_exact` 2470 against 1940); each function's two paths and the error proof of each are in its entry of the `std.math` reference.
- **Guide: [Floats and std.math](docs/guide/floats.md), and `Float` in the Lean model.** The page shows the pinned rules of ADR 0027 with one worked program that the documentation tests run. The Lean model in `formal/lean/OskaFormal/Float/` checks the same arithmetic vectors as `float_arith.rs`, the conversions and the canonical NaN. Nothing to change in a program.
- **`Hash` for the core key types.** Integers, `Bool`, `String`, `Path` and `Bytes` are `Hash`, and so are `Option<T>` and `List<T>` when `T` is, and a struct or enum is `Hash` without an `impl` when every field is. The hash is a fixed, unseeded 64-bit FNV-1a, the same on every platform and on both backends, so a program prints the same value everywhere. A type that holds a `Secret` is refused as `Hash` with `E0354`, and one with any other part that is not `Hash` (a `Result`, a capability) with `E0265`. An `impl Hash` you write is used instead of the derived one. See [ADR 0028](docs/adr/0028-a-map-iterates-in-insertion-order-with-a-fixed-unseeded-hash.md).
- **A host the system cannot route to reads `network unreachable`.** Both backends worded it `host unreachable`, which the networking error table does not have. A connect, send or receive that fails that way now says `network unreachable`, as one that cannot find a route to the network does. A program that matches the text `host unreachable` must match `network unreachable`.
- **DNS queries leave from a random UDP source port.** `HostConnect.exchange_datagram` binds a random port from 49152 to 65535 on the interpreter and natively, where the system picked the port before, and still takes only an answer from the server's address and port with the query's id. Nothing to do.
- **`std.dns`, a stub resolver written in Oska.** `use std.dns`, then `dns.resolve(config, dns.NetExchange.new(net, random), "example.com")` gives a host's addresses (IPv6 first, then IPv4) the same way on every platform: it reads the hosts file and `resolv.conf` (`dns.load_config(fs, net)`), asks each name server over UDP, and asks again over TCP when an answer is truncated. Every answer is untrusted and checked before use, and a failure reads `host not found`, `timed out` or `name server unreachable` whatever the operating system. The message and file parsers (`build_query`, `parse_response`, `parse_hosts`, `parse_resolv_conf`, `parse_ip`) are pure Oska and run natively on all five platforms. Two methods are new and run on both backends: `HostConnect.exchange_datagram(message)` (one UDP datagram out, the first one back whose first two bytes match, in at most 5 seconds) and `NetConnect.system_name_servers()` (Windows' DNS servers, from `GetAdaptersAddresses`; an empty list elsewhere). A Windows executable now imports `iphlpapi.dll` as well. `connect()` does not use `std.dns` yet (tracked in a follow-up issue): the interpreter resolves names with the operating system's resolver, and the native backend resolves only IP addresses and `localhost`. See [ADR 0026](docs/adr/0026-name-resolution-is-an-oska-stub-resolver-and-windows-asks-iphlpapi-for-its-servers.md).
- **`std.dns`, a stub resolver written in Oska.** `use std.dns`, then `dns.resolve(config, dns.NetExchange.new(net, random), "example.com")` gives a host's addresses (IPv6 first, then IPv4) the same way on every platform: it reads the hosts file and `resolv.conf` (`dns.load_config(fs, net)`), asks each name server over UDP, and asks again over TCP when an answer is truncated. Every answer is untrusted and checked before use, and a failure reads `host not found`, `timed out` or `name server unreachable` whatever the operating system. The message and file parsers (`build_query`, `parse_response`, `parse_hosts`, `parse_resolv_conf`, `parse_ip`) are pure Oska and run natively on all five platforms. Two methods are new and run on both backends: `HostConnect.exchange_datagram(message)` (one UDP datagram out, the first one back whose first two bytes match, in at most 5 seconds) and `NetConnect.system_name_servers()` (Windows' DNS servers, from `GetAdaptersAddresses`; an empty list elsewhere). A Windows executable now imports `iphlpapi.dll` as well. `connect()` uses it on both backends. See [ADR 0026](docs/adr/0026-name-resolution-is-an-oska-stub-resolver-and-windows-asks-iphlpapi-for-its-servers.md).
- **On Windows, `NetConnect.system_name_servers()` lists the DNS servers of the adapters that are up, in metric order.** It used `GetNetworkParams`, which lists IPv4 servers only, whatever the adapter's state. It now calls `GetAdaptersAddresses` of `iphlpapi.dll` (the executable's one function of that DLL, replacing `GetNetworkParams`), skips a disconnected adapter and the loopback, lists IPv6 servers as well (eight groups of four hex digits), and leaves out link-local and site-local IPv6 servers, whose scope an address literal cannot carry. A test's `t.random` gives the same bytes on every run. A negative `n` panics with `P0042`, and one past 256 MiB with `P0043`.

On x86_64 Linux the binary is about a quarter smaller. `oskac run --interpret` is about 10% faster on the site build with the glibc build, and up to a third faster on some loops. The musl build gains less. Nothing to do: programs print the same output.

On x86_64 Linux the binary is about a third smaller, and `oskac run --interpret` is 9 to 24% faster on loops, lists and recursion, and about the same on the site build. A bug inside `oskac` now prints `oskac: internal error: ...` with a request to report it, removes the temporary files it made and exits 101, as before. Nothing to do: programs print the same output.
- **Bitwise operators, shifts and rotations on `U8`, `U32` and `U64`.** `&`, `|`, `^`, `~`, `<<`, `>>`, and the methods `rotl(n)` and `rotr(n)`. A shift or rotation by the type's width or more, or by a negative amount, panics with `P0008`. Mixing one of these operators with another operator, or chaining shifts, without parentheses is `E0108`, with a machine fix that adds them. The operators on any other type are `E0223`.
- **Wrapping arithmetic and integer conversions.** `wrapping_add`, `wrapping_sub` and `wrapping_mul` on `U8`, `U32` and `U64`. `to_int`, `to_u8`, `to_u16`, `to_u32` and `to_u64` convert between `Int` and the unsigned types and panic with `P0001` when the value does not fit; `wrapping_to_u8`, `wrapping_to_u16` and `wrapping_to_u32` keep the low bits of a wider unsigned value.
- **`Bytes`, a packed buffer of bytes.** `Bytes.new()`, `Bytes.zeroed(len)`, `Bytes.from_hex(text)` and `"text".to_bytes()` make one; `len`, `get`, `at`, `slice`, the endian reads `read_u16_be` to `read_u64_le`, `to_hex` and `to_text` read it; `push`, `set`, `append` and the endian pushes `push_u16_be` to `push_u64_le` change it through a `var`, in place when nothing else holds it. `Bytes` has `Eq` and `Hash`, and `dbg` shows its hexadecimal digits. An index out of bounds in `at` or `set` panics with `P0002`, a slice or read out of bounds with the new `P0042`, and a buffer that would grow past 256 MiB with the new `P0043` (not yet checked for `String.to_bytes` or the capabilities' `read_bytes`, which give a buffer of any length).
- **Secret integers: compute on keys without exposing them.** `Secret.new(value)` makes a `Secret<U8>`, `Secret<U32>`, `Secret<U64>`, `Secret<Bool>` or `Secret<Bytes>`; it is not an audit site, and `expose()` stays the only way out. On secret integers `+ - *` wrap, the bitwise and shift operators, `rotl` and `rotr` work, and a public operand of the same type gives a secret result; `ct_eq` gives a `Secret<Bool>`, which combines with `and`, `or`, `xor` and `not`, and `c.ct_select(a, b)` picks without a branch. `Secret<Bytes>` reads secret integers at public offsets, and compares with `constant_time_eq`. The checker refuses a secret that would decide a branch (`E0353`), an index, offset, length or hash key (`E0354`), a division, remainder or shift amount (`E0355`), or an ordering (`E0356`); `==` on a secret integer is `E0351`, whose fix now rewrites it to `ct_eq`. `ct_select` on two buffers of different lengths panics with `P0042`.
- **Bytes from outside are untrusted, and files can be read and written as bytes.** `DirRead.read_bytes(path)` and `FileRead.read_bytes()` give a file's bytes as they are, UTF-8 or not, as `Untrusted<Bytes>`; `DirWrite.write_bytes(path, contents)` and `FileWrite.write_bytes(contents)` write exactly the bytes given, confined as the text methods are. `Connection.send_bytes` and `receive_bytes` are declared. Untrusted bytes where trusted `Bytes` is required are `E0300`, every `Bytes` operation keeps the trust of its inputs (`to_text()` of untrusted bytes is `Option<Untrusted<String>>`), and `.assume_trusted()` on bytes vouches for them and is an audit site. `Untrusted<Bytes>` is allowed; `E0320` still rejects `Untrusted<...>` of any other type except `String`.
- **The native backend checks that secret operations compile to constant-time code.** Operations on secret integers, `Secret<Bool>` and `Secret<Bytes>`, `ct_eq`, `ct_select` and the constant-time comparisons are lowered with no branch. After optimizing, on every target, the backend follows each secret value through registers and calls and refuses to build, with the new internal error `E0398` and nothing written, if one would decide a conditional branch or the address of a load, store or call. A value stored to memory and loaded back is not followed; secrets are marked again where they are read out of their `Secret`. `E0398` is a bug in `oskac` to report; nothing in your programs changes, and the interpreter computes the same values with no timing promise.

Give it a module (`std.sql`) or an item (`List.push`) to see just that, and `--format=json` for tools. The same reference is on oskalang.dev at `/api/`, with `/api.json` for agents. See [`oskac doc`](docs/guide/cli-reference.md#oskac-doc).
- **Guides for bytes and secrets.** [Bytes and binary data](docs/guide/bytes.md) and [Secrets and constant-time code](docs/guide/secrets.md) are new, and the language tour has a section on both. The `AGENTS.md` that `oskac new` writes, and the plugin's `oska` skill, now say to keep binary data in `Bytes` and key material in a `Secret`.
- **`std.sha2`: SHA-256 and SHA-512.** After `use std.sha2`, `sha2.sha256(data)` and `sha2.sha512(data)` return the digest of trusted or untrusted bytes as trusted `Bytes`, and `sha2.Sha256` and `sha2.Sha512` hash a piece at a time with `new`, `update` and `finish`; a hasher is a value, so a copy forks it. `sha2.sha256_secret` and `sha2.Sha256Secret` hash a `Secret<Bytes>` into a secret digest in constant time. Every function is pure and the module has no audit site. Like `std.json`, it is written in Oska: it runs under `oskac run`, `test` and `build` on every platform, with no `E0371`, and the authority report lists only your program's own functions, not the module's. The code is hand-written and unaudited; it is tested against FIPS 180-4's examples and NIST's test vectors.
- **`std.ecdsa`: verifying ECDSA signatures on P-256 and P-384.** After `use std.ecdsa`, `ecdsa.PublicKey.from_bytes(curve, bytes)` loads a SEC1 uncompressed point (`ecdsa.Curve.P256` or `ecdsa.Curve.P384`) from trusted or untrusted bytes, with no trust assertion, and returns `None` unless both coordinates are below the field prime and the point is on the curve; `key.to_bytes()` gives the encoding back. `ecdsa.verify(key, digest, signature)` checks a fixed-width `r || s` signature and `ecdsa.verify_der` a strict DER one, as X.509 and TLS carry it. You pass the digest of the message, made with the hash the signature names (`std.sha2`); a digest longer than the curve's order is cut to its leftmost bytes. A signature with `r` or `s` outside 1 to n - 1, a wrong length or a non-DER encoding is `false`. There is no signing. Every function is pure and the module has no audit site. The code is hand-written and unaudited; it is tested against RFC 6979's examples and edge cases on both backends, and every Wycheproof ECDSA vector in the files used, natively on every platform.
- **`std.rsa`: verifying RSA signatures.** After `use std.rsa`, `rsa.PublicKey.from_components(modulus, exponent)` loads big-endian integers from trusted or untrusted bytes, with no trust assertion, and returns `None` unless the modulus is odd and 2048 to 8192 bits and the exponent is odd, at least 3 and below 2^32. `rsa.verify_pkcs1(key, hash, digest, signature)` checks an RSASSA-PKCS1-v1_5 signature against the one encoding RFC 8017 allows (a `DigestInfo` with its `NULL` parameter), and `rsa.verify_pss` an RSASSA-PSS signature made with MGF1 over the same hash and a salt as long as the digest; `hash` is `rsa.HashAlgorithm.Sha256`, `Sha384` or `Sha512`, and you pass the digest of the message. A signature that is not the modulus' length, not below it, or padded any other way is `false`. There is no signing. Every function is pure and the module has no audit site. The code is hand-written and unaudited; it is tested against edge cases on both backends and Wycheproof's RSA signature vectors natively on every platform.
- **`std.p256`: P-256 Diffie-Hellman.** After `use std.p256`, `p256.public_key(scalar)` gives the public point of a 32-byte `Secret<Bytes>` scalar, and `p256.shared_secret(scalar, peer)` the x coordinate of the scalar times a peer's SEC1 uncompressed point, both as `Secret<Bytes>`; the peer's point is checked to be on the curve, and a scalar or a peer of the wrong form gives `None`. The curve arithmetic is written over secret integers, so the checker proves no branch or memory address depends on the scalar and the native backend keeps that on every platform; the results are secret, so exposing one (a TLS key share) is your audit site and the module has none. The code is hand-written and unaudited; it is tested against RFC 5903 and edge cases on both backends and Wycheproof's P-256 ECDH vectors natively on every platform. A scalar of zero or of n or more gives `None`, as the entry "`std.p256` refuses a scalar out of range" says; pick scalars from 1 to n - 1.
- **`std.x509`: certificates and the root store.** After `use std.x509`, `x509.Certificate.parse(der)` reads a DER certificate from trusted or untrusted bytes with a strict parser (a BER length, an over-long length or a trailing byte is `X509Error.Malformed`), with no trust assertion. `x509.verify_server(store, leaf, others, host, now)` builds a path from the server's certificates, in any order and with extras, to a root in `x509.TrustConfig.default()`, a pinned copy of the roots Mozilla trusts for TLS server authentication (NSS release `NSS_3_134_RTM`), and returns the path or an `X509Error` with a stable kind: it checks each certificate's validity at the time you pass in (no clock is read), the signatures (ECDSA P-256 and P-384, RSA PKCS#1 v1.5 and PSS, Ed25519), basic constraints, key usage, extended key usage, name constraints, Mozilla's "distrust after" dates, and the host name as RFC 9525 says. `host` is trusted text, as are the bytes and text given to `TrustConfig.with_root_der` and `with_root_pem` to trust a root of your own; `with_roots` and `only_roots` take parsed certificates, and `x509.parse_der` and `x509.parse_pem` read them from untrusted input. A path is at most 8 certificates and one validation at most 64 signature checks (`LimitExceeded`), the server's certificate must have an extended key usage naming server authentication, a CA's name constraints apply to every certificate below it, and issuers are chosen by key identifier too. `verify_chain` is the same without the host name. Every function is pure and the module has no audit site. The code is hand-written and unaudited; it is tested against crafted chains for every failure kind on both backends and every real root in Mozilla's store natively. See [Certificates and the root store](docs/guide/x509.md), including how the roots are regenerated.
- **`sha2.sha384(data)`**, the SHA-384 digest of trusted or untrusted bytes, 48 bytes, for ECDSA P-384 and SHA-384 signatures. It is tested against FIPS 180-4's examples and digests of every length from 0 to 130 bytes.
- **`std.ed25519`: verifying Ed25519 signatures.** After `use std.ed25519`, `ed25519.PublicKey.from_bytes(bytes)` loads a 32-byte key from trusted or untrusted bytes, with no trust assertion, and returns `None` unless it canonically encodes a point of the curve that is not of small order; `key.to_bytes()` gives the encoding back. `ed25519.verify(key, message, signature)` checks a signature strictly as RFC 8032 says, with the cofactorless equation OpenSSH uses: a signature that is not 64 bytes, a non-canonical or small-order `R`, or an `S` not below the group order is `false`, so signatures are not malleable. There is no signing. Every function is pure and the module has no audit site. The code is hand-written in Oska and unaudited; it is tested against RFC 8032's vectors and every Wycheproof Ed25519 vector.
- **`std.hmac`: HMAC-SHA-256, and secret text as secret bytes.** After `use std.hmac`, `hmac.sha256(key, message)` gives the tag of trusted or untrusted bytes under a `Secret<Bytes>` key as a `Secret<Bytes>`, and `hmac.verify_sha256(key, message, tag)` checks a tag received in constant time and returns a public `Bool`, `false` for a tag that is not 32 bytes. A key of any length works. Both are pure, and the module has no audit site: expose a tag in your own code if you need it in the clear, and `oskac audit` lists that call. The prelude's new `Secret<String>.to_bytes()` turns a secret from `Env.secret` into a `Secret<Bytes>` key without exposing it; it is not an audit site. The code is hand-written and unaudited; it is tested against RFC 4231's test cases and Wycheproof's HMAC-SHA-256 vectors, on the interpreter and natively on every platform.
- **`std.sshsig`: OpenSSH keys and `ssh-keygen -Y sign` signatures.** After `use std.sshsig`, `sshsig.PublicKey.parse(line)` reads an `ssh-ed25519` key line such as `site/oska-release.pub` (another key type is `UnsupportedAlgorithm`), with `comment()`, `fingerprint()` (the `SHA256:` text `ssh-keygen -l` prints) and `ed25519()`. `sshsig.verify(signature, message, namespace, key)` checks an armored signature, `sha256` or `sha512`, and returns `Result<(), SshsigError>`: `WrongKey`, `WrongNamespace`, `UnsupportedAlgorithm` or `BadSignature`, after `Armor`, `Malformed` or `UnsupportedVersion` from parsing; `sshsig.Signature.parse` with `public_key()`, `namespace()` and `hash_algorithm()` reports what a signature claims first. The key line and the namespace are trusted text only (`E0300` otherwise), so a key read from a file needs your own `.assume_trusted()`, which `oskac audit` lists; the module has no audit site of its own, and a hostile signature file gives an error, never a panic. It is tested against signatures made by `ssh-keygen` and every published release's `SHA256SUMS.sig`, on the interpreter and natively on every platform.
- **`std.x25519`, `std.hkdf`, `std.chacha20poly1305` and `std.aes128gcm`: the key exchange and encryption TLS 1.3 needs.** After `use std.x25519`, `x25519.public_key(scalar)` and `x25519.scalarmult(scalar, peer)` are RFC 7748's X25519 on a `Secret<Bytes>` scalar, giving `Option<Secret<Bytes>>` (`None` unless the lengths are 32); `std.hkdf` has `hkdf.extract(salt, ikm)` and `hkdf.expand(prk, info, length)` (RFC 5869 with HMAC-SHA-256, `None` over 8160 bytes); and `std.chacha20poly1305` and `std.aes128gcm` have `seal(key, nonce, aad, plaintext)` and `open(key, nonce, aad, sealed)` with a 12-byte nonce, where `open` checks the tag in constant time and gives `None` for a forgery. Keys and everything computed from them are `Secret<Bytes>`, so a program that puts a result on the wire exposes it in its own code; the modules have no audit site. The AES is bitsliced, with no table indexed by a secret, and the native backend checks every secret operation compiles to branch-free code. They are tested against the RFCs, the GCM specification and Wycheproof on the interpreter and natively on every platform. Like the other crypto modules they are hand-written and unaudited. See [the guide](docs/guide/hashing-and-signatures.md#key-exchange-and-encryption).
- **`Approval` and `Approver`: a person's yes to one action.** `Approver.terminal(stdin, stderr)` asks on standard error, never standard output, and reads the answer from standard input; `approver.confirm(summary, details)` shows the summary and each detail as `dbg` shows text, so control and bidirectional characters appear as escapes, and returns `Some(Approval)` only on `y` or `yes`. An `Approval` cannot be made by hand. A tool calls `approval.consume(summary, details)`, which succeeds once: a second use, of the approval or any copy of it, is refused with `ApprovalError.Used`, and an approval for a different action with `ApprovalError.Mismatch`. In a test, `t.approver` answers from `t.answer_approval(yes)` and `t.approvals_asked()` gives the summary and details of each question it was asked. `TestContext` gains the field `approver`. See [Approvals](docs/guide/capabilities.md#approvals).
- **`std.json`: read and write JSON safely.** `use std.json`, then `json.parse(text)` gives a `json.Value` or a `json.Error` with a byte offset and a reason. Every string it reads, keys included, is untrusted text, while numbers and booleans are trusted; `Number.to_int` gives `None` for a fraction, an exponent or an integer too large for an `Int`. Input over `json.MAX_LENGTH` (8 MiB), nesting deeper than `json.MAX_DEPTH` (128) and a key repeated in one object are errors, never a panic. `json.encode(value)` writes canonical JSON on one line, escaping every control character, U+2028 and U+2029. `json.Schema` builds closed object, string, integer, number, boolean, enumeration and list schemas, prints them as JSON Schema, and `validate`s a value, giving the first violation's path; `json.decode(text, schema, read)` does all three. The module is written in Oska and runs on both backends.
- **`Budget`, authority to spend model tokens and calls.** `main` may declare a `Budget`, which is unlimited; `budget.limit(tokens, calls)` gives a child budget clamped to what its parent has left, listed as an attenuation in the authority report, and `t.budget` in a test has 100000 tokens and 100 calls. `reserve(tokens)` holds tokens and one call before a request, refusing with `OverBudget` when the budget or any budget it was limited from has less left, or has no tokens left at all; the `Reservation` it gives is settled once, with `debit(input, output, cache_creation, cache_read)` or `release()`. `remaining()` and `spent()` report the counters, which every copy of a budget shares. `std.llm` will spend from it. See [Budgets](docs/guide/capabilities.md#budgets).
- **`std.mcp`: tools an agent can call, each with its own authority.** `use std.mcp`, then implement `mcp.Toolset` for a `cap struct` holding the narrowed capabilities your tools need: `specs` lists each tool's `mcp.ToolSpec` (a name, a description, an input `json.Schema` and an optional title), and `call(name, args)` runs one and returns an `mcp.ToolResult` (`text`, `json` or `error`; its text is untrusted). Write `call` as a `match` on the name with one string-literal arm per tool, and `oskac check` lists each tool under `call` with the capabilities its arm reaches, with the default arm, and flags a tool that writes to standard output, a spec with no arm and an arm with no spec, or says the names were not checked when `specs` does not name them with literals; JSON reports carry the same under a new `toolset` key on `call`'s entry. A `call` of any other shape is reported once for the whole toolset, marked as not split per tool. `mcp.serve(stdin, stdout, info, tools)` then makes the program an MCP server over standard input and output (see the next entry).
- **`std.mcp`: serve a `Toolset` over MCP.** `mcp.serve(stdin, stdout, mcp.ServerInfo.new(name, version), tools)` reads one JSON-RPC message per line and answers each, until standard input closes, for any MCP client, in protocol 2026-07-28 (`server/discover`, `_meta` on every request, `-32602` for missing fields and `-32022` for another version) and 2025-11-25 (`initialize`, `notifications/initialized`, `ping`), with `tools/list` and `tools/call`. It first returns an `mcp.McpError`, before it reads anything, for two tools with one name, a name that is not 1 to 128 ASCII letters, digits, `_` and `-`, or an input schema that is not an object. It answers an unknown tool itself and checks the arguments of every call against the tool's schema, so `Toolset.call` only sees valid arguments and a name from its own specs; failed arguments are a tool error (`isError`) naming the field. Each tool's `readOnlyHint`, `destructiveHint` and `openWorldHint` are derived from the capabilities the checker computed it reaches, and cannot be written by hand. `mcp.handle(session, tools, line)`, with a session from `mcp.Session.new(info, tools)`, is the per-message function, public so a program's tests can drive its server with recorded lines and no process. `examples/notes_server.osk` is a worked server with its authority report and tests. A tool that reaches `Stdout` still writes into the protocol stream: the report flags it. A message line over `mcp.MAX_LINE` (1 MiB) gets `-32600`, but standard input still buffers the whole line first, so this keeps the framing and does not bound memory. A message with no `id` never gets a reply. `serve` lists the tools once and serves that list.

## v0.6.0

Released 2026-11-20.

v0.6.0 adds the native backend for Windows, so all five supported platforms are native. It also turns the parity gate on and adds `oskac release`. These are the changes you can see:

- **`run`, `test` and `build` are native on x86_64 Windows**, as on Linux and macOS. Before, `run` and `test` used the interpreter there, tens of times slower on program logic. `--interpret` still selects the interpreter. See [platform support](docs/guide/cli-reference.md#platform-support).
- **`oskac build` on Windows writes a Windows executable, `<name>.exe`**, where v0.5.0 wrote an aarch64 Linux one. To get the old output, build with `--target linux-aarch64`. `--target windows-x86_64` builds a Windows executable from any host, and `--target all` writes five executables. The same program gives the same bytes on every host.
- **The parity gate: a program the native backend cannot compile yet is an error.** `oskac run` and `oskac test` refuse it with `E0390`, the same diagnostic `oskac build` prints, and exit code 2. Before, they ran it on the interpreter after a one-line note. If a program stops running after the upgrade, run it with `--interpret` and report the construct the message names. From this release on, a language change lands on all five platforms at once.
- **Windows file access is confined race-free.** On both backends, each path is opened one component at a time beneath the capability's open root handle. A symlink, a junction or any other reparse point, a hard-linked file, or a reserved device name such as `CON` is refused, as on Linux and macOS. Before, Windows checked a path and then opened it, so a junction swapped in between could escape the root.
- **`oskac release` builds an application for all five platforms** into one directory. It writes a `SHA256SUMS` that names the release and signs it with your SSH key, in the format `oskac`'s own releases use. The version, key and name refusals are `E0395`, `E0396` and `E0397`. See [Releasing an application](docs/guide/releasing.md).

## v0.5.0

Released 2026-11-19.

v0.5.0 adds native backends for macOS, on Apple silicon and Intel, and words every `IoError` in Oska's own text. Programs keep their meaning; these are the changes you can see:

- **`run`, `test` and `build` are native on macOS**, on both processors, as on Linux. Before, `run` and `test` used the interpreter on a Mac, tens of times slower on program logic. A program the native backend cannot compile yet still runs on the interpreter after the one-line `E0390` note, and `--interpret` still selects the interpreter. See [platform support](docs/guide/cli-reference.md#platform-support).
- **`oskac build` on a Mac writes a macOS executable for that Mac**, where v0.4.0 wrote an aarch64 Linux one. To get the old output from a Mac, build with `--target linux-aarch64`.
- **`--target macos-aarch64` and `--target macos-x86_64`** build macOS executables from any host, and `--target all` writes four executables, where it wrote two. Neither is refused with `E0394` any more. The same program gives the same bytes on every host.
- **macOS executables are ad-hoc signed**, so they run on a Mac with no Apple tools needed to build them, but Gatekeeper refuses them after a download. To distribute one, see [Signing and notarizing for macOS](docs/guide/macos-signing.md).

A path the failure concerns still comes first. If a test compares an error message, update its expected text from this table (the full table is in the [runtime reference](docs/runtime.md#errors-and-traits)):

  | Before (Linux) | After |
  | --- | --- |
  | `` `x`: No such file or directory (os error 2) `` | `` `x`: not found `` |
  | `` `x`: Permission denied (os error 13) `` | `` `x`: permission denied `` |
  | `` `x`: Not a directory (os error 20) `` | `` `x`: not a directory `` |
  | `` `x`: Is a directory (os error 21) `` | `` `x`: is a directory `` |
  | `` `x`: File exists (os error 17) `` | `` `x`: already exists `` |
  | `` `x`: Directory not empty (os error 39) `` | `` `x`: directory not empty `` |
  | `No space left on device (os error 28)` | `no space left on device` |
  | `Broken pipe (os error 32)` | `broken pipe` |
  | any other system error, such as `` `x`: Input/output error (os error 5) `` | `` `x`: I/O error `` |

  The messages that refuse confined access (a symlink, a hard link, a path that escapes its root) are unchanged.

## v0.2.0

Released 2026-11-10.

v0.2.0 is a **breaking change** to the filesystem capabilities, with no deprecation period ([ADR 0008](docs/adr/0008-file-access-goes-through-confined-capabilities.md)). `Fs`, `FsRead`, and `FsWrite` no longer read or write anything. They only attenuate, and every read and write goes through a directory capability (`DirRead`, `DirWrite`) or a file capability (`FileRead`, `FileWrite`). A program that calls a removed method fails `oskac check` with `E0273`, whose message shows the fix. The check cannot apply it for you, because only you know the root.

Each removed method has a one-line migration. Replace `<root>` with the directory the program should reach:

| Before (v0.1.0) | After (v0.2.0) |
| --- | --- |
| `fs.read_to_string(path)` on an `FsRead` | `fs.restrict_to("<root>").read_to_string(path)` |
| `fs.list_dir(path)` on an `FsRead` | `fs.restrict_to("<root>").list_dir(path)` |
| `fs.write(path, text)` on an `FsWrite` | `fs.restrict_to("<root>").write(path, text)` |
| `fs.create_dir(path)` on an `FsWrite` | `fs.restrict_to("<root>").create_dir(path)` |
| `fs.restrict_to("file")` naming a single file | `fs.restrict_to_file("file")`, then `.read_to_string()` or `.write(text)` with no path |
| Reading anywhere through an `FsRead` | `fs.restrict_to("/")`, which the authority report shows |

Other things change with it:

- A function that took an `FsRead` or an `FsWrite` to read or write files now takes a `DirRead` or a `DirWrite`, or a `FileRead` or a `FileWrite`.
- `main` may not declare a directory or file capability (`E0217`). Declare `Fs`, `FsRead`, or `FsWrite`, and attenuate.
- `restrict_to` on a file no longer works. The capability it returns is broken, and every operation on it fails with a "not a directory" `IoError`. Use `restrict_to_file`.
- Every symlink beneath a root is refused, including one that points inside the root.
- `oskac check` now lists each attenuation under its function, in the report and in the JSON `attenuations` array.
- **Contracts are now enforced.** In v0.1.0 a `requires` or `ensures` clause was type-checked but never evaluated, so a contract that was silently false did nothing. In v0.2.0 every clause runs on every call, in every build, including `--release`. A false `requires` panics with `P0006` at the call, and a false `ensures` panics with `P0007` at the clause, both with exit code 101. A program that relied on a wrong contract being ignored now panics: fix the call or the function, or correct the contract. Two placements that v0.1.0 accepted are now errors: a contract on a method of `impl Trait for Type` (`E0218`, move it to the trait's declaration of the method, where it binds every impl) and a contract on `main` (`E0219`). A `?` or `return` directly in a contract is `E0282`. A contract's `==`, `!=` and interpolation now count as calls of the `Eq` and `Display` impls they reach, so using them on a capability-bearing value is `E0280`.
- **Capabilities can no longer hide in generic code or in closures.** v0.1.0 let some programs pass a capability where only pure code was allowed, and these are now errors:
  - A type argument that breaks what a generic assumes of its type parameter is the new `E0274`: a capability-bearing type for a parameter that a contract uses, or that a closure used as a plain `fn` captures, and a type holding a `Scope` for a parameter that an unscoped closure captures. That includes a trait's `Self`: a capability-bearing type cannot implement a trait whose contract uses `self`. Pass the capability as its own parameter, or take a `cap fn`.
  - A closure is a `cap fn` when something it captures turns out capability-bearing later in the body, as in `let g = || xs` before `xs.push(out)`. If it was already used as a plain `fn`, that is `E0270` at the closure. A value already used as a plain `fn` also rejects a `cap fn` assigned to it later (`E0270`).
  - A mutating method writes its receiver back, so `push` of untrusted text into a `List<String>` is now `E0300`, and `push` of a `cap fn` into a `List<fn()>` is `E0270`. Declare the list with `Untrusted<String>` or `cap fn`.
  - A closure that captures a value whose type turns out to hold a `Scope` only later in the body, as in `var xs = []` and `let g = || xs.len()` before `xs.push(s)`, is `E0292`. Declare the value with its type first.

  Where values meet, a plain `fn` and a `cap fn` now join to `cap fn` instead of being a type error, so some programs that v0.1.0 rejected now check.

An example of the migration:

```oska error=E0273
fn count(fs: FsRead, path: Path) -> Result<Int, IoError> {
    Ok(fs.read_to_string(path)?.lines().count())
}
```

```oska
fn count(fs: FsRead, path: Path) -> Result<Int, IoError> {
    Ok(fs.restrict_to("/srv/app").read_to_string(path)?.lines().count())
}
```

### Security fixes

v0.1.0 let a capability reach code that was meant to be pure. These are now errors (see the bullets above):

- A closure that captured a value whose type was not known yet could carry `Stdout` into a pure function (`E0270`).
- A generic function could hand a capability to a plain `fn` through a type parameter (`E0274`).
- A `Scope` could escape its block through a generic capture (`E0274`, `E0292`).
- `push` could add untrusted text to a `List<String>` (`E0300`).

## v0.1.0

Released 2026-11-10.

v0.1.0 is the first release of Oska, a pre-alpha. It is the first signed release, and the first with a one-line installer. These are the things you can use:

- **`oskac`, the compiler and runner.** `oskac check` type-checks a program and prints its authority report. `oskac run` runs it on the interpreter, and `oskac test` runs its `test` blocks. `oskac explain <code>` shows a diagnostic code's entry.
- **Signed binaries for five platforms:** Linux x86_64 and aarch64, macOS x86_64 and aarch64, and Windows x86_64. Each release has a `SHA256SUMS` signed with the release key.
- **The one-line installers**, `install.sh` and `install.ps1`. They verify the checksum and the signature and install to `~/.oska/bin`. Run the installer again to update.
- **The site, oskalang.dev**, built by an Oska program from the repository's docs, with the guides, the error-code catalog, `llms.txt` and a Markdown copy of every page.
